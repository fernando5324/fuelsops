# ADR-021: Tabla de configuraciones personalizables del tenant

## Estado

Aceptado

## Decisión

Lo más coherente es que order_code_prefix y order_code_start pertenezcan a una configuración del tenant, en lugar de agregarlos directamente a tenants.

## Instrucciones

La idea sería que tenants contenga la identidad de la entidad, mientras que tenant_settings contenga la configuración operativa y de presentación de esa entidad.

Campos que recomiendo
```
| Campo                       | Tipo            | Propósito                                              |
| --------------------------- | --------------- | ------------------------------------------------------ |
| `id`                        | BIGINT          | ID interno de la configuración                         |
| `tenant_id`                 | BIGINT          | Tenant al que pertenece. Único, relación 1:1           |
| `organization_name`                 | VARCHAR(150)    | Nombre comercial que se mostrará en el sistema         |
| `organization_description`          | VARCHAR(500)    | Descripción breve de la entidad, opcional              |
| `default_language`          | VARCHAR(10)     | Idioma predeterminado, por ejemplo `es`                |
| `timezone`                  | VARCHAR(100)    | Zona horaria del tenant, por ejemplo `America/Lima`    |
| `contact_email`             | VARCHAR(150)    | Correo de contacto                                     |
| `contact_phone`             | VARCHAR(50)     | Teléfono de contacto                                   |
| `address`                   | TEXT            | Dirección                                              |
| `business_hours`            | JSON            | Horarios de atención, si posteriormente son necesarios |
| `social_links`              | JSON            | Redes sociales y otros enlaces                         |
| `branding`                  | JSON            | Logo, colores y configuración visual                   |
| `order_code_prefix`         | VARCHAR(20)     | Prefijo de los códigos de pedido, por ejemplo `PED`    |
| `order_code_start`          | BIGINT UNSIGNED | Número inicial de la secuencia de pedidos              |
| `created_at` / `updated_at` | TIMESTAMP       | Auditoría                                              |
| `created_by` / `updated_by` | BIGINT          | Usuario que creó/modificó la configuración             |
| `is_deleted`                | TINYINT         | Mantiene la convención actual del proyecto             |
```

> **Nota de deriva (2026-10-07):** `contact_email` y `contact_phone` **no se
> crearon en la BD** (tampoco están en `docs/02_Database/database.sql`, la
> fuente canónica). El correo y el teléfono de la organización viven en
> **`tenants.email`** y **`tenants.phone`**, que son los que expone y guarda la
> página de empresa del **ADR-026** (`/configuracion/compania`,
> `SettingsController::company()/updateCompany()`). Las dos filas de esta tabla
> y las dos líneas del DDL de más abajo se conservan como diseño original; si
> alguna vez se implementan, habrá que migrar los datos desde `tenants`.

Sobre order_code_start

Aquí haría una pequeña distinción importante.

order_code_start debería representar el número desde el cual comienza la generación automática, no necesariamente "el último número utilizado".

Por ejemplo:
```
order_code_prefix = PED
order_code_start  = 1
```
produce:
```
PED-000001
PED-000002
PED-000003
```
Otro tenant podría tener:
```
order_code_prefix = OC
order_code_start  = 500
```
y comenzar:
```
OC-000500
OC-000501
OC-000502
```
Pero no usaría order_code_start para llevar el contador actual. Para eso, posteriormente podemos tener una secuencia/contador independiente. Esto es importante porque el código puede ser editable y no queremos depender de MAX(code).

Sobre branding y social_links

Mantendría estos como JSON porque son configuraciones variables y no justifican necesariamente tablas propias en esta etapa.

Por ejemplo:
```
{
    "primary_color": "#1B3A6B",
    "secondary_color": "#F47920",
    "logo": "..."
}
```
Y:
```
{
    "facebook": "...",
    "instagram": "...",
    "linkedin": "...",
    "website": "..."
}
```
No incluiría todavía template_id, announcement, popup, hero_presentation, etc. de tu otro proyecto porque esos campos pertenecen específicamente al concepto de sitios públicos/templates. Para este sistema de gestión de pedidos no necesitamos arrastrar esa arquitectura.

SQL recomendado
```
CREATE TABLE IF NOT EXISTS tenant_settings (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    tenant_id BIGINT UNSIGNED NOT NULL,

    organization_name VARCHAR(150) NOT NULL,
    organization_description VARCHAR(500) NULL,

    default_language VARCHAR(10) NOT NULL DEFAULT 'es',
    timezone VARCHAR(100) NOT NULL DEFAULT 'America/Lima',

    contact_email VARCHAR(150) NULL,
    contact_phone VARCHAR(50) NULL,
    address TEXT NULL,

    business_hours JSON NULL,
    social_links JSON NULL,
    branding JSON NULL,

    order_code_prefix VARCHAR(20) NOT NULL DEFAULT 'PED',
    order_code_start BIGINT UNSIGNED NOT NULL DEFAULT 1,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by BIGINT UNSIGNED NULL,

    updated_at TIMESTAMP NULL DEFAULT NULL
        ON UPDATE CURRENT_TIMESTAMP,
    updated_by BIGINT UNSIGNED NULL,

    is_deleted TINYINT(1) NOT NULL DEFAULT 0,

    UNIQUE KEY uk_tenant_settings_tenant (tenant_id),

    CONSTRAINT fk_tenant_settings_tenant
        FOREIGN KEY (tenant_id)
        REFERENCES tenants (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_tenant_settings_created_by
        FOREIGN KEY (created_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_tenant_settings_updated_by
        FOREIGN KEY (updated_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT

) ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_unicode_ci;
```

> Las columnas `contact_email`/`contact_phone` de este DDL **no se aplicaron**
> (ver la nota de deriva junto a la tabla de campos): el contacto vive en
> `tenants.email`/`tenants.phone`.

## Una consideración para is_deleted

Como tenant_settings tiene una relación 1:1 con tenants, el UNIQUE (tenant_id) significa que aunque marques la configuración como is_deleted = 1, no podrías crear otra configuración para ese mismo tenant.

En este caso, yo mantendría is_deleted por consistencia con tu arquitectura, pero conceptualmente esta tabla no debería eliminarse físicamente ni necesitar múltiples versiones. La configuración simplemente se actualiza.

Por eso, en esta tabla el is_deleted tiene más función de auditoría/convención que de comportamiento normal.

Estructura resultante

Quedaría bastante limpia:
```
tenants
   │
   └── tenant_settings
          ├── Información general
          ├── Contacto
          ├── Localización
          ├── Branding
          ├── Redes sociales
          └── Configuración de pedidos
                ├── order_code_prefix
                └── order_code_start

orders
   ├── tenant_id
   └── code
```
Y conceptualmente:
```
Tenant
│
├── Identidad
│   └── tenants
│
├── Configuración
│   └── tenant_settings
│
└── Pedidos
    └── orders
```
Esto además deja abierta la puerta a que mañana agregues configuraciones como default_currency, date_format, decimal_places, order_code_padding, etc., sin seguir haciendo crecer innecesariamente la tabla tenants.

## Nota de implementación (2026-10-03)

Estado: **tabla creada y poblada**; la pantalla de configuración **no** forma parte de esta entrega (ver ADR-020 §27.10).

### Se aplicó el DDL completo de este ADR

`tenant_settings` se creó en la BD viva con **todas** las columnas de la sección de DDL de este ADR (identidad, contacto, localización, branding, redes sociales y configuración de pedidos), no solo con las tres del código. Motivo: el ADR propone esta tabla como el hogar de la configuración por organización, y recortarla habría dejado el resto del diseño sin soporte; agregar columnas después es aditivo.

### `order_code_padding` se añadió aquí

Este ADR mencionaba `order_code_padding` solo como ejemplo futuro (línea 190). Al implementar ADR-020 resultó necesario de verdad: el ancho del relleno (`PED-000001`) forma parte del formato del código y debe poder cambiar sin tocar `config/platform.php`.

```
order_code_padding TINYINT UNSIGNED NOT NULL DEFAULT 6
```

### Valores del tenant 1

| Columna | Valor |
|---|---|
| `organization_name` | el nombre real del tenant en la BD viva (`Fuel Erp`) |
| `default_language` | `es` |
| `timezone` | `America/Lima` (de `config('app.timezone')`) |
| `order_code_prefix` | `PED` |
| `order_code_start` | `1` |
| `order_code_padding` | `6` |

`SEEDS.sql` siembra la fila con el nombre del tenant de la semilla (`Sertoco`), porque los seeds son idempotentes y no deben depender del dato que el cliente haya escrito en la BD.

### Decisiones de modelo

- `TenantSetting` usa `Auditable` + `LogicalDelete` y **no** `BelongsToTenant`: la fila ES de un tenant, así que un scope global sobre `tenant_id` estorbaría a la lectura por `tenant_id`. Mantiene el `is_deleted` por convención, tal como recomienda la sección "Una consideración para is_deleted".
- LaNumeración **no** vive aquí: está en `order_code_counters` (sección 23 de `database.sql`), porque es un contador técnico que se bloquea con `lockForUpdate()` y no configuración editable. Ver `OrderCodeService`.
- `Tenant::settings()` es la relación 1:1; `OrderCodeService::settings()` crea la fila con los defaults de `config('platform.order_code')` cuando una organización todavía no tiene configuración.
