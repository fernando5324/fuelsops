# ADR-020: Código de pedido por Tenant

- **Estado:** Accepted
- **Fecha:** 2026-10-03
- **Ámbito:** Pedidos / Multi-tenancy
- **Proyecto:** Plataforma Sertoco / futura plataforma multi-entidad
- **Relacionado con:** ADR-001 — Estructura inicial de base de datos
- **Relacionado con:** ADR-003 — Arquitectura de comunicación del Frontend

---

## 1. Contexto

La plataforma actualmente gestiona pedidos y utiliza una tabla `orders`.

La plataforma será utilizada por diferentes entidades mediante el concepto de `tenants`.

Cada pedido pertenece a una entidad determinada mediante:

```
orders.tenant_id
```

Por lo tanto, el identificador visible de un pedido no debe ser global para toda la plataforma.

Cada entidad debe poder:

Comenzar su numeración desde cero.
Utilizar una numeración inicial diferente.
Utilizar códigos provenientes de un sistema anterior.
Definir posteriormente un prefijo propio si se requiere.
Editar manualmente el código de un pedido.

El sistema debe permitir que dos entidades diferentes tengan el mismo código sin generar conflicto.

Ejemplo:
```
Tenant A
PED-000001

Tenant B
PED-000001
```
Esto es válido porque cada código pertenece a un tenant diferente.

## 2. Problema

No se debe utilizar el id interno de la tabla orders como código visible del pedido.

El id de base de datos tiene una función técnica y debe permanecer independiente del código utilizado por los usuarios.

Por ejemplo:
```
id: 438
code: PED-000127
```
Si posteriormente el usuario modifica:
```
PED-000127
```
por:
```
PED-2026-0150
```
el registro continúa siendo:
```
id: 438
```
Por lo tanto, el código visible y el identificador interno deben ser conceptos separados.

## 3. Decisión

Se agregará un campo específico para el código visible del pedido:

orders.code

La estructura conceptual será:
```
orders
├── id
├── tenant_id
├── code
├── ...
```
Donde:
```
id
```
- Identificador técnico interno.
- Autoincremental.
- No editable.
- No debe mostrarse como código operativo al usuario.
- Se utiliza para relaciones internas y referencias técnicas.

```
tenant_id
```
- Identifica la entidad propietaria del pedido.
- Obligatorio.
- Permite separar los pedidos entre diferentes entidades.

```
code
```
- Identificador operativo visible para el usuario.
- Editable.
- Pertenece al tenant.
- Puede tener diferentes formatos.
- No debe utilizarse como identidad técnica del registro.
4. Unicidad del código

El código debe ser único únicamente dentro de su tenant.

La restricción será conceptualmente:
```
UNIQUE (tenant_id, code)
```
Esto significa:
```
Tenant 1
PED-000001 ✅
PED-000002 ✅

Tenant 2
PED-000001 ✅
PED-000002 ✅
```
Pero:
```
Tenant 1
PED-000001

Tenant 1
PED-000001 ❌
```
No debe existir duplicidad de código dentro del mismo tenant.

## 5. Formato inicial recomendado

El formato inicial recomendado será:
```
PED-000001
PED-000002
PED-000003
```
Donde:
```
PED
```
representa:
```
Pedido
```
Se utiliza PED en lugar de nombres específicos del cliente o del producto/plataforma.

No utilizar inicialmente:
```
SER
FOP
FO
FuelsOps
```
porque estos nombres pueden estar asociados a una entidad, cliente o marca específica.

El sistema debe poder ser utilizado posteriormente por otras entidades sin que el código visible dependa de Sertoco.

## 6. Código editable

El campo code será editable.

Por ejemplo:
```
PED-000001
```
puede cambiarse a:
```
PED-2026-0150
```
o incluso a un código utilizado anteriormente por la entidad:
```
OC-45892
```
siempre respetando la unicidad dentro del tenant.

El cambio de código no modifica:
```
orders.id
```
ni altera las relaciones existentes del pedido.

## 7. El código no representa el ID interno

No debe existir una dependencia lógica obligatoria entre:
```
orders.id
```
y:
```
orders.code
```
Por ejemplo, no asumir que:
```
id = 438
```
debe producir:
```
PED-000438
```
El código puede coincidir inicialmente con una numeración secuencial, pero esto no debe formar parte de la identidad técnica del pedido.

Ejemplo válido:
```
id: 438
tenant_id: 5
code: PED-000127
```
También es válido:
```
id: 438
tenant_id: 5
code: OC-45892
```

## 8. Numeración por Tenant

La numeración debe considerarse independiente para cada tenant.

Ejemplo:
```
Tenant A
PED-000001
PED-000002
PED-000003
```
Mientras otro tenant puede tener:
```

Tenant B
PED-000001
PED-000002
PED-000003
```

No debe existir un contador global obligatorio para todos los tenants.

## 9. Número inicial

El sistema debe permitir que un nuevo tenant pueda comenzar su numeración desde un valor determinado.

Ejemplo:
```
Tenant A
Número inicial: 1
```

Resultado:
```

PED-000001
PED-000002
PED-000003
```

Otro tenant podría comenzar desde:
```
Número inicial: 500
```
Resultado:
```
PED-000500
PED-000501
PED-000502
```
Esto será especialmente útil cuando una entidad ya tenga una numeración propia antes de incorporarse a la plataforma.

## 10. Migración de códigos existentes

Al incorporar una nueva entidad a la plataforma, no debe ser obligatorio modificar los códigos que ya utiliza.

Por ejemplo, si la entidad actualmente maneja:
```
OC-45890
OC-45891
OC-45892
```
estos códigos pueden conservarse al migrar los pedidos.

El sistema debe validar únicamente que no existan duplicados dentro del mismo tenant.

La plataforma no debe asumir que todos los pedidos históricos utilizan el formato:
```
PED-000001
```

## 11. Configuración futura por Tenant

Aunque el formato inicial será:
```
PED-000001
```
la arquitectura debe dejar abierta la posibilidad de configurar el formato por tenant.

Por ejemplo, conceptualmente:
```
tenant
├── order_code_prefix
├── order_code_start
└── ...
```
Ejemplo:
```
Tenant A
prefix: PED
start: 1
```
Resultado:
```
PED-000001
PED-000002
```
Otro tenant:
```
Tenant B
prefix: ORD
start: 1000
```
Resultado:
```
ORD-01000
ORD-01001
```

Esta configuración no necesariamente debe implementarse completa en la primera versión.

La estructura actual debe evitar decisiones que impidan agregarla posteriormente.

## 12. No confundir código con contador

El hecho de que el código sea editable significa que no debe utilizarse directamente como mecanismo de numeración.

Ejemplo:
```
PED-000001
PED-000002
PED-000003
```

Si el usuario cambia:
```
PED-000003
```
por:
```
PED-2026-0150
```
el siguiente pedido no debe depender de analizar el código anterior para decidir automáticamente su numeración.

El mecanismo de generación de nuevos códigos debe tratarse como una responsabilidad independiente.

## 13. Generación de nuevos códigos

Cuando se cree un pedido nuevo, el sistema debe generar un código según la configuración del tenant.

La lógica debe:

- Identificar el tenant actual.
- Obtener la configuración de numeración correspondiente.
- Generar un nuevo código.
- Validar que no exista dentro del tenant.
- Guardar el pedido.
- Mantener la unicidad mediante la restricción de base de datos.

Debe evitarse una lógica que dependa únicamente de:
```
MAX(code) + 1
```
especialmente cuando el código es editable y puede tener formatos diferentes.

La implementación puede utilizar posteriormente una secuencia/contador independiente por tenant.

## 14. Edición del código

La edición debe estar disponible desde la pantalla de edición del pedido.

Ejemplo:
```
Código del pedido
┌──────────────────────────┐
│ PED-000127               │
└──────────────────────────┘
```
El usuario podrá modificarlo:
```
Código del pedido
┌──────────────────────────┐
│ OC-45892                 │
└──────────────────────────┘
```

Antes de guardar:

- Validar formato cuando corresponda.
- Validar que el código no exista dentro del mismo tenant.
- Mostrar un error claro si existe duplicidad.

Ejemplo:
```
Ya existe un pedido con el código "OC-45892".
```

## 15. Seguridad y aislamiento entre Tenants

Todas las operaciones relacionadas con códigos deben respetar el tenant_id.

No se debe permitir:

- Consultar pedidos de otro tenant.
- Editar códigos de otro tenant.
- Validar duplicidad contra pedidos de otros tenants como si fueran del mismo espacio.
- Utilizar un código como única condición para identificar un pedido.

Las consultas deberán considerar el tenant correspondiente.

Conceptualmente:
```
WHERE tenant_id = ?
AND code = ?
```
No:
```
WHERE code = ?
```
cuando se esté resolviendo una operación contextual de tenant.

## 16. Visualización en el sistema

El código debe convertirse en el identificador visible principal del pedido.

Por ejemplo, en el listado:
```
Código       Cliente                  Estado
--------------------------------------------------
PED-000127   Servicentro Kevin       Pendiente
PED-000128   Cliente ABC             Atendido
```

En el detalle:
```
Pedido PED-000127

Servicentro Kevin E.I.R.L.
```
No es necesario mostrar el id interno al usuario.

El id puede continuar utilizándose internamente para URLs, relaciones y operaciones técnicas.

## 17. Historial y documentos

Cambiar el código del pedido no debe romper ni modificar:

- Historial de estados.
- Detalles del pedido.
- Documentos adjuntos.
- Relaciones con clientes.
- Relaciones con conductores.
- Relaciones con vehículos.
- Relaciones con productos.
- Auditoría.
- Otros registros relacionados.

Todas estas relaciones deben continuar utilizando el orders.id interno.

Ejemplo:
```
orders
id: 438
code: PED-000127
```
Si cambia a:
```
orders
id: 438
code: OC-45892
```
los registros relacionados continúan apuntando a:
```
order_id = 438
```

## 18. Consideración sobre URLs

El código visible no debe convertirse obligatoriamente en la clave técnica de las URLs.

Se puede mantener:
```
/orders/438
```
aunque el usuario vea:
```
PED-000127
```
Esto permite que el código sea editable sin romper enlaces internos ni relaciones técnicas.

Si posteriormente se decide utilizar el código en URLs, deberá evaluarse como una decisión independiente.

## 19. Ejemplo completo
```
Tenant A
tenant_id: 1
```
Pedidos:
```
id: 10
code: PED-000001

id: 11
code: PED-000002

id: 12
code: PED-000003
```
El administrador cambia:
```
PED-000003
```
por:
```
OC-2026-003
```
Resultado:
```
id: 12
code: OC-2026-003
Tenant B
tenant_id: 2
```
Puede comenzar desde cero:
```
id: 50
code: PED-000001

id: 51
code: PED-000002
```
No existe conflicto con:
```
tenant_id: 1
code: PED-000001
```
porque la unicidad se aplica mediante:

tenant_id + code
## 20. Cambios esperados en la base de datos

La implementación deberá revisar la tabla orders.

Debe existir:
```
tenant_id
code
```
Si tenant_id todavía no existe en orders, deberá incorporarse de acuerdo con la arquitectura multi-tenant existente.

Agregar:
```
code VARCHAR(...)
```
con un tamaño suficiente para permitir códigos personalizados.

Se recomienda no limitar inicialmente el código a una longitud excesivamente pequeña.

Ejemplo:
```
code VARCHAR(50) NOT NULL
```
La longitud exacta debe adaptarse a las convenciones actuales de la base de datos.

Agregar una restricción:
```
UNIQUE KEY uq_orders_tenant_code (tenant_id, code)
```
La implementación debe considerar los pedidos existentes antes de crear la restricción de unicidad.

## 21. Migración de pedidos existentes

Antes de agregar code como obligatorio:

- Identificar pedidos existentes.
- Generar códigos iniciales para ellos.
- Garantizar que sean únicos dentro de su tenant.
- Posteriormente establecer code como NOT NULL.
- Agregar la restricción única (tenant_id, code).

No realizar una migración que pueda dejar pedidos existentes sin código.

## 22. Reglas para OpenCode

Antes de implementar:

- Revisar la estructura actual de tenants.
- Revisar la estructura actual de orders.
- Revisar cómo se determina actualmente el tenant autenticado.
- Revisar cómo se crean pedidos.
- Revisar cómo se editan pedidos.
- Revisar las rutas actuales.
- Revisar los formularios React existentes.
- Revisar los Services relacionados con pedidos.
- Revisar el listado de pedidos.
- Revisar la pantalla de detalle.
- Revisar el historial de estados.
- Revisar los documentos relacionados.

No asumir nombres de columnas o estructuras que no existan actualmente.

- Reutilizar las convenciones existentes del proyecto.

## 23. Reglas de implementación

No modificar innecesariamente:

- El flujo público de creación de pedidos.
- El historial de estados.
- Los documentos adjuntos.
- Las relaciones existentes.
- Los cálculos financieros.
- La arquitectura Inertia + Services.
- El diseño actual del panel lateral.

El objetivo de este ADR es introducir correctamente el concepto de código de pedido multi-tenant.

No aprovechar esta tarea para realizar refactors no relacionados.

## 24. Criterios de aceptación

La funcionalidad se considera correcta si:

- Cada pedido tiene un code.
- Cada pedido pertenece a un tenant.
- El id interno permanece independiente del code.
- El código es visible en el listado.
- El código es visible en el detalle.
- El código puede editarse.
- El código puede ser diferente al id.
- Dos tenants pueden utilizar el mismo código.
- Un mismo tenant no puede tener códigos duplicados.
- La validación de unicidad considera tenant_id.
- Los pedidos existentes reciben un código durante la migración.
- Los pedidos históricos mantienen sus relaciones.
- Cambiar el código no afecta al historial de estados.
- Cambiar el código no afecta a los documentos.
- Cambiar el código no afecta a los detalles del pedido.
- Los nuevos pedidos pueden generar códigos automáticamente.
- La generación de códigos está aislada por tenant.
- El sistema no depende de MAX(code) + 1.
- Se mantiene abierta la posibilidad de configurar prefijo y numeración por tenant.
- No se utiliza Sertoco, SER, FuelsOps ni otra marca específica como parte obligatoria del código.

## 25. Resultado esperado

La estructura final debe seguir este concepto:
```
                    PLATAFORMA
                         │
              ┌──────────┴──────────┐
              │                     │
           Tenant A              Tenant B
              │                     │
        ┌─────┴─────┐         ┌─────┴─────┐
        │            │         │            │
    Pedido         Pedido    Pedido       Pedido
    id: 10         id: 11    id: 50       id: 51
    PED-000001     PED-000002 PED-000001   PED-000002
```

El principio fundamental es:

El id identifica técnicamente al pedido. El code identifica operativamente al pedido para el usuario. El código pertenece al tenant y puede ser editable.

La unicidad se garantiza mediante:
```
tenant_id + code
```
y no mediante el código global de toda la plataforma.

## 26. Estado
```
Accepted
```
Esta decisión establece la primera versión del sistema de identificación visible de pedidos para una arquitectura multi-tenant.

La configuración avanzada de prefijos, formatos, secuencias y numeración personalizada por tenant podrá implementarse posteriormente sin modificar el principio fundamental de separar:
```
ID interno
+
Código operativo
```

## 27. Nota de implementación (2026-10-03)

Estado: **implementado y verificado** (E2E 62/62, smoke del motor 12/12, build de Vite OK). Esta sección documenta lo que se construyó realmente, sin reescribir las secciones anteriores.

### 27.1 Esquema aplicado (BD viva + `database.sql`)

Sin migraciones (regla del proyecto): el DDL se aplicó directo a `sertocobd` y se reflejó en el esquema canónico.

| Cambio | Detalle |
|---|---|
| `orders.code` | `VARCHAR(50) NULL` en el primer paso (para poder hacer el backfill), **`NOT NULL`** al final |
| Unicidad | `UNIQUE KEY uq_orders_tenant_code (tenant_id, code)` |
| `tenant_settings` | Sección 22 de `database.sql` (tabla 1:1 con `tenants`, ADR-021) |
| `order_code_counters` | Sección 23 de `database.sql` (contador técnico 1:1 por tenant) |

Restricción importante: el índice **no incluye `is_deleted`**, de modo que el código de un pedido en papelera queda **reservado** (los códigos no se reciclan). Es la misma razón por la que `plant_products` no tiene índice único sobre `is_deleted` (ver Lecciones registradas).

### 27.2 Modelos y configuración

- `app/Models/TenantSetting.php`: `Auditable` + `LogicalDelete`, **sin** `BelongsToTenant` (la fila ES de un tenant; el scope global sobre `tenant_id` estorbaría al leerla por `tenant_id`).
- `app/Models/OrderCodeCounter.php`: sin timestamps, con `tenant_id` y `last_number`. Es una tabla técnica: no es una entidad de negocio ni se edita en pantalla.
- `app/Models/Tenant.php`: nueva relación `settings(): HasOne`.
- `config/platform.php`: bloque `order_code` con los valores por defecto de la plataforma (`prefix` `PED`, `start` `1`, `padding` `6`, `max_length` `50`). Sirven para crear la fila de `tenant_settings` de una organización nueva; en el tenant 1 los valores viven en la BD.
- `orders.code` se añadió a `Order::$fillable` (sin eso el `Order::create()` del servicio descartaba el código en silencio y el `NOT NULL` reventaba la inserción).

### 27.3 `app/Services/OrderCodeService.php`

Algoritmo de `next()` (se invoca **dentro** de la transacción que inserta el pedido):

1. Resuelve `tenant_settings` del tenant (crea la fila con los defaults si no existe; usa `withDeleted()` para reutilizar una fila dada de baja antes que chocar con el único 1:1).
2. `ensureCounterExists()`: si falta el contador, lo inicializa con **`COUNT(orders.code)`**, nunca con `MAX(code)` (ADR-020 §13), y aplica `max(order_code_start - 1, count)`.
3. `OrderCodeCounter::where('tenant_id', …)->lockForUpdate()->firstOrFail()`: serializa a los pedidos concurrentes de esa organización.
4. Incrementa y arma `PREFIJO + '-' + número` con `str_pad` a `order_code_padding` dígitos.
5. Comprobación defensiva: si el código ya existe (alguien editó un código a mano con un número mayor), sigue incrementando hasta 100 intentos; si se agotan lanza `RuntimeException` con `order.code_exhausted`.
6. Guarda `last_number` y devuelve el código.

El `uq_orders_tenant_code` es la red de seguridad final ante una concurrencia extrema; con el `lockForUpdate` la ventana real es mínima.

### 27.4 Integración con `OrderService`

- `OrderCodeService` inyectado por constructor (resolución por contenedor; no hay instanciaciones manuales en el código de la aplicación).
- `create()`: asigna `'code' => $this->orderCodes->next()` **dentro** de la transacción existente, de modo que el bloqueo y el INSERT son atómicos.
- `update()`: `Arr::only($data, ['code', …])` para que la edición del código no pueda pisar otros campos.
- `buildSnapshot()`: el bloque `order` del snapshot de papelera (ADR-011) ahora incluye `code`, para que el historial de un ciclo de borrado guarde el código vigente en ese momento.

### 27.5 Validación y normalización (`UpdateOrderRequest`)

- `prepareForValidation()` normaliza `code` con `mb_strtoupper(trim(…))` **antes** de validar, para que ` ped-1 `, `ped-1` y `PED-1` no parezcan tres códigos distintos (la collation `utf8mb4_unicode_ci` ya los trataría como duplicados, pero el mensaje sería confuso).
- Reglas: `required`, `string`, `max:50`, `regex:/^[A-Z0-9][A-Z0-9.-]*$/` y `Rule::unique('orders', 'code')->where(tenant_id = …)->ignore($order)`.
- El regex es **permisivo a propósito**: acepta tanto `PED-000001` como los formatos heredados que admite ADR-020 §12 (`OC-45892`), sin obligar a una normalización que rompa la referencia al sistema anterior.
- `Rule::unique` consulta sobre el query builder (sin global scopes), por lo que **también ve los pedidos en papelera**: reutilizar el código de uno en papelera da 422, igual que en la base.
- Mensajes propios en `lang/es/order.php`: `code`, `code_hint`, `code_placeholder`, `code_required`, `code_taken` (con el `:input` que Laravel inyecta en `unique`), `code_invalid`, `code_too_long`, `code_exhausted`. El `validation.unique` genérico no dice qué código está repetido.
- El **formulario público no pide el código** (ADR-020 §16): `PublicOrderStoreRequest` no lo incluye y `Public\OrderController::store()` no lo manda.

### 27.6 Búsqueda

- `OrderController::index()`: el `q` del listado ahora compara `code` además de `notes` y de los datos del cliente/chofer/vehículo que ya buscaban.
