# ADR-014: Reglas de desarrollo

## Objetivo

Implementar cambios de forma segura, simple y eficiente, evitando ejecuciones,
consultas y análisis innecesarios.

## Flujo general

Para cada tarea:

1. Analizar primero el código relacionado con la solicitud.
2. Identificar los archivos que realmente necesitan modificarse.
3. Implementar únicamente lo solicitado.
4. Revisar los cambios realizados.
5. Ejecutar la validación mínima necesaria.
6. Finalizar la tarea cuando el cambio esté correctamente implementado.

No realizar mejoras, refactorizaciones o cambios adicionales que no hayan sido solicitados.

## Validaciones

No ejecutar builds, pruebas completas o comandos costosos después de cada cambio.

### Cambios pequeños

Para cambios de UI, estilos, textos, componentes o ajustes simples:

- Realizar una revisión del código modificado.
- Ejecutar únicamente validaciones rápidas si son necesarias.
- No ejecutar automáticamente un build completo.
- No ejecutar toda la suite de pruebas.

### Cambios de lógica

Para cambios en controladores, servicios, consultas, validaciones,
cálculos o endpoints:

- Realizar validación rápida.
- Ejecutar pruebas específicas relacionadas con el cambio cuando existan.
- No ejecutar pruebas no relacionadas.

### Cambios críticos

Para cambios relacionados con:

- Base de datos.
- SQL.
- Autenticación.
- Permisos.
- Eliminación/restauración.
- Transacciones.
- Lógica que afecta múltiples módulos.

Realizar pruebas más completas cuando sea necesario.

## Frontend y Backend

No ejecutar comandos de frontend para cambios exclusivamente de backend.

No ejecutar comandos de backend para cambios exclusivamente visuales.

Ejemplos:

- Cambio React/CSS → no ejecutar pruebas de Laravel innecesariamente.
- Cambio Controller/Service → no ejecutar build de React innecesariamente.
- Cambio SQL → validar primero la estructura y las consultas relacionadas.

## Base de datos

Antes de consultar la base de datos:

1. Revisar primero el código relacionado.
2. Revisar modelos, SQL o documentación disponible.
3. Consultar la base de datos solamente cuando sea necesario para confirmar
   información real o comportamiento que no pueda determinarse mediante el código.

Evitar consultas repetitivas a la base de datos.

No modificar datos reales para realizar pruebas sin que sea necesario.

## Lectura del código

Leer primero los archivos directamente relacionados con la tarea.

Evitar leer archivos completos que no sean necesarios.

No volver a leer archivos sin motivo cuando su contenido relevante ya fue analizado,
salvo que hayan sido modificados o sea necesario verificar una sección concreta.

## Errores

Si una validación falla:

1. Determinar si el error está relacionado con el cambio actual.
2. Corregirlo si corresponde.
3. Ejecutar nuevamente solamente la validación necesaria.

No iniciar una cadena de pruebas completas por un error que no está relacionado
con la tarea.

## Finalización

Una tarea se considera terminada cuando:

- El cambio solicitado está implementado.
- El código modificado fue revisado.
- Se ejecutó la validación apropiada para el nivel de cambio.
- No existen errores relacionados con la modificación.

No continuar con refactorizaciones, optimizaciones o mejoras no solicitadas.

## Módulo de precios

La lógica de cálculo de precios debe mantenerse centralizada.

Cuando se modifique un valor utilizado por el cálculo:

- Actualizar el cálculo con los datos ingresados.
- Validar el resultado relacionado.
- No ejecutar pruebas completas del sistema si el cambio está limitado
  al cálculo de precios.
- No modificar la estructura de `price_calculations` sin que sea necesario.
- Mantener el registro del cálculo utilizado para preservar el histórico.
