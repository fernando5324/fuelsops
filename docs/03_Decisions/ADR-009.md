# ADR-009: Frontend API Service Architecture

- **Status:** Accepted
- **Date:** 2026-09-22
- **Scope:** Frontend architecture
- **Applies to:** Sertoco prototype and future frontend projects


## Context

The frontend uses React to interact with backend functionality.

In previous projects, API calls were centralized in a `Services` directory,
with one service file per business module.

For example:

```
resources/js/Services/Articles.js
```
A Service contained the API endpoints and HTTP operations associated with
the corresponding business module.

Example:
```
import ajax from '@/Utils/Ajax';
import { uriBase } from '@/Utils/Common';

const baseUrl = `${uriBase}/api/articles`;

export const search = (params) => {
    return ajax.post(`${baseUrl}/search`, params);
};

export const searchSelect = (params) => {
    return ajax.post(`${baseUrl}/search/select`, params);
};

export const save = (data) => {
    return ajax.post(`${baseUrl}/save`, data, true);
};

export const remove = (id) => {
    return ajax.delete(`${baseUrl}/remove/${id}`, null, true);
};
```

This approach keeps API communication outside React components and makes
the frontend easier to maintain.

Without this separation, API calls can become distributed across pages,
components and UI elements:
```
Orders.jsx
Dashboard.jsx
OrderModal.jsx
OrderTable.jsx
CustomerSelect.jsx
OrderCreate.jsx
OrderEdit.jsx
```
This can lead to:

- Repeated API URLs.
- Repeated HTTP configuration.
- Inconsistent error handling.
- Difficulty locating backend endpoints.
- Strong coupling between UI components and the HTTP implementation.
- More difficult changes when the HTTP client or API structure changes.

The project needs a consistent architectural rule for frontend-to-backend
communication.

## Decision

All HTTP/API communication initiated by React must be encapsulated in the
resources/js/Services directory.

React components and pages must not directly communicate with the Laravel API
using axios, fetch, XMLHttpRequest or another HTTP client.

The architecture will follow:
```
React Page / Component
        ↓
Service
        ↓
Centralized HTTP Client
        ↓
Laravel API
```
The Services layer is responsible for the API contract used by the
frontend.

The React UI layer is responsible for presentation and user interaction.

## 1. Service Directory

Services will be stored under:
```
resources/js/Services/
```
A Service should generally represent a business module or resource.

For Sertoco, the initial structure may be:
```
resources/
└── js/
    ├── Components/
    ├── Pages/
    ├── Layouts/
    │
    ├── Services/
    │   ├── Orders.js
    │   ├── Customers.js
    │   ├── Drivers.js
    │   ├── Vehicles.js
    │   ├── Advisors.js
    │   ├── Plants.js
    │   ├── Wholesalers.js
    │   ├── Products.js
    │   └── Media.js
    │
    └── Utils/
        ├── Ajax.js
        └── Common.js
```
The exact list of Services will evolve according to the modules implemented
by the application.

## 2. One Service per Business Module

The preferred organization is one Service file per main business module.

Examples:
```
Services/Orders.js
Services/Customers.js
Services/Drivers.js
Services/Vehicles.js
Services/Products.js
Services/Media.js
```
This keeps related API operations together.

For example:
```
import ajax from '@/Utils/Ajax';
import { uriBase } from '@/Utils/Common';

const baseUrl = `${uriBase}/api/orders`;

export const search = (params) => {
    return ajax.post(`${baseUrl}/search`, params);
};

export const find = (id) => {
    return ajax.get(`${baseUrl}/${id}`);
};

export const save = (data) => {
    return ajax.post(`${baseUrl}/save`, data, true);
};

export const remove = (id) => {
    return ajax.delete(`${baseUrl}/remove/${id}`, null, true);
};
```
The exact HTTP methods and endpoint paths depend on the backend API.

## 3. Service Responsibility

A Service is responsible for API communication.

It may contain:

- API endpoint paths.
- HTTP methods.
- Request parameters.
- Request payloads.
- Calls to the centralized HTTP client.
- Returning the API response.

For example:
```
export const search = (params) => {
    return ajax.post(`${baseUrl}/search`, params);
};
```
The Service should not contain UI logic.

## 4. Component Responsibility

React components and pages are responsible for:

- Rendering UI.
- Form state.
- Local component state.
- Loading state.
- User interaction.
- Showing validation errors.
- Showing success messages.
- Opening and closing modals.
- Navigation.
- Calling the appropriate Service.

Example:
```
import * as OrdersService from '@/Services/Orders';

const response = await OrdersService.search({
    customer_id,
    advisor_id,
    page
});
```
The component should not need to know the actual API URL.

It should use:
```
OrdersService.search(...)
```
instead of:
```
axios.post('/api/orders/search', ...)
```
## 5. HTTP Client

All Services should use the centralized HTTP utility.

Initial location:
```
resources/js/Utils/Ajax.js
```
The architecture is:
```
Services/Orders.js
        ↓
Utils/Ajax.js
        ↓
HTTP client
        ↓
Laravel API
```
The centralized HTTP utility may handle common infrastructure concerns such
as:

- HTTP configuration.
- Headers.
- Authentication.
- CSRF.
- Timeouts.
- Common request configuration.
- Common response handling.
- Common error handling.

The exact implementation may evolve independently from the Services.

## 6. HTTP Client Abstraction

Individual Services should not create their own independent HTTP client
instances unless there is a documented reason.

Avoid patterns such as:
```
import axios from 'axios';

const client = axios.create(...);
```
inside every Service.

Instead:
```
import ajax from '@/Utils/Ajax';
```
The purpose is to keep the HTTP implementation centralized.

This allows the project to change or extend its HTTP infrastructure without
requiring changes throughout the frontend.

## 7. API URL Encapsulation

API URLs must remain inside their corresponding Service.

For example, this should not appear in a React component:
```
'/api/orders/search'
```
Instead:
```
Orders.search(params)
```
The Service owns the endpoint:
```
const baseUrl = `${uriBase}/api/orders`;

export const search = (params) => {
    return ajax.post(`${baseUrl}/search`, params);
};
```
This prevents API URLs from being duplicated throughout the application.

## 8. Request Parameters

When an operation requires several related parameters, prefer an object over
a long list of positional parameters.

Prefer:
```
Orders.search({
    article_id,
    author_id,
    category_id,
    page
});
```
and:
```
export const search = (params) => {
    return ajax.post(`${baseUrl}/search`, params);
};
```
instead of:
```
Orders.search(
    article_id,
    author_id,
    category_id,
    page
);
```
This becomes easier to maintain when additional filters are introduced.

Positional parameters may still be used for very simple operations where
they improve readability.

## 9. Naming

Service names should represent the business resource or module.

Preferred:
```
Orders.js
Customers.js
Products.js
Vehicles.js
Media.js
```
Avoid generic names when the file represents a specific module:
```
Api.js
Requests.js
CommonApi.js
Backend.js
Helpers.js
```
The filename should communicate what API functionality it contains.

## 10. Service Methods

Service method names should describe the business operation.

Examples:
```
search()
find()
save()
update()
remove()
create()
```
The project should use consistent naming.

For example, if save() represents both creation and update in the
application's existing API pattern, it may remain save().

Do not introduce unnecessary naming changes solely for stylistic reasons.

## 11. Service Boundaries

Services should group API operations by business responsibility.

For example:
```
Services/Orders.js
```
may contain:
```
search()
find()
save()
remove()
```
while:
```
Services/Customers.js
```
contains customer-related operations.

Do not place unrelated modules into a generic Service.

Avoid:
```
Services/Common.js
```
containing dozens of unrelated API endpoints.

## 12. UI Logic Must Remain Outside Services

Services must not contain React or UI logic.

Do not put the following inside a Service:
```
React state
setState()
useState()
useEffect()
toast notifications
modal state
navigation
DOM manipulation
component rendering
```
For example, avoid:
```
export const save = async (data) => {
    const response = await ajax.post(...);

    toast.success('Guardado correctamente');

    navigate('/orders');

    return response;
};
```
Instead:
```
export const save = (data) => {
    return ajax.post(`${baseUrl}/save`, data, true);
};
```

The component decides what to do with the result.

## 13. Example Component Flow

The preferred flow is:
```
User interaction
       ↓
React Component
       ↓
Orders.save(data)
       ↓
Services/Orders.js
       ↓
Ajax.post(...)
       ↓
Laravel API
       ↓
Response
       ↓
React Component
       ↓
UI update
```
For example:
```
const handleSubmit = async (data) => {
    setLoading(true);

    try {
        const response = await OrdersService.save(data);

        // UI success handling
    } catch (error) {
        // UI error handling
    } finally {
        setLoading(false);
    }
};
```
The component controls the UI state.

The Service controls the API communication.

## 14. Error Handling

The exact error handling strategy should be centralized as much as
possible in Ajax.js, while UI-specific error presentation remains inside
the component.

For example:
```
Ajax.js
    ↓
Normalizes HTTP/API error
    ↓
Service
    ↓
Returns/rejects
    ↓
Component
    ↓
Displays appropriate message
```
A Service should not decide how an error is visually presented.

For example, it should not directly render:
```
Toast
Modal
Alert
```
The component should decide how the user should be informed.

## 15. Loading States

Loading state belongs to the UI layer.

For example:
```
const [loading, setLoading] = useState(false);
```
The Service should not modify React loading state.

The Service simply performs the operation.

## 16. Authentication and Shared HTTP Concerns

Authentication-related HTTP configuration should preferably be handled by the
centralized HTTP layer.

For example:
```
Ajax.js
    ↓
Authentication headers / CSRF / common configuration
    ↓
Service
```
Individual Services should not repeatedly implement the same authentication
or HTTP configuration.

## 17. Inertia and API Calls

The project may use Laravel + React + Inertia.

Not every interaction between React and Laravel is necessarily an API call.

The architecture distinguishes between:
```
React
├── Inertia
│   └── Navigation and Inertia form/actions
│
└── Services
    └── API communication
```
If a page is using Inertia's normal navigation or form mechanisms, it may use
the Inertia router according to the project's established conventions.

For example:
```
router.post(...)
```
does not necessarily need to be converted into:
```
Orders.save(...)
```
The Service rule applies specifically to communication with backend API
endpoints.

Do not create unnecessary APIs solely to force every backend interaction
through Services.

## 18. Direct HTTP Calls Are Prohibited in UI Components

The following patterns should not be used for API communication inside
React components:
```
axios.get(...)
axios.post(...)
axios.put(...)
axios.patch(...)
axios.delete(...)
fetch(...)
XMLHttpRequest
```
Instead use the corresponding Service:
```
Orders.search(...)
Orders.find(...)
Orders.save(...)
Orders.remove(...)
```
This is an architectural rule, not merely a preferred coding style.

## 19. Creating New API Functionality

When a new API endpoint is required, follow this process:

- Identify the business module.
- Check whether the corresponding Service already exists.
- Add the API operation to the existing Service when appropriate.
- If no Service exists, create one for the module.
- Use the centralized HTTP client.
- Expose only the necessary method to the React layer.
- Keep endpoint details out of components.
- Keep UI behavior out of Services.

Example:

If a new endpoint is introduced:
```
POST /api/products/search/select
```
the implementation should be added to:
```
resources/js/Services/Products.js
```
rather than directly to:
```
Products.jsx
```

## 20. Avoid Premature Service Fragmentation

The default structure is one file per business module.

For example:
```
Services/
├── Orders.js
├── Customers.js
└── Products.js
```
Do not immediately create:
```
Services/
├── Orders/
│   ├── Search.js
│   ├── Create.js
│   ├── Update.js
│   └── Delete.js
```
unless the module becomes large enough to justify the additional structure.

The architecture should remain simple until complexity requires further
separation.

## 21. Future Scaling

If a Service becomes very large, it may later be converted into a directory.

For example:
```
Services/
└── Orders/
    ├── index.js
    ├── search.js
    ├── create.js
    └── update.js
```
This is an optional future evolution.

It should only be introduced when the size or complexity of the module
justifies it.

Do not introduce this structure prematurely.

## 22. Relationship With Backend Architecture

The frontend Service organization should generally follow business
resources/modules rather than database tables blindly.

For example:
```
Services/Orders.js
```
represents the order-related API from the frontend perspective.

It does not mean that every backend table must have a corresponding Service.

The frontend Service represents a business capability.

The backend remains responsible for:

- Business rules
- Validation
- Authorization
- Database operations
- Transactions
- Domain logic

The Service only represents the frontend communication boundary.

## 25. Advantages

This architecture provides:

- Clear separation between UI and API communication.
- Centralized HTTP configuration.
- Easier discovery of API endpoints.
- Less duplicated code.
- Less duplicated URLs.
- Easier maintenance.
- Easier replacement or modification of the HTTP client.
- More consistent API usage.
- Better organization as the application grows.
- Better separation of responsibilities.
- Easier testing of API communication independently from UI components.

## 26. Limitations

This architecture introduces an additional layer between the component and
the backend.

For very simple applications, this may initially appear more verbose than
calling an API directly.

However, the additional layer is intentional because the project is
expected to grow and contain multiple business modules.

The Service layer should therefore remain lightweight.

Do not turn Services into a second business-logic layer.

## 27. Definition of Done

The frontend API architecture is considered correctly implemented when:

- API calls are centralized under resources/js/Services.
- React components do not directly call Axios or Fetch for API endpoints.
- Each main business module has an appropriate Service.
- Services use the centralized HTTP utility.
- API URLs are not duplicated across components.
- Services do not contain React state or UI logic.
- Components remain responsible for UI behavior.
- HTTP infrastructure remains centralized.
- Inertia navigation remains separate from API Services when appropriate.
- New API functionality follows the same architecture.
- The structure remains simple and is only expanded when actual complexity
  requires it.

## 28. Architectural Rule

The fundamental rule established by this ADR is:

React components consume Services; Services consume the HTTP client;
the HTTP client communicates with the backend API.

In practical terms:

DO:
```
React
  ↓
Orders.search()
  ↓
Ajax.post()
  ↓
Laravel API
```

Do not:

```
React
  ↓
axios.post('/api/orders/search')
```

This rule should be followed for future frontend modules unless a new ADR
explicitly changes the architecture.

## 29. Responsabilidad de los Services

Los Services representan la comunicación con un módulo o recurso del sistema.

Ejemplo:
```
resources/js/Services/

Orders.js
Customers.js
Drivers.js
Vehicles.js
Products.js
Plants.js
Wholesalers.js
Advisors.js
```
Cada Service puede contener:

- Operaciones API.
- URLs de API.
- Métodos HTTP.
- Parámetros de consulta.
- Métodos para búsquedas.
- Métodos para obtener detalles.
- Definiciones de rutas del módulo cuando resulte conveniente.

Ejemplo:
```
import ajax from '@/Utils/Ajax';

const api = '/api/orders';

export const search = (params) => {
    return ajax.post(`${api}/search`, params);
};

export const find = (id) => {
    return ajax.get(`${api}/${id}`);
};

export const routes = {
    index: '/orders',
    create: '/orders/create',
    store: '/orders',
    edit: (id) => `/orders/${id}/edit`,
    update: (id) => `/orders/${id}`,
    destroy: (id) => `/orders/${id}`,
    changeStatus: (id) => `/orders/${id}/status`,
};
```
## 30. Services y operaciones Inertia

Los Services no reemplazan a Inertia.

Un mismo módulo puede tener operaciones API y rutas utilizadas por Inertia.

Ejemplo:
```
Orders.js

API
├── search()
├── find()
└── getDetails()

Routes
├── index
├── create
├── store
├── edit
├── update
├── destroy
└── changeStatus
```
Esto permite mantener toda la información relacionada con el módulo en un único lugar sin obligar a que todas las operaciones utilicen Axios.

Ejemplo:
```
import Orders from '@/Services/Orders';
import { router } from '@inertiajs/react';

const handleSubmit = (data) => {
    router.post(Orders.routes.store, data);
};
```
Mientras que una búsqueda dinámica puede utilizar:
```
const handleSearch = async (params) => {
    const response = await Orders.search(params);

    return response;
};
```
## 31. Preferencia por parámetros mediante objetos

Los métodos de Service que reciben múltiples parámetros deberán preferir objetos.

Evitar:
```
Orders.search(
    orderId,
    advisorId,
    customerId,
    driverId,
    page
);
```
Preferir:
```
Orders.search({
    order_id: orderId,
    advisor_id: advisorId,
    customer_id: customerId,
    driver_id: driverId,
    page,
});
```

Esto permite agregar nuevos filtros sin modificar constantemente la firma del método.

También facilita leer el código.

## 32. Regla para determinar qué utilizar

Se utilizarán las siguientes reglas:

| Necesidad                                    | Mecanismo      |
| -------------------------------------------- | -------------- |
| Navegar a una página                         | Inertia        |
| Crear registro mediante formulario principal | Inertia        |
| Editar registro                              | Inertia        |
| Eliminar registro                            | Inertia        |
| Cambiar estado                               | Inertia        |
| Validación de formulario Laravel             | Inertia        |
| Redirección después de guardar               | Inertia        |
| Mensajes `flash`                             | Inertia        |
| Búsqueda dinámica                            | Service + Ajax |
| Autocompletado                               | Service + Ajax |
| Select dinámico                              | Service + Ajax |
| Filtros sin navegación                       | Service + Ajax |
| Obtener detalle JSON                         | Service + Ajax |
| Consulta parcial                             | Service + Ajax |
| API consumida por React                      | Service + Ajax |

## 33. CRUD administrativo

Los CRUD administrativos utilizarán principalmente Inertia.

Ejemplo:
```
Products
├── GET /products
├── GET /products/create
├── POST /products
├── GET /products/{id}/edit
├── PUT /products/{id}
└── DELETE /products/{id}
```
El frontend puede utilizar:
```
router.post(...)
router.put(...)
router.delete(...)
```
Las búsquedas o consultas adicionales del CRUD pueden utilizar:
```
Products.js
```
mediante Service + Ajax.

Por ejemplo:
```
Products.search({
    name: search,
    is_active: true,
});
```

## 34. Búsquedas y autocompletados

Los componentes que necesiten información dinámica pueden utilizar Services.

Ejemplo:
```
const response = await Customers.search({
    search: value,
});
```
Esto resulta especialmente útil para:
```
Clientes.
Conductores.
Vehículos.
SCOP.
Productos.
Plantas.
Mayoristas.
Asesores.
```
El componente controla:
```
loading
data
error
selected value
```
El Service controla:
```
endpoint
HTTP method
request
```
## 35. Separación de responsabilidades

No se deberá colocar lógica de presentación dentro de Services.

Incorrecto:
```
export const search = async (params) => {
    const response = await ajax.post('/api/orders/search', params);

    toast.success('Resultados encontrados');

    return response;
};
```
El Service no debe conocer:
```
Toasts.
Modales.
Componentes.
Navegación.
Estado visual.
Mensajes específicos de UI.
```
Correcto:
```
export const search = (params) => {
    return ajax.post('/api/orders/search', params);
};
```
El componente decide qué hacer con el resultado.

## 36. Nota de implementación (22-09-2026)

Refactor aplicado en una sola tarea junto con el cambio de rutas/APIs a
inglés (ADR-064/ADR-003) y la reorganización de controladores por traits.

### Estructura implementada

- `resources/js/Utils/Ajax.js`: cliente axios central (`http`), con encabezado
  `X-Requested-With` por defecto; es la única vía de HTTP desde el front
  (se eliminó el uso directo de `window.axios` en componentes).
- `resources/js/Services/*.js`: **un Service por módulo** (`Orders.js`,
  `Media.js`, `Advisors.js`, `Wholesalers.js`, `Plants.js`, `Products.js`,
  `Customers.js`, `Drivers.js`, `Vehicles.js`, `OrderStatuses.js`, `Users.js`).
  Cada Service declara:
  - `routes`: objeto con las URLs a usar por las operaciones **Inertia**
    (`index`, `store`, `update(id)`, `destroy(id)`, etc.). Fuente única de
    URLs de API (p. ej. estados → `/api/order-statuses`, no `/api/estados`).
  - métodos axios para las operaciones que devuelven JSON real
    (`detail`, `lookup*`, `changeStatus`, CRUD directo).
- `resources/js/Services/index.js`: registro `catalogServices` que mapea
  `config.resource` → Service (la página genérica no conoce URLs).
- Los Services **no contienen lógica de presentación** (§35): devuelven la
  `response` de axios; el componente decide qué hacer.

### Híbrido Inertia/Ajax (§32) aplicado

- **CRUD de catálogos/usuarios** y **cambio de estado**: siguen con el router
  de Inertia (`router.post/put/delete`) pero con URLs tomadas de
  `Service.routes` (mantienen flash + redirección).
- **Detalle de pedido** (`/api/orders/{id}/detail`), **cambio de estado**
  cuando se consuma por Ajax, y **lookups públicos**
  (`/orders/lookup-customer|driver|vehicle`): viajan por axios desde el
  Service (`Orders.detail`, `Orders.lookupCustomer`, ...).
- Parámetros de métodos en objetos (§31).

### Página genérica de catálogos

- Se movió a `resources/js/Pages/Platform/Shared/Index.jsx` (el backend
  renderiza `Platform/Shared/Index`). Resuelve su Service por
  `catalogServices[config.resource]` y usa `config.url` (ADR-069) solo para
  navegación/paginación/filtros.
- El backend ya no envía `apiUrl`: fue retirado de la config (derivaba mal
  `/api/estados`).

### Controladores (misma tarea)

- `app/Http/Controllers/Platform/Concerns/HasIndexPage.php` (index Inertia +
  hooks `pageUrl()`, `showAudit()`, `options()`, `applyQueryScope()`) y
  `HasCrudActions.php` (store/update/destroy + `rules()`, `logicalDelete()`,
  `prepareForCreate/Update`, `beforeCreate/Update`, `authorizeEntity()`,
  `resolveRouteEntity()`).
- Los 18 controladores de módulo ahora son `extends Controller { use ...; }`;
  **no existe** carpeta física `Platform/Catalogs/` (es solo un nombre lógico).
- Métodos (no propiedades) como hooks para evitar conflictos de composición
  de traits (p. ej. `logicalDelete(): bool`, `pageUrl(): string`).
- Página genérica del front sin Card alrededor del listado: `PageHeader`
  (`resources/js/Components/PageHeader.jsx`) con el título a la misma altura
  del botón "Nuevo", y `PanelLayout` ya no recibe `title`.

### Páginas dedicadas por módulo

Los módulos que dejan de usar la página genérica crean su propio componente
en `resources/js/Pages/Platform/<Modulo>/Index.jsx` (frontend individual) y
en el backend sobreescriben el hook `pageComponent()` del trait
`HasIndexPage` para renderizar ese componente en vez de
`Platform/Shared/Index` (backend por módulo, sin carpeta física de
catálogos). Se retiran del registro `catalogServices` y su página importa su
Service directamente. El Service del módulo (`Service routes + axios`) se
conserva. Primer caso implementado el 22-09-2026: **Asesores**
(`Platform/Advisors/Index.jsx` + `AdvisorController::pageComponent()`).
