# ADR-005: Convención de campos de auditoría y usuario sistema

**Estado:** Aceptado
**Fecha:** 2026-09-18
**Ámbito:** Prototipo Sertoco

## Contexto

El sistema maneja tablas de negocio, tablas maestras y catálogos. Se
necesita una convención única de campos de auditoría para saber quién
creó o modificó cada registro, cuándo y en qué zona horaria.

Además, existe un flujo público (formulario de registro de pedidos) que
crea registros sin un usuario autenticado. Para poder mantener
`created_by` como campo obligatorio, se requiere un usuario de sistema.

También se requiere un mecanismo de borrado lógico para los módulos
principales y entidades maestras, de modo que los pedidos históricos
conserven sus referencias.

## Decisión

### Campos de auditoría en todas las tablas de negocio

Toda tabla de negocio incluirá:

```text
created_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME NULL DEFAULT NULL
    COMMENT 'Fecha y hora del registro en TimeZone 0'
created_by BIGINT UNSIGNED NOT NULL  (FK users)
updated_by BIGINT UNSIGNED NULL      (FK users)
```

- `created_at`: momento de creación.
- `updated_at`: momento de la última actualización, almacenado en
  TimeZone 0 (UTC).
- `created_by`: usuario que creó el registro; obligatorio.
- `updated_by`: último usuario que modificó el registro; opcional.

Todos los tipos se estandarizan: `BIGINT UNSIGNED` para las referencias
a usuarios y `TINYINT(1)` para los flags booleanos.

### Borrado lógico

Solo los módulos principales y entidades maestras llevan `is_deleted`
(`TINYINT(1) NOT NULL DEFAULT 0`):

- `orders`
- `order_details`
- `media_files`
- `customers`
- `drivers`
- `vehicles`

Los catálogos simples con pocos campos (`advisors`, `wholesalers`,
`plants`, `products`, `order_statuses`) no usan `is_deleted`: se
desactivan con `is_active` según ADR-001.

### Usuario sistema

Se crea un usuario semilla en `users` con los siguientes valores:

```text
name:        'sistema'
first_name:  'Sistema'
email:       'sistema@sertoco.local'
is_owner:    0
is_active:   1
```

Características:

- Se utiliza como `created_by` para los registros creados por el
  formulario público, los catálogos sembrados y las operaciones de
  sistema.
- Su contraseña es intencionalmente vacía; **nunca debe poder
  autenticarse**.

## Consecuencias

### Positivas

- Trazabilidad uniforme en todas las tablas de negocio.
- `updated_at` guardado en TimeZone 0 evita ambigüedades de huso
  horario.
- El borrado lógico permite conservar referencias históricas.
- El usuario `sistema` habilita la auditoría de los envíos públicos sin
  violar la restricción `NOT NULL`.

### Limitaciones

- Los `created_by`/`updated_by` no se implementan con triggers: la
  responsabilidad recae en la aplicación.
- El campo `updated_at` debe ser asignado por la aplicación (no usa
  `ON UPDATE CURRENT_TIMESTAMP`), por lo que la capa de persistencia
  (modelo/servicio) debe actualizarlo explícitamente.
- No hay una convención de `deleted_by`: el borrado lógico registra el
  actor mediante `updated_by` en la misma operación.
