# ADR-069: Estrategia de búsqueda y filtrado en listados administrativos

**Estado:** Aceptado
**Fecha:** 2026-09-04

## Contexto

Los módulos del Admin Panel contienen páginas principales donde se listan entidades que pueden ser creadas, editadas o eliminadas, como artículos, productos, servicios, páginas, etc.

Estos listados requieren mecanismos de búsqueda y filtrado para facilitar la localización de registros.

Inicialmente se consideró utilizar un Combobox o selector para buscar entidades por título. Sin embargo, para los listados administrativos esto agrega una interacción innecesaria cuando el objetivo principal del usuario es realizar una búsqueda textual.

Los selectores con búsqueda siguen siendo útiles en formularios de creación o edición cuando el usuario necesita seleccionar una entidad existente, por ejemplo, seleccionar un artículo relacionado, una categoría o un responsable.

## Decisión

Los listados administrativos utilizarán búsqueda textual mediante campos de entrada (input), complementada con filtros específicos de cada módulo.

Por ejemplo, el listado de artículos podrá utilizar:

┌───────────────────────────────────────────────┐
│ Buscar por título...                          │
├───────────────────────────────────────────────┤
│ Estado: [Todos ▼]    Categoría: [Todas ▼]   │
└───────────────────────────────────────────────┘

La búsqueda por título será realizada en el servidor y no dependerá exclusivamente de los registros previamente cargados en el navegador.

Ejemplo
GET /articles?search=laravel&status=published&category_id=3

Laravel construirá la consulta aplicando únicamente los filtros proporcionados.

Tenant
  ↓
Artículos del tenant
  ↓
Búsqueda por título
  ↓
Estado
  ↓
Categoría
  ↓
Paginación

### Búsqueda textual

El campo de búsqueda por título permitirá introducir texto libre.

Por ejemplo:

laravel

podrá encontrar:

Laravel básico
Introducción a Laravel
Laravel para APIs
Laravel + React

La búsqueda podrá comenzar después de un número mínimo de caracteres y utilizar debounce en el frontend para evitar realizar solicitudes innecesarias mientras el usuario escribe.

Inicialmente se utilizará un intervalo aproximado de 300–500 ms de debounce.

La implementación podrá evolucionar posteriormente hacia mecanismos de búsqueda más avanzados, como FULLTEXT de MySQL o un motor especializado, si el volumen de información lo justifica.

### Paginación

Los listados utilizarán paginación server-side.

El frontend no cargará todos los registros de una entidad únicamente para realizar filtros localmente.

Por ejemplo:

Base de datos
    ↓
Consulta filtrada
    ↓
20 registros
    ↓
React/Inertia

Esto permitirá que el sistema continúe funcionando correctamente cuando un tenant tenga una cantidad considerable de registros.

### Selectores y Combobox

Los Combobox o selectores con búsqueda no quedan descartados.

Se utilizarán cuando el objetivo sea seleccionar una entidad existente, especialmente en formularios de creación o edición.

Ejemplo:

Crear artículo
────────────────────────────

Título:
[________________________]

Categoría:
[ Buscar categoría... ▼ ]

Responsable:
[ Buscar responsable... ▼ ]

Artículo relacionado:
[ Buscar artículo... ▼ ]

En estos casos, si existen muchos registros, el Combobox podrá utilizar búsqueda remota mediante consultas al servidor y debounce.

Por tanto:

Listado
→ Input de búsqueda

Formulario
→ Select / Combobox cuando sea necesario seleccionar entidades

### Identificación de registros

Cuando el usuario seleccione una entidad existente mediante un selector, el frontend utilizará su ID como identificador, mientras que mostrará al usuario un atributo legible como título o nombre.

Ejemplo:

```json
{
    "id": 153,
    "title": "Laravel avanzado"
}
```

La interfaz mostrará:

Laravel avanzado

pero internamente utilizará:

153

Cuando se requiera localizar un registro concreto mediante su ID, se realizará una comparación exacta:

WHERE id = 153

La búsqueda textual por título será un mecanismo diferente:

WHERE title LIKE '%laravel%'

No se utilizará el nombre/título como identificador principal de las entidades.

Multi-tenancy

Todas las consultas de búsqueda y filtrado deberán respetar el aislamiento del tenant.

Conceptualmente:

tenant_id
    ↓
Registros disponibles para el tenant
    ↓
Filtros
    ↓
Resultados

Nunca se deberá permitir que un filtro o búsqueda consulte registros pertenecientes a otro tenant.

## Alternativas consideradas

### 1. Cargar todos los registros y filtrar en React

Descartado como estrategia principal.

Puede funcionar con pocos registros, pero no escala correctamente y aumenta el consumo de memoria y transferencia.

### 2. Combobox para buscar en los listados

Descartado para los listados generales.

Es más apropiado para seleccionar entidades concretas en formularios que para realizar búsquedas generales.

### 3. Consulta a la BD por cada carácter

Descartado.

Generaría solicitudes innecesarias y una carga adicional sobre el backend.

Se utilizará debounce para agrupar la escritura del usuario y realizar la búsqueda después de un breve período de inactividad.

### 4. Búsqueda server-side con input

Adoptado.

Permite mantener los listados escalables y proporciona una experiencia sencilla para el usuario.

## Consecuencias

### Positivas

Interfaz más sencilla para buscar registros.
Menor cantidad de datos transferidos al navegador.
Compatible con grandes cantidades de registros.
Permite combinar múltiples filtros.
Mantiene la lógica de búsqueda en el backend.
Los Combobox quedan disponibles para casos donde realmente representan una selección de entidades.
Evita utilizar nombres/títulos como identificadores.

### Negativas

Cada búsqueda requiere comunicación con el servidor.
Requiere implementar correctamente debounce y paginación.
Las consultas deben optimizarse mediante índices cuando el volumen de datos aumente.

## Regla arquitectónica

Los listados administrativos utilizarán búsqueda textual y filtros server-side; los selectores/Combobox se utilizarán principalmente para seleccionar entidades existentes en formularios.

La búsqueda textual sirve para encontrar registros.

El Combobox sirve para seleccionar registros.

Esta distinción será la convención utilizada en los módulos futuros del Admin Panel.
