# ADR-011: Eliminación lógica y papelera de pedidos

- **Estado:** Propuesto
- **Fecha:** 2026-09-25
- **Proyecto:** Sertoco
- **Área:** Pedidos / Administración / Auditoría
- **Relacionado con:** ADR-001 - Modelo inicial de pedidos y archivos

---

## 1. Contexto

Sertoco necesita permitir que un administrador pueda retirar un pedido de la operación normal sin eliminar físicamente su información de la base de datos.

Actualmente las tablas utilizan la siguiente convención para auditoría:

```
is_deleted TINYINT(1) NOT NULL DEFAULT 0,

created_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME NULL DEFAULT NULL COMMENT 'Fecha y hora del registro en America/Lima',
created_by BIGINT UNSIGNED NOT NULL,
updated_by BIGINT UNSIGNED NULL
```
La eliminación de pedidos debe conservar:

- información del pedido;
- detalles del pedido;
- cliente;
- planta;
- mayoristas;
- productos;
- precios;
- documentos adjuntos;
- información histórica;
- pagos realizados.

Además, se requiere una página de "Papelera" donde los administradores puedan:

- consultar pedidos eliminados;
- visualizar información básica;
- conocer quién lo eliminó;
- conocer cuándo fue eliminado;
- conocer el motivo;
- restaurar el pedido.

La eliminación de un pedido no debe interpretarse como cancelación comercial ni como anulación de pagos.

## 2. Decisión

Los pedidos utilizarán eliminación lógica mediante:
```
is_deleted TINYINT(1) NOT NULL DEFAULT 0
```
No se realizará DELETE FROM orders para la eliminación normal desde la interfaz.

Cuando un usuario elimine un pedido:
```
orders.is_deleted = 1
```
Además, se registrará la operación en una nueva tabla:
```
order_deletions
```
Esta tabla funcionará como registro de eliminación y permitirá administrar posteriormente la restauración.

## 3. Nueva tabla: order_deletions

Crear la tabla:
```
CREATE TABLE IF NOT EXISTS order_deletions (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    tenant_id BIGINT UNSIGNED NOT NULL,
    order_id BIGINT UNSIGNED NOT NULL,

    reason VARCHAR(500) NOT NULL,

    deleted_at DATETIME NOT NULL,
    deleted_by BIGINT UNSIGNED NOT NULL,

    snapshot JSON NULL,

    restored_at DATETIME NULL,
    restored_by BIGINT UNSIGNED NULL,

    created_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NULL DEFAULT NULL COMMENT 'Fecha y hora del registro en America/Lima',
    created_by BIGINT UNSIGNED NOT NULL,
    updated_by BIGINT UNSIGNED NULL,

    INDEX idx_order_deletions_tenant (tenant_id),
    INDEX idx_order_deletions_order (order_id),
    INDEX idx_order_deletions_deleted_by (deleted_by),
    INDEX idx_order_deletions_deleted_at (deleted_at),
    INDEX idx_order_deletions_restored_by (restored_by),

    CONSTRAINT fk_order_deletions_tenant
        FOREIGN KEY (tenant_id)
        REFERENCES tenants (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_order_deletions_order
        FOREIGN KEY (order_id)
        REFERENCES orders (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_order_deletions_deleted_by
        FOREIGN KEY (deleted_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_order_deletions_restored_by
        FOREIGN KEY (restored_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_order_deletions_created_by
        FOREIGN KEY (created_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_order_deletions_updated_by
        FOREIGN KEY (updated_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
) ENGINE=InnoDB;
```
OpenCode debe revisar las definiciones reales de orders, users y tenants antes de ejecutar el DDL y adaptar las FK si fuera necesario.

## 4. Propósito de order_deletions

Esta tabla no reemplaza a:
```
orders.is_deleted
```
Ambos cumplen funciones diferentes.
```
orders.is_deleted
```
Indica el estado actual del pedido.
```
0 = activo
1 = eliminado
order_deletions
```
Registra la operación de eliminación.

Permite saber:

- Quién lo eliminó
- Cuándo lo eliminó
- Por qué lo eliminó
- Qué información tenía en ese momento
- Si posteriormente fue restaurado
- Quién lo restauró
- Cuándo fue restaurado

## 5. Snapshot JSON

El campo:
```
snapshot JSON
```
debe conservar una fotografía de la información relevante del pedido en el momento de la eliminación.

Ejemplo conceptual:
```
{
    "order": {
        "id": 125,
        "order_number": "PED-000125",
        "order_date": "2026-09-25",
        "status": "registered"
    },
    "customer": {
        "id": 20,
        "name": "Empresa ABC",
        "ruc": "20123456789"
    },
    "plant": {
        "id": 3,
        "name": "Callao"
    },
    "details": [
        {
            "product_id": 10,
            "product_name": "Diesel DB S50",
            "wholesaler_id": 4,
            "wholesaler_name": "Hidromundo",
            "gallons": 5000,
            "sale_price": 22.7623
        }
    ]
}
```
El snapshot es exclusivamente histórico.

No debe utilizarse para restaurar automáticamente las relaciones del pedido.

La restauración debe utilizar los registros originales de:
```
orders
order_details
media_files
```
si estos continúan disponibles.

## 6. Regla principal de eliminación

La eliminación de un pedido debe ejecutarse mediante una transacción.

Flujo:
```
Usuario selecciona "Eliminar"
        ↓
Mostrar confirmación
        ↓
Solicitar motivo
        ↓
Validar pedido
        ↓
Crear snapshot
        ↓
Crear order_deletions
        ↓
orders.is_deleted = 1
        ↓
Marcar archivos relacionados
        ↓
Mantener pagos
        ↓
COMMIT
```
Si ocurre un error:
```
ROLLBACK
```
No debe quedar un pedido parcialmente eliminado.

## 7. Motivo de eliminación

El motivo será obligatorio.

Ejemplos:
```
Pedido registrado por error
Pedido duplicado
Solicitud del cliente
Información incorrecta
Pedido reemplazado
Otro
```
La interfaz puede utilizar una lista de motivos y permitir una descripción adicional.

Como mínimo debe guardarse:
```
reason
```

No permitir eliminar un pedido sin motivo.

## 8. Mensaje de confirmación

Al seleccionar eliminar, mostrar un modal de confirmación.

Texto sugerido:
```
¿Eliminar pedido?

El pedido #PED-000125 será enviado a la papelera.

El pedido dejará de aparecer en el listado principal, pero su
información se conservará y podrá restaurarse posteriormente.

Esta acción no elimina los pagos ni los documentos registrados.

Motivo de eliminación:
[________________________________]

[Cancelar] [Enviar a papelera]
```
El botón definitivo debe utilizar un texto claro:

Enviar a papelera

en lugar de:

Eliminar definitivamente

porque la operación no es una eliminación física.

## 9. Advertencia cuando existen pagos

Antes de confirmar, verificar si el pedido tiene pagos asociados.

Si tiene pagos:

Este pedido tiene pagos registrados.

Enviar el pedido a la papelera no eliminará ni revertirá
los pagos asociados.

Si el pedido requiere una cancelación o devolución,
debe realizarse mediante el proceso correspondiente.

Esta advertencia debe mostrarse antes de la confirmación final.

La eliminación lógica del pedido NO debe:
```
eliminar pagos;
modificar pagos;
marcar pagos como anulados;
generar devoluciones;
revertir transacciones.
```

## 10. Archivos adjuntos

Los archivos asociados al pedido utilizan media_files.

Al enviar un pedido a la papelera:
```
media_files.is_deleted = 1
```
para los archivos relacionados directamente con el pedido.

No eliminar físicamente los archivos del almacenamiento en esta operación.

Los metadatos del archivo deben permanecer disponibles.

Esto permite conservar:
```
nombre
extensión
mime type
ubicación
tamaño
relación
etc.
```
La eliminación física del archivo puede ser una función independiente en el futuro.

## 11. Detalles del pedido

Los registros de:
```
order_details
```
NO deben eliminarse.

Al marcar:
```
orders.is_deleted = 1
```

los detalles permanecen asociados al pedido.

No agregar is_deleted a order_details únicamente para esta funcionalidad, salvo que exista posteriormente un requerimiento independiente que lo justifique.


## 12. Pagos

Los pagos asociados al pedido deben permanecer intactos.

No ejecutar:
```
DELETE payments
```
ni modificar su estado debido a la eliminación lógica del pedido.

La relación conceptual será:
```
orders
   │
   └── payments
```
El pedido puede estar eliminado mientras sus pagos continúan existiendo.

Esto permite mantener la trazabilidad financiera.

Las FK de pagos no deben utilizar eliminación en cascada para esta funcionalidad.

## 13. Filtro de pedidos normales

El listado principal de pedidos debe excluir automáticamente los pedidos eliminados.

Todas las consultas normales de pedidos deben considerar:
```
WHERE is_deleted = 0
```
Esto aplica a:

listado;
- búsqueda;
- filtros;
- estadísticas;
- contadores;
- exportaciones;
- consultas administrativas normales.

No se debe permitir que un pedido eliminado aparezca accidentalmente en el listado normal.

## 14. Página de Papelera

Crear una nueva página administrativa:
```
/Pedidos/Papelera
```
o adaptar la ruta a la convención actual del proyecto.

La página debe mostrar únicamente:
```
orders.is_deleted = 1
```
y debe consultar también:
```
order_deletions
```
para mostrar información de la eliminación.

## 15. Información de la papelera

El listado puede mostrar:

| Campo                | Descripción                        |
| -------------------- | ---------------------------------- |
| Pedido               | Número/código del pedido           |
| Cliente              | Cliente asociado                   |
| Fecha del pedido     | Fecha original                     |
| Estado               | Estado que tenía antes de eliminar |
| Eliminado por        | Usuario que realizó la eliminación |
| Fecha de eliminación | Fecha y hora                       |
| Motivo               | Motivo registrado                  |
| Pagos                | Indicador si existen pagos         |
| Acciones             | Ver / Restaurar                    |


No es necesario mostrar toda la información del pedido en la tabla.

La papelera debe ser simple y orientada a recuperación.

## 16. Indicador de pagos

Si el pedido tiene pagos, mostrar una indicación visual.

Ejemplo:
```
✓ Sin pagos
```
o:
```
⚠ Tiene pagos
```
Al pasar o seleccionar el indicador puede mostrarse:

Este pedido tiene 2 pagos registrados.
Los pagos se conservan aunque el pedido esté en la papelera.

## 17. Ver pedido eliminado

La papelera debe permitir abrir el pedido.

La vista de detalle debe ser de solo lectura mientras el pedido permanezca eliminado.

Mostrar una alerta superior:
```
Pedido en papelera

Este pedido fue enviado a la papelera el 25/09/2026
por Luis Fernando.

Motivo:
Pedido registrado por error.

El pedido puede restaurarse para volver a la operación normal.
```
No permitir modificar normalmente un pedido eliminado.

La acción principal será:

- Restaurar pedido

## 18. Restauración

La restauración debe cambiar:
```
orders.is_deleted = 0
```
y registrar la restauración en:
```
order_deletions.restored_at
order_deletions.restored_by
```
No eliminar el registro de order_deletions.

Esto es importante para mantener el historial.

Ejemplo:
```
Eliminado:
25/09/2026 16:30
por Usuario A

Restaurado:
25/09/2026 17:15
por Usuario B
```

## 19. Confirmación de restauración

Al seleccionar restaurar:
```
¿Restaurar pedido?

El pedido #PED-000125 volverá a aparecer en el listado
principal de pedidos.

Su información, detalles, archivos y pagos se conservarán.

¿Deseas continuar?

[Cancelar] [Restaurar pedido]
```

## 20. Restauración y archivos

Si los archivos asociados al pedido fueron marcados:
```
media_files.is_deleted = 1
```
al restaurar el pedido deben volver a estar disponibles:
```
media_files.is_deleted = 0
```
únicamente para los archivos que fueron afectados por la eliminación del pedido.

No modificar archivos que ya estuvieran eliminados previamente por otra razón.

Para esto, la implementación debe identificar los archivos afectados durante la operación de eliminación.

## 21. Restauración y pagos

La restauración del pedido tampoco debe modificar los pagos.

Los pagos continúan exactamente como estaban.

Ejemplo:
```
Antes:

Pedido eliminado
Pago ejecutado = S/ 1,500

Después de restaurar:


Pedido activo
Pago ejecutado = S/ 1,500
```
No crear ni eliminar movimientos financieros como consecuencia de la restauración.

## 22. Validaciones antes de restaurar

Antes de restaurar verificar:

1. El pedido existe.
2. Pertenece al tenant actual.
3. is_deleted = 1.
4. Existe un registro de eliminación activo.
5. Las relaciones principales siguen disponibles.
6. El pedido no está siendo modificado simultáneamente.

Si alguna validación falla, no restaurar parcialmente.

## 23. ¿Puede eliminarse nuevamente un pedido restaurado?

Sí.

Si un pedido restaurado vuelve a eliminarse:
```
Pedido
  ↓
Eliminado
  ↓
Restaurado
  ↓
Eliminado nuevamente
```
Debe registrarse una nueva operación de eliminación.

No reutilizar el registro histórico anterior.

Ejemplo:
```
order_deletions

ID 1
Pedido 125
Eliminado 25/09
Restaurado 25/09

ID 2
Pedido 125
Eliminado 26/09
Restaurado NULL
```
Esto proporciona un historial completo.

## 24. Estado de una eliminación

No agregar necesariamente un campo status si se puede determinar mediante:
```
restored_at IS NULL
```
La interpretación será:
```
restored_at IS NULL
    → actualmente en papelera

restored_at IS NOT NULL
    → ya fue restaurado
```
Esto evita almacenar información redundante.

## 25. Una eliminación activa por pedido

En la lógica de aplicación debe garantizarse que solamente exista una eliminación activa para un pedido.

Un pedido:
```
is_deleted = 1
```
debe tener una eliminación correspondiente cuyo:
```
restored_at IS NULL
```
Al restaurarlo, ese registro queda cerrado.

Si posteriormente se elimina nuevamente, se crea otro registro.

## 26. Seguridad y tenant

La papelera debe respetar completamente el aislamiento por tenant.

Nunca se debe permitir:
```
tenant A
    ↓
ver/restaurar
    ↓
pedido de tenant B
```
Todas las consultas y operaciones deben validar:
```
tenant_id
```
Además, solamente usuarios con permisos administrativos adecuados podrán:
```
enviar pedidos a la papelera;
consultar la papelera;
restaurar pedidos.
```
La implementación debe utilizar el sistema de autorización existente en Sertoco.

No crear un sistema paralelo de permisos.

## 27. Mensajes de éxito

Al enviar un pedido a la papelera:

Pedido enviado a la papelera correctamente.

Al restaurar:

Pedido restaurado correctamente.

## 28. Mensajes de error

Si ocurre un problema:

No fue posible enviar el pedido a la papelera.
El pedido no fue modificado.

Para restauración:

No fue posible restaurar el pedido.
El pedido permanece en la papelera.

Si el pedido ya fue eliminado:

El pedido ya se encuentra en la papelera.

Si ya fue restaurado:

El pedido ya se encuentra activo.

Si no existe:

El pedido solicitado no existe o no está disponible.

No exponer errores SQL ni información técnica al usuario final.

## 29. Transacciones

La eliminación debe utilizar una transacción.

Operación:
```
BEGIN

1. Obtener pedido
2. Validar tenant
3. Validar que no esté eliminado
4. Obtener información para snapshot
5. Crear order_deletions
6. Marcar orders.is_deleted = 1
7. Marcar media_files afectados como is_deleted = 1

COMMIT
```
La restauración:
```
BEGIN

1. Obtener pedido
2. Validar tenant
3. Validar que esté eliminado
4. Obtener eliminación activa
5. orders.is_deleted = 0
6. Restaurar media_files afectados
7. Actualizar restored_at
8. Actualizar restored_by

COMMIT
```
Si cualquier operación falla:
```
ROLLBACK
```

## 30. No realizar eliminación física desde la interfaz

La papelera NO debe tener inicialmente:

Eliminar definitivamente

La única acción disponible será:

Restaurar

La eliminación física puede evaluarse posteriormente mediante una política de retención y permisos especiales.

No implementar eliminación definitiva como parte de este ADR.

## 31. Ordenamiento de la papelera

Por defecto, mostrar primero los pedidos eliminados más recientemente:
```
ORDER BY deleted_at DESC
```
Esto permite encontrar rápidamente las últimas eliminaciones.

## 32. Filtros de la papelera

La primera versión puede incluir:
```
búsqueda por número de pedido;
búsqueda por cliente;
rango de fecha de eliminación;
usuario que eliminó;
indicador de pagos.
```
No es necesario implementar filtros avanzados si la cantidad de pedidos todavía es reducida.

## 33. Consideración sobre created_by y updated_by

La tabla orders mantiene sus campos existentes:
```
created_by
updated_by
```
La eliminación no debe sobrescribir:
```
created_by
```
ni utilizarlo como información de eliminación.

La información de eliminación se registra mediante:
```
order_deletions.deleted_by
order_deletions.deleted_at
```
De igual manera, la restauración se registra mediante:
```
order_deletions.restored_by
order_deletions.restored_at
```

## 34. Resultado esperado

Al finalizar esta implementación, el flujo será:

```
                 PEDIDOS
                    │
          ┌─────────┴─────────┐
          │                   │
      Activos             Eliminados
          │                   │
          ▼                   ▼
     Listado normal       Papelera
                              │
                     ┌────────┴────────┐
                     │                 │
                   Ver              Restaurar
                                       │
                                       ▼
                                  Pedido activo
```
La información nunca se destruye durante la eliminación normal.

Los pagos permanecen.

Los detalles permanecen.

Los archivos permanecen físicamente y sus registros se conservan.

La eliminación queda registrada.

La restauración queda registrada.

## 35. Criterios de aceptación

La implementación se considera correcta cuando:

- [ ] Un pedido puede enviarse a la papelera.
- [ ] La operación no ejecuta un DELETE físico sobre orders.
- [ ] orders.is_deleted cambia de 0 a 1.
- [ ] Se crea un registro en order_deletions.
- [ ] El registro guarda usuario, fecha y motivo.
- [ ] Se genera snapshot JSON del pedido.
- [ ] Los detalles del pedido permanecen intactos.
- [ ] Los pagos permanecen intactos.
- [ ] Los archivos físicos no se eliminan.
- [ ] Los media_files asociados quedan marcados como eliminados.
- [ ] El pedido deja de aparecer en el listado normal.
- [ ] El pedido aparece en Papelera.
- [ ] Se puede consultar el detalle del pedido desde Papelera.
- [ ] Se muestra que el pedido está eliminado.
- [ ] Se puede restaurar.
- [ ] Restaurar cambia orders.is_deleted a 0.
- [ ] Los archivos afectados vuelven a estar disponibles.
- [ ] Los pagos no se modifican durante la restauración.
- [ ] La restauración registra restored_at y restored_by.
- [ ] El registro histórico de order_deletions permanece.
- [ ] Si se elimina nuevamente, se crea un nuevo registro de eliminación.
- [ ] Todas las operaciones respetan tenant_id.
- [ ] Solo usuarios autorizados pueden eliminar/restaurar.
- [ ] Las operaciones utilizan transacciones.
- [ ] Los mensajes de éxito y error utilizan flash messages de Inertia/Laravel según la arquitectura actual.
- [ ] No se implementa eliminación física desde la interfaz.

### Una decisión que mantendría tal cual

La parte más importante es que **`order_deletions` no sea simplemente una tabla para saber que algo fue eliminado**, sino el historial de cada ciclo:

```
Pedido #125

25/09 16:30 ── Eliminado por Luis
                 Motivo: Pedido duplicado
                 Snapshot: {...}

25/09 17:10 ── Restaurado por Luis

26/09 09:20 ── Eliminado por otro usuario
                 Motivo: Información incorrecta
                 Snapshot: {...}
```
Eso te da una trazabilidad bastante buena sin complicar todavía el sistema con una auditoría general para todas las tablas.

Y para la papelera, inicialmente mantendría únicamente Restaurar; no pondría "Eliminar definitivamente". Si en el futuro Sertoco necesita una política de retención, podemos crear otro ADR específico para eliminación permanente y conservación legal/operativa de documentos y pagos.

## Nota de implementación

Implementado el 25-09-2026 con los alcances aprobados por el usuario:

- **Permisos (§13-§14)**: enviar a papelera y restaurar requieren `users.is_owner = 1`
  (gate en el ApiController → 403); consultar la papelera y su detalle está abierto a
  cualquier usuario autenticado.
- **Acción de eliminación (§8-§11)**: solo desde el detalle `Show` (botón "Enviar a
  papelera" + modal de motivo, visible únicamente al owner). No se incluye
  "Eliminar definitivamente" (mantiene la decisión de papelera con solo Restaurar).
- **Columna adicional aprobada**: `order_deletions.affected_media_ids JSON NULL`
  (ADR §20) para restaurar solo los archivos afectados por esa eliminación.
- **Esquema (sección 19 de `database.sql`)**: tabla `order_deletions` con
  `tenant_id`, `order_id`, `reason`, `snapshot`, `deleted_at`, `deleted_by`,
  `affected_media_ids`, `restored_at`, `restored_by` + auditoría. `snapshot` es JSON
  inmutable: `order`, `customer`, `plant`, `details` y `payments: []` (no existe
  módulo de pagos, §9/§12/§16/§21 N/A).
- **Motor** (`OrderService::sendToTrash/restoreFromTrash/buildSnapshot`):
  transacciones; el envío marca `orders.is_deleted=1`, crea el registro de
  eliminación y marca los `media_files` afectados con `is_deleted=1` SIN borrado
  físico (§20); la restauración revierte `is_deleted=0` en pedido y en los media
  que sigan `is_deleted=1`, y cierra el registro con `restored_at/restored_by`
  manteniéndolo como historial (§18/§23). La implementación usa `forceFill` +
  `save()` (no `LogicalDelete::delete()/restore()`) porque `is_deleted` no está en
  `$fillable` y el `restore()` del trait no resetea el flag.
- **Trait**: `LogicalDelete` ganó los scopes `withDeleted()`/`onlyDeleted()`.
- **Backend**: `OrderDeletion` (modelo, Auditable + BelongsToTenant sin
  LogicalDelete), `TrashController::index/show` (resolución manual con
  `Order::onlyDeleted()`, tenant ajeno → 404), `TrashOrderRequest` (motivo
  requerido, máx 500), `OrderApiController::trash()/restore()`. Rutas web
  `pedidos.papelera.*` ANTES de `/pedidos/{order}`; APIs `api.orders.trash`
  (binding sobre pedido activo) y `api.orders.restore` (sin binding, para alcanzar
  pedidos eliminados).
- **Frontend**: página `Platform/Orders/Trash.jsx` (listado con motivo/fecha/
  eliminado por + Restaurar solo owner), submenú Pedidos {Pedidos, Papelera},
  `Show.jsx` con acción de papelera y variante read-only (banner Alert, oculta
  Editar/StatusChanger, botón Restaurar). i18n en `lang/es/order.php` y
