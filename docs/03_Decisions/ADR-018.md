# ADR-018: Exportación PDF del reporte "Avance de ventas" utilizando Browsershot

## 1. Objetivo

Implementar la exportación a PDF del reporte "Avance de ventas".

El PDF debe contener la información del reporte actualmente mostrada en la página web:

* Período seleccionado.
* Total de galones.
* Compras totales.
* Ventas totales.
* Margen total.
* Gráfico de evolución de compras, ventas y margen.
* Gráfico Pie de galones por producto.
* Tabla "Resumen por día".

El PDF debe tener una presentación profesional y adecuada para ser compartida con gerentes, evaluadores o responsables de la operación.

La generación del PDF debe realizarse mediante Browsershot utilizando Chromium/Puppeteer.

---

# 2. Arquitectura

Mantener la arquitectura existente:

* Backend: Laravel.
* Frontend: React.
* Inertia.
* Ant Design.
* Apache ECharts.
* MySQL.
* Browsershot para generación del PDF.

La página web continuará funcionando normalmente mediante:

Laravel -> Inertia -> React -> ECharts.

La generación del PDF será independiente de la interfaz administrativa React.

Arquitectura conceptual:

```text
Página web

Laravel
   ↓
Inertia
   ↓
React
   ↓
Ant Design + ECharts


Exportación PDF

Laravel
   ↓
Consulta / servicio de estadísticas
   ↓
Vista Blade exclusiva para PDF
   ↓
ECharts
   ↓
Browsershot / Chromium
   ↓
PDF
```

No convertir directamente toda la aplicación React a PDF.

Crear una vista Blade específica para impresión/reporte.

---

# 3. Librería

Utilizar:

Browsershot

Browsershot debe utilizar Chromium/Puppeteer para renderizar el HTML del reporte y convertirlo a PDF.

Antes de implementar:

1. Revisar si Browsershot ya está instalado.
2. Si no está instalado, instalar la versión compatible con la versión actual de Laravel/PHP.
3. Revisar los requisitos de Node.js, npm y Chromium/Puppeteer.
4. Seguir la documentación y convenciones actuales del proyecto.
5. No instalar dependencias adicionales innecesarias.

---

# 4. Principio importante: una sola fuente de datos

La lógica de negocio utilizada para calcular el reporte no debe duplicarse.

La página web y el PDF deben utilizar la misma lógica de backend para obtener:

* Total de galones.
* Compras.
* Ventas.
* Margen.
* Margen por galón.
* Datos diarios.
* Datos agrupados por producto.

No crear cálculos diferentes para React y PDF.

Idealmente reutilizar el mismo Service o clase existente que alimenta la página "Avance de ventas".

Conceptualmente:

```text
                Servicio de estadísticas
                         │
              ┌──────────┴──────────┐
              ↓                     ↓
           React                  Blade
              ↓                     ↓
           ECharts              ECharts
                                    ↓
                               Browsershot
                                    ↓
                                   PDF
```

Esto garantiza que los valores mostrados en pantalla y los valores exportados coincidan.

---

# 5. Botón de exportación

Agregar una acción visible en la página "Avance de ventas":

"Exportar PDF"

Utilizar un icono apropiado, por ejemplo un icono de archivo PDF o descarga.

La acción debe utilizar los filtros actualmente seleccionados.

Ejemplo:

```text
[Mes / período] [Desde] [Hasta] [Filtrar] [Exportar PDF]
```

Si el usuario seleccionó:

```text
Desde: 01/09/2026
Hasta: 30/09/2026
```

El PDF debe contener exactamente ese período.

No utilizar automáticamente otro período diferente.

---

# 6. Flujo de exportación

El flujo esperado es:

1. El usuario selecciona el período.
2. El usuario consulta la información.
3. La página muestra los resultados.
4. El usuario presiona "Exportar PDF".
5. React envía al backend los filtros actuales.
6. Laravel valida los filtros.
7. Laravel obtiene nuevamente los datos utilizando el servicio de estadísticas.
8. Laravel genera la vista Blade del reporte.
9. Browsershot renderiza la vista.
10. Chromium genera el PDF.
11. Laravel devuelve el archivo para descarga.

No enviar toda la información de la tabla desde React al backend para construir el PDF.

El backend debe volver a consultar los datos utilizando los filtros recibidos.

Esto evita manipulación de datos y garantiza que el PDF sea generado con información consistente.

---

# 7. Parámetros del endpoint

Crear una ruta específica para exportar el reporte.

Ejemplo conceptual:

```text
GET /sales-progress/export/pdf
```

O seguir la convención de rutas existente del proyecto.

Los parámetros deben incluir como mínimo:

```text
from
to
```

Ejemplo:

```text
?from=2026-09-01&to=2026-09-30
```

Validar las fechas en Laravel.

No aceptar datos financieros calculados enviados desde React como fuente de verdad.

---

# 8. Vista Blade del PDF

Crear una vista Blade independiente para el reporte.

Ejemplo conceptual:

```text
resources/views/reports/sales-progress.blade.php
```

Utilizar HTML y CSS específicos para impresión.

La vista debe ser independiente de Ant Design.

No intentar reutilizar componentes React dentro de Blade.

La vista debe recibir los datos calculados por Laravel.

---

---

# 10. Formato del PDF

Utilizar tamaño:

A4

Orientación:

Preferentemente vertical.

Si la tabla requiere demasiado ancho, evaluar orientación horizontal.

No cambiar automáticamente a horizontal sin comprobar primero si el contenido puede presentarse correctamente en vertical.

Configurar:

* Márgenes razonables.
* Encabezado.
* Pie de página.
* Numeración de páginas cuando sea posible.
* Buena separación entre secciones.
* Saltos de página controlados.

Evitar que una fila de la tabla quede partida entre dos páginas cuando sea posible.

---

# 11. Encabezado del reporte

El PDF debe tener un encabezado profesional.

Debe mostrar como mínimo:

```text
SERTОCO

AVANCE DE VENTAS

Período:
01/09/2026 - 30/09/2026
```

Si el proyecto ya dispone de un logo reutilizable, utilizarlo.

No crear un logo nuevo.

Utilizar la identidad visual existente del sistema.

---

# 12. Cards / indicadores

En el PDF mostrar los mismos indicadores que aparecen en la página:

* Total galones.
* Compras totales.
* Ventas totales.
* Margen total.

Ejemplo:

```text
TOTAL GALONES
125,450 gal

COMPRAS
S/ 580,200.00

VENTAS
S/ 625,800.00

MARGEN
S/ 45,600.00
```

Los indicadores deben utilizar una presentación visual clara.

No es necesario replicar exactamente el componente Ant Design utilizado en la aplicación.

El PDF debe utilizar HTML/CSS optimizado para impresión.

---

# 13. Gráfico de evolución

El PDF debe incluir el gráfico de evolución de:

* Compras.
* Ventas.
* Margen.

Debe utilizar Apache ECharts.

El gráfico debe conservar la información visual de la página web:

* Fechas en el eje X.
* Compras.
* Ventas.
* Margen.
* Leyenda.
* Valores comprensibles.

No mostrar días sin pedidos.

---

# 14. Renderizado de ECharts en PDF

Debido a que Browsershot utiliza Chromium, los gráficos ECharts deben estar completamente renderizados antes de generar el PDF.

La implementación debe garantizar que:

1. La página HTML se cargue.
2. ECharts se inicialice.
3. El gráfico se renderice.
4. Browsershot espere a que el contenido esté disponible.
5. El PDF se genere solamente después de que los gráficos estén listos.

No generar el PDF antes de que ECharts termine de renderizar.

Si es necesario, utilizar una estrategia de espera apropiada en Browsershot/Puppeteer.

No utilizar tiempos de espera excesivamente largos como solución general.

Preferir una condición de renderizado explícita cuando sea posible.

---

# 15. Gráfico Pie

El PDF debe incluir:

"Galones por producto"

El gráfico debe representar:

```text
Producto -> Total galones
```

Debe mostrar la distribución porcentual.

En el PDF no es necesario implementar la interacción de seleccionar/deseleccionar productos.

La interacción de selección/deselección pertenece exclusivamente a la página web.

El PDF debe mostrar todos los productos del período seleccionado.

Debe incluir una leyenda clara.

---

# 16. Tabla "Resumen por día"

El PDF debe incluir la tabla:

"Resumen por día"

Columnas:

```text
Fecha
Total Galones
Compras S/
Ventas S/
Margen S/
Margen S/ por galón
```

No mostrar días sin pedidos.

Utilizar formato numérico consistente:

```text
12,500
S/ 58,000.00
S/ 62,000.00
S/ 4,000.00
S/ 0.32
```

El encabezado de la tabla debe repetirse en cada página cuando la tabla continúe en una segunda página.

Evitar que una fila quede dividida entre dos páginas cuando sea posible.

---

# 17. Totales de la tabla

Al final de la tabla mostrar los totales del período.

Ejemplo:

```text
TOTAL
37,500
S/ 173,300.00
S/ 185,300.00
S/ 12,000.00
S/ 0.32
```

El margen por galón total debe calcularse como:

```text
Margen total / Total galones
```

No utilizar promedio simple de los márgenes diarios.

---

# 18. Fórmulas

Mantener las mismas fórmulas de la página web.

Margen:

```text
Margen S/ = Ventas S/ - Compras S/
```

Margen por galón:

```text
Margen S/ por galón = Margen S/ / Total Galones
```

Mostrar máximo 2 decimales para margen por galón.

Si Total Galones es cero:

```text
Margen S/ por galón = 0
```

Evitar división por cero.

---

# 19. Consistencia entre web y PDF

Los siguientes valores deben coincidir entre la página web y el PDF cuando se utilice el mismo período:

* Total galones.
* Compras.
* Ventas.
* Margen.
* Datos diarios.
* Galones por producto.

El PDF no debe mostrar información diferente de la página para el mismo filtro.

---

# 20. Nombre del archivo

Generar un nombre descriptivo.

Ejemplo:

```text
avance-ventas-2026-09-01-2026-09-30.pdf
```

Si existe una convención de nombres de archivos en el proyecto, seguirla.

No utilizar nombres genéricos como:

```text
document.pdf
report.pdf
file.pdf
```

---

# 21. Manejo de errores

Si ocurre un error durante la generación:

* No devolver un PDF incompleto.
* Registrar el error en los logs de Laravel.
* Mostrar un mensaje amigable al usuario.
* No mostrar información técnica innecesaria al usuario final.

Si no existen pedidos para el período:

El PDF puede generarse mostrando:

```text
Sin información para el período seleccionado
```

Los indicadores deben aparecer en cero.

Los gráficos deben mostrar un estado vacío apropiado.

La tabla debe mostrar que no existen registros.

---

# 22. Seguridad

La ruta de exportación debe utilizar los mismos mecanismos de autenticación y autorización que la página "Avance de ventas".

No permitir que un usuario no autorizado descargue el reporte.

Validar los parámetros de fecha.

No confiar en valores financieros enviados desde el frontend.

Los valores financieros deben calcularse en el backend.

---

# 23. Rendimiento

Evitar generar múltiples consultas independientes para cada sección del PDF.

Reutilizar el servicio de estadísticas.

Evitar generar gráficos innecesariamente complejos.

El PDF debe generarse en un tiempo razonable.

No utilizar esperas artificiales excesivas para compensar problemas de renderizado.

---

# 24. Dependencias de servidor

Antes de finalizar la implementación comprobar que Browsershot/Chromium pueda ejecutarse correctamente en el entorno de desarrollo y en el entorno de despliegue actual.

El proyecto actualmente puede ejecutarse en Railway.

Por lo tanto, verificar específicamente los requisitos de:

* Node.js.
* npm.
* Puppeteer.
* Chromium.
* Dependencias necesarias para Chromium en el entorno de despliegue.

No asumir que una instalación que funciona localmente funcionará automáticamente en Railway.

Si se requiere configuración adicional para el despliegue, documentarla claramente.

No modificar la infraestructura de producción sin necesidad.

---

# 25. No duplicar el reporte

La página web y el PDF no deben convertirse en dos sistemas independientes de estadísticas.

Debe existir una lógica centralizada:

```text
SalesProgressService
        │
        ├── Web
        │    └── Inertia / React
        │
        └── PDF
             └── Blade / Browsershot
```

El nombre del servicio es conceptual.

Si ya existe un Service relacionado con estadísticas o avance de ventas, utilizarlo.

No crear una segunda implementación de los cálculos si ya existe una.

---

# 26. Restricciones

No implementar en esta etapa:

* Exportación Excel.
* Exportación CSV.
* Exportación Word.
* Reportes adicionales.
* Envío automático por correo.
* Programación de reportes.
* Historial de PDFs.
* Almacenamiento permanente de PDFs.
* Nuevas tablas para almacenar reportes.
* Nuevas estadísticas no solicitadas.

El objetivo es exclusivamente permitir:

"Exportar PDF" del reporte "Avance de ventas".

---

# 27. Criterios de aceptación

La funcionalidad se considera terminada cuando:

1. Existe un botón "Exportar PDF" en "Avance de ventas".
2. El botón utiliza los filtros actuales.
3. Laravel valida correctamente el período.
4. El backend obtiene nuevamente los datos utilizando la lógica centralizada.
5. Browsershot genera correctamente el PDF.
6. El PDF contiene los cuatro indicadores.
7. El PDF contiene el gráfico de evolución.
8. El PDF contiene el gráfico Pie de galones por producto.
9. Los gráficos ECharts aparecen correctamente renderizados.
10. La tabla "Resumen por día" aparece correctamente.
11. Los días sin pedidos no aparecen.
12. El margen se calcula correctamente.
13. El margen por galón muestra máximo 2 decimales.
14. Los totales coinciden con la página web.
15. El encabezado del reporte muestra el período correcto.
16. El PDF tiene formato A4 y presentación profesional.
17. La tabla puede continuar en múltiples páginas correctamente.
18. El encabezado de la tabla se repite cuando corresponda.
19. El archivo tiene un nombre descriptivo.
20. Los errores de generación quedan registrados.
21. La funcionalidad respeta la autenticación y autorización existente.
22. No se han creado tablas innecesarias.
23. No se ha duplicado la lógica de negocio.
24. La generación funciona correctamente en el entorno local.
25. Se ha verificado la compatibilidad con el entorno de despliegue actual antes de considerar terminada la funcionalidad.
