# ADR-018: Exportación PDF del reporte "Avance de ventas" utilizando Browsershot

## 1. Objetivo

Implementar la exportación a PDF del reporte "Avance de ventas".

El PDF debe contener la información del reporte actualmente mostrada en la página web:

* Período seleccionado.
* Total de galones.
* Compras totales.
* Ventas totales.
* Margen total.
* Gráfico de evolución de compras, ventas y margen.
* Gráfico Pie de galones por producto.
* Tabla "Resumen por día".

El PDF debe tener una presentación profesional y adecuada para ser compartida con gerentes, evaluadores o responsables de la operación.

La generación del PDF debe realizarse mediante Browsershot utilizando Chromium/Puppeteer.

Mantener la arquitectura existente:

* Backend: Laravel.
* Frontend: React.
* Inertia.
* Ant Design.
* Apache ECharts.

* Browsershot para generación del PDF.

La página web continuará funcionando normalmente mediante:

Browsershot

# 4. Principio importante: una sola fuente de datos

La lógica de negocio utilizada para calcular el reporte no debe duplicarse.

La página web y el PDF deben utilizar la misma lógica de backend para obtener:

* Total de galones.
* Compras.
* Ventas.
* Margen.
* Margen por galón.
* Datos diarios.
* Datos agrupados por producto.

No crear cálculos diferentes para React y PDF.

Idealmente reutilizar el mismo Service o clase existente que alimenta la página "Avance de ventas".

Conceptualmente:

```text
                Servicio de estadísticas
                         │
              ┌──────────┴──────────┐
              ↓                     ↓
           React                  Blade
              ↓                     ↓
           ECharts              ECharts
                                    ↓
                               Browsershot
                                    ↓
                                   PDF
```

Esto garantiza que los valores mostrados en pantalla y los valores exportados coincidan.

Utilizar un icono apropiado, por ejemplo un icono de archivo PDF o descarga.

# 6. Flujo de exportación

El flujo esperado es:

1. El usuario selecciona el período.
2. El usuario consulta la información.
3. La página muestra los resultados.
4. El usuario presiona "Exportar PDF".
5. React envía al backend los filtros actuales.
6. Laravel valida los filtros.
7. Laravel obtiene nuevamente los datos utilizando el servicio de estadísticas.
8. Laravel genera la vista Blade del reporte.
9. Browsershot renderiza la vista.
10. Chromium genera el PDF.
11. Laravel devuelve el archivo para descarga.

No enviar toda la información de la tabla desde React al backend para construir el PDF.

El backend debe volver a consultar los datos utilizando los filtros recibidos.

Esto evita manipulación de datos y garantiza que el PDF sea generado con información consistente.

# 14. Renderizado de ECharts en PDF

Debido a que Browsershot utiliza Chromium, los gráficos ECharts deben estar completamente renderizados antes de generar el PDF.

La implementación debe garantizar que:

1. La página HTML se cargue.
2. ECharts se inicialice.
3. El gráfico se renderice.
4. Browsershot espere a que el contenido esté disponible.
5. El PDF se genere solamente después de que los gráficos estén listos.

No generar el PDF antes de que ECharts termine de renderizar.

Si es necesario, utilizar una estrategia de espera apropiada en Browsershot/Puppeteer.

No utilizar tiempos de espera excesivamente largos como solución general.

Preferir una condición de renderizado explícita cuando sea posible.

# 18. Fórmulas

Mantener las mismas fórmulas de la página web.

> **Corrección (ver "Nota de implementación" al final del documento).** El
> margen NO es `Ventas − Compras`. Ese cálculo dejó de ser válido con ADR-013,
> que lo redefinió como la suma de `galones × plant_products.margin` por cada
> línea del pedido. La fórmula de abajo es la que está en producción; la del
> enunciado original se conserva tachada para dejar el cambio registrado.

Margen (regla vigente, ADR-013):

```text
Margen S/ = Σ (galones de la línea × margen de la relación planta+producto)
```

~~Margen S/ = Ventas S/ - Compras S/~~

Los ejemplos numéricos del enunciado (§11, §12, §17) también están calculados
con `Ventas − Compras` y deben leerse con la fórmula vigente: para el período de
setiembre 2026, ventas `S/ 90,732.40` y compras `S/ 67,401.60` darían
`S/ 23,330.80` con la fórmula antigua, mientras que el margen real del sistema
es `S/ 390.00`.

Margen por galón:

```text
Margen S/ por galón = Margen S/ / Total Galones
```

Mostrar máximo 2 decimales para margen por galón.

Si Total Galones es cero:

```text
Margen S/ por galón = 0
```

Evitar división por cero.

Además, la web y el PDF muestran `—` (no `S/ 0.00`) cuando un valor no existe:
un precio o un margen ausente se distingue de un margen de cero.

## 28.1 Lo que falta para cerrar el criterio 25

El usuario decidió explícitamente dejar Railway fuera del alcance de esta
sesión. Lo que hay que hacer cuando se retome, y que además **sí** afecta a
cualquier despliegue Linux:

* Declarar `BROWSERSHOT_CHROME_PATH` con la ruta real del Chromium del
  contenedor, o instalar el navegador del sistema y apuntar ahí
  (`/usr/bin/chromium` o `/usr/bin/chromium-browser`).
* Node.js debe estar en la imagen **y** `node_modules/puppeteer` en las
  dependencias de producción. En este proyecto `puppeteer` es `devDependency`,
  así que una instalación de producción sin `--include=dev` se quedaría sin él:
  hay que moverlo a `dependencies` o instalarlo aparte en el build.
* `PUPPETEER_SKIP_DOWNLOAD` para que la imagen no descargue un Chromium que no
  se va a usar, y los flags de headless para contenedores sin GPU
  (`--disable-gpu`, `--disable-dev-shm-usage`), que ya se envían.
* `storage/app/browsershot/` debe existir y ser escribible: ahí va el
  `user-data-dir` que se le da a Chromium.
* Límite de tiempo: la generación tarda varios segundos. El proxy tiene que
  tolerarlo y `max_execution_time` (120 s en el `php.ini` local) debería
  revisarse en producción.

## 28.2 Tres fallos reales encontrados al verificar (y sus causas)

Estos no se deducen del código: aparecieron al ejecutar contra el vhost y son
el motivo de que la verificación se hiciera por HTTP y no por CLI.

### 1. `Undefined constant "undefined"` (Blade)

La vista del PDF comparaba contra `undefined`, un valor de JavaScript:

```php
$money = fn ($value) => $value === null || $value === undefined ? $dash : …
```

En PHP, `undefined` es una **constante no definida**, y el errorAborta el
render con un 500 antes de llegar a Chromium. La aserción correcta es solo
`$value === null`.

### 2. Un filtro inválido devolvía 302 y se descargaba HTML como `.pdf`

`SalesReportRequest` es un `FormRequest` de la página web, así que por defecto
Laravel redirigía con los errores a `/reportes/avance-ventas`. Como la descarga
va por `fetch` con `responseType: 'blob'`, ese **HTML terminaba guardado en el
disco del usuario con nombre `avance-ventas.pdf`**: el peor resultado posible,
porque parece un PDF y no lo abre.

Dos arreglos, ambos en el sitio de cada capa:

* `SalesReportRequest::failedValidation()` devuelve **422 con JSON** solo cuando
  la ruta es `reports.sales.export`. La página web conserva su redirect de
  siempre, que es lo que Inertia espera para pintar los errores.
* `SalesReports.exportPdf()` revisa el `Content-Type` de la respuesta: si no es
  `application/pdf`, desarma el blob y lanza el mensaje real. Sin esto, un 422 o
  un 500 con `responseType: 'blob'` se resuelven "con éxito" y llegan a la
  descarga.

### 3. Chromium: Edge no arranca bajo php-cgi (el hallazgo más importante)

Apache de WAMP corre como servicio de Windows (`LocalSystem`, **sesión 0**), sin
escritorio y sin `USERPROFILE`. En ese contexto **el binario de Edge aborta con
`Code: 1002` incluso con `--version` y sin ninguna bandera**: no es un problema
de headless, de sandbox ni de perfil, y ninguna bandera de Chromium lo arregla.

Esto es exactamente el fallo que se esconde si se valida con
`php artisan serve`: PHP-CLI hereda el entorno del shell, donde Edge sí arranca,
y la función parece funcionar mientras el vhost devuelve 500 a los usuarios.

**Google Chrome sí arranca en el mismo contexto** (verificado: mismo `LocalSystem`,
mismo binario vía Puppeteer, exit 0 y DOM devuelto). Por eso
`BROWSERSHOT_CHROME_PATH` apunta a Chrome en desarrollo, y el servicio le pasa un
`user-data-dir` propio bajo `storage/app/browsershot/profile`.

El diagnóstico que lo aislado (comparar `cmd`, `node` y `chrome --version` bajo
el mismo `Process`) está en la nota de verificación de `AGENTS.md`.

### 4. `process is not defined` en el bundle del PDF

`vite.pdf.config.js` no definía `process.env.NODE_ENV`, y el runtime inlineado
reventaba en el navegador con `ReferenceError: process is not defined` antes de
pintar nada. El síntoma era silencioso en apariencia: `__pdfChartsReady` se
quedaba en `false` y Browsershot agotaba los 30 s esperando.

Se resuelve con un bloque `define` en `vite.pdf.config.js`
(`process.env.NODE_ENV = 'production'`). **No lo detecta el build**: el bundle
sale bien y solo falla al ejecutarse, así que hace falta ejecutarlo de verdad.
