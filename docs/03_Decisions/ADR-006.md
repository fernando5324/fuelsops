# ADR-006: Public Form and Internal Platform UI Design

- **Status:** Accepted
- **Date:** 2026-09-20
- **Scope:** Sertoco public order form and internal platform
- **Related:** ADR-001 - Initial Database Structure

## Context

The first Sertoco prototype already has a functional public order
registration form.

The current implementation reproduces the main business workflow, but its
visual design is still relatively technical and form-oriented.

The objective of this decision is to improve the user experience without
changing the underlying business workflow.

The current Sertoco form, used as the functional reference, contains the
following information:

- Order date
- Advisor
- Customer RUC
- Customer name
- Driver license
- Driver full name
- Tanker plate
- Tractor plate
- SCOP
- Plant
- Wholesaler
- Product
- Gallons
- Sale price
- Compartments
- Order observations
- Total gallons
- Total customer sale
- Order registration action

The current form is divided visually into the following sections:

1. General information
2. Driver information
3. Vehicle information
4. Order detail
5. Order observations
6. Order summary
7. Register order

The attached reference screenshot represents the existing business
workflow and should be treated as the functional baseline.

It should NOT be treated as the final visual design.

The new interface should preserve the required business information while
making the application easier to understand, faster to use and less
technical for normal users.

The application has two different UI contexts:

1. Public order registration.
2. Internal platform for managing orders, catalogs and related information.

These two contexts should share the same visual identity but should not
necessarily use exactly the same layout.

---

## Decision

Sertoco will use a friendly, clean and business-oriented UI instead of a
technical-looking administration interface.

The design will prioritize:

1. Clarity
2. Fast data entry
3. Visual hierarchy
4. Readability
5. Responsive behavior
6. Clear validation
7. Consistent actions
8. Low visual noise
9. Reusable components
10. Consistent branding

The redesign must improve the presentation and interaction of the existing
workflow without changing business rules or database contracts.

The public form should be optimized for completing an order.

The internal platform should be optimized for finding, reviewing and
managing information.

## 1. Brand Identity

### 1.1 Primary colors

The current Sertoco brand colors are:

```
Primary blue:
#1B3A6B

Primary orange:
#F47920
```

These colors must become centralized design tokens or CSS variables.

For example:
```
--color-primary: #1B3A6B;
--color-accent: #F47920;
```

Do not scatter hexadecimal values throughout individual components.

The exact naming may follow the project's existing styling conventions.

## 1.2 Color usage

Blue should primarily represent:

- Brand identity
- Header
- Sidebar
- Navigation
- Primary structural elements
- Selected navigation items
- Important informational elements

Orange should primarily represent:

- Main call-to-action
- Active progress
- Important highlights
- Primary action emphasis
- Small visual accents

Orange should not be used for every button, label or piece of text.

The interface should use neutral colors for most backgrounds, inputs,
surfaces and secondary information.

The goal is to make the orange visually meaningful rather than saturating
the interface with the brand color.

distorted.

## 16. Add Product

The current button says:
```
+ Agregar fila
```
This should be changed to:
```
+ Agregar producto
```
"Fila" is an implementation concept.

"Producto" is a business concept.

The first product row should be available automatically.

Additional rows should be added by the user.

The number should be generated automatically.

Users should never manually enter the row number.

## 17. Removing Products

If a product row contains information, removing it should not accidentally
delete data.

The interface may:

- Ask for confirmation.
- Or provide an undo action.

The selected approach should remain simple.

After removal, visible row numbers should be recalculated.

## 24. Validation

Validation should be understandable to normal users.

Avoid messages such as:
```

SQLSTATE[23000]
Invalid foreign key
```
Use:
```

```
or:
```

```
Errors should appear next to the relevant field.

For a long form, a general message may also be displayed:
```
Revisa los campos marcados antes de registrar el pedido.
```

The interface should focus or scroll to the first relevant error when
appropriate.

Previously entered valid information must never be lost because of a
validation error.

## 25. Success State

After successfully registering the order, do not simply clear the form.

```
[ Ver pedido ]
[ Registrar otro pedido ]
```
The exact actions can depend on whether the public form is authenticated
or anonymous.

## 33. Internal Forms

Internal forms should follow the same design language as the public form.

Every input should have:

- Visible label
- Appropriate input type
- Clear validation
- Required/optional indication where relevant
- Help text only when useful

Do not use placeholder text as the only label.

Primary actions should be visually clear:
```
[ Guardar ]
```
Secondary actions:
```
[ Cancelar ]
```
Destructive actions should use explicit text:
```
Eliminar producto
```
instead of an ambiguous icon alone.

## 34. Typography

Use a clean and readable sans-serif font.

The current screenshot uses strongly condensed uppercase labels.

That visual treatment may be retained selectively for branding or small
section labels, but it should not dominate the entire interface.

Do not use uppercase for long descriptions.

Preferred hierarchy:
```
Page title
Section title
Field label
Body text
Help text
```

Text should prioritize readability over decorative styling.

## 35. Cards and Sections

Cards should be used to group meaningful information.

Avoid putting every individual input into a separate card.

Use:

- Moderate border radius
- Light borders
- Subtle shadows
- Consistent internal spacing

Avoid excessive shadows, excessive floating elements and unnecessary
visual containers.

The current screenshot contains several large white cards separated by
large amounts of empty space.

The redesigned interface can keep cards where useful but should reduce
unnecessary vertical fragmentation.

## 36. Spacing

Use a consistent spacing system.

Do not manually invent different margins for every component.

The form should have enough whitespace to remain comfortable, but should
not become unnecessarily long.

The goal is:
```
Clear
Comfortable
Compact enough for productivity
```
rather than:
- Maximum whitespace

## 37. Responsive Design

The public form must work correctly on:

- Desktop
- Laptop
- Tablet
- Mobile

Desktop:

- Two-column form fields where appropriate.
- Product table.
- Full navigation when applicable.

Tablet:

- Reduce columns where necessary.
- Maintain comfortable controls.

Mobile:

- One-column form.
- Product rows become cards or stacked groups.
- Large enough touch targets.
- Primary action remains easy to access.
- No unusable compressed tables.

The public order registration flow should receive particular attention on
mobile because users may not always complete it from a desktop computer.

## 38. Interaction States

Important controls must support:

- Default
- Hover
- Focus
- Active
- Disabled
- Loading
- Success
- Error

Inputs should have a clear focus state.

Buttons should have a visible loading state when an operation is running.

Example:

Registrar pedido

changes temporarily to:

Registrando...

and becomes disabled until the operation completes.

This prevents accidental duplicate submissions.

## 39. Accessibility

The redesigned UI must maintain basic accessibility.

At minimum:

- Every input has a real label.
- Buttons have understandable text or accessible labels.
- Icons are not the only source of meaning.
- Keyboard focus is visible.
- Color is not the only way to communicate status.
- Text has sufficient contrast.
- Error messages are understandable.
- Interactive elements have adequate touch targets.

The interface should not sacrifice accessibility merely to reproduce the
visual style of the current screenshot.

## 46. Important OpenCode Constraints

The implementation must NOT:

- Change database tables merely to improve the UI.
- Rename backend fields merely because the Spanish label is different.
- Change business calculations.
- Change the meaning of SCOP.
- Change the meaning of compartments.
- Remove any existing business field without a separate decision.
- Introduce unnecessary workflow states.
- Introduce charts without a business requirement.
- Introduce complex drag-and-drop functionality.
- Introduce excessive animations.
- Replace the logo.
- Replace the brand colors.
- Turn every element into a card.
- Use excessive gradients.
- Use excessive glassmorphism.
- Make the application look like a generic SaaS landing page.
- Expose database terminology to normal users.
- Create technical-looking error messages.
- Make the mobile product table unusable.

The redesign is a UX/UI improvement, not a business logic rewrite.

## 53. Nota de implementación (02-10-2026): resumen de la página de confirmación

Estado: **implementado y verificado**. Alcance: solo la página pública
`/pedidos/{order}/confirmado` (`Public/Orders/Confirmed.jsx`) y el `confirmed()`
del controlador público. Sin cambios de esquema, sin rutas nuevas y sin tocar
el panel.

Motivo: el formulario público funciona (ADR-015 incluido), pero la página de
confirmación mostraba **datos ausentes sin dar error**.

### El defecto de fondo: relaciones no cargadas

`Public\OrderController::confirmed()` hacía
`$order->load(['customer', 'details', 'status'])`. Las relaciones que no se
cargan llegan como `null` al front, y como todo el render usa `?.` y `|| '-'`
**no hay excepción ni warning**: la información simplemente no aparece.

| Se veía | Causa |
| --- | --- |
| Asesor en blanco | `advisor` sin cargar (`order.advisor === null`) |
| Planta, mayorista y producto del detalle **todos en `-`** | `details.plant/wholesaler/product` sin cargar, y el render era `r.plant?.name \|\| '-'` |
| Conductor y vehículos ausentes | `driver`, `tanker`, `tractor` sin cargar y sin renderizar |
| Observaciones ausentes | el dato **sí** llegaba (`notes` es un atributo, no una relación): simplemente no se pintaba |
| Documentos adjuntos ausentes | `files` sin cargar y sin renderizar |
| Distribución por compartimentos ausente | ADR-015 §7 la dejó fuera de alcance (ya no: ver abajo) |
| Galones y precio "crudos" (`3000.00`, `22.8468`) | la tabla usaba `dataIndex` sin `render`, sin el locale de plataforma |

La corrección es **eager loading explícito** de todo lo que la página pinta:

```php
$order->load([
    'advisor', 'customer', 'driver', 'tanker', 'tractor', 'status',
    'details.plant', 'details.wholesaler', 'details.product',
    'compartments.product',
    'files',
]);
```

### Estructura elegida: secciones numeradas como el formulario

Decidido con el usuario: el resumen se reorganiza en **6 `SectionCard`
numeradas, en el mismo orden del formulario** (así el cliente verifica campo
por campo lo que acaba de enviar), en lugar de una sola tarjeta con
`Descriptions`:

1. **Información general** — fecha (con hora), estado (`Tag` con el color del
   estado), asesor, cliente con su RUC.
2. **Datos del chofer** — licencia y nombre.
3. **Datos del vehículo** — placa de la cisterna y del tracto.
4. **Detalle del pedido** — tabla con `#`, SCOP, planta, mayorista, producto,
   galones (`formatGallons`), precio (`formatMoney`) y total
   (`formatMoney(gallons × sale_price)`); se **agrega la columna `#`** (la
   tenía el formulario) y se normaliza el formato de los importes.
5. **Distribución por compartimentos** — tabla de solo lectura
   `Comp · Producto · N° SCOP · Volumen (gal)` con pie `Total de galones` y
   estado vacío `no_compartments`. Es la primera vez que la página pública la
   muestra: **anula el punto 7 de la nota de implementación de ADR-015**, que
   la dejaba fuera de alcance.
6. **Observaciones y documentos** — las notas (o `no_observations`) y la tabla
   de adjuntos (nombre, tipo, tamaño con `formatFileSize`, o `no_documents`).

Debajo queda el resumen con las clases `ui-summary` ya existentes (galones en
azul `--info` y total a cobrar en naranja `--money`, con sus `*_hint`) y los
botones "Registrar otro pedido" / "Volver al inicio". El hero de éxito se
mantiene igual. Se quitó la `Card` que envolvía todo el contenido: el
espaciado lo aporta `ui-card-gap` de `SectionCard`, igual que en el formulario.

### Decisiones tomadas con el usuario

1. **Secciones numeradas**, no una tarjeta única (consistencia con el formulario
   y con el detalle del panel).
2. **Los adjuntos se listan sin enlace.** La ruta `/media/{mediaFile}/download`
   está dentro del grupo con autenticación, así que un cliente público no puede
   descargar; se confirma qué se adjuntó (nombre, tipo, tamaño) y se aclara con
   `confirmed_files_hint` que la descarga se hace desde la plataforma. **No se
   abrió la descarga al público** (la URL de la confirmación es adivinable por
   id).
3. **No se muestran precio de compra ni ganancia.** `OrderService::totals()`
   también los calcula (los usa el panel), pero son datos internos de Sertoco y
   esta es una página pública: solo se expone lo que se le cobra al cliente
   (`total_gallons` y `total_sale`).

### Gotcha nuevo (antd v6) detectado al escribir el headless

`.ant-table-tbody tr` incluye una fila **oculta `.ant-table-measure-row`** (la
tabla de medición de columnas, en un `<table>` propio sin `thead`) cuyos `td`
contienen los rótulos de columna. Filtrar solo por "tiene `td`" no alcanza:
hay que excluir `r.classList.contains('ant-table-measure-row')`. Si no, la
primera fila que devuelve el selector es el encabezado y las aserciones de
contenido fallan sin que el producto esté mal.
