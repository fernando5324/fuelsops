# ADR-062: Estrategia de internacionalización del panel y contenido multilingüe

**Estado:** Aceptado
**Fecha:** 2026-08-31

## Contexto

La plataforma contará con un panel administrativo utilizado por los usuarios para configurar y administrar sus organizaciones.

Se requiere diferenciar dos necesidades de internacionalización:

1. El idioma de la **interfaz del panel administrativo**.
2. Los idiomas del **contenido publicado por cada organización**.

El panel administrativo deberá estar preparado para soportar múltiples idiomas, aunque inicialmente solo se habilitará el español.

Por otro lado, una organización podría necesitar publicar su sitio web en uno o varios idiomas. Por ejemplo, una organización podría tener únicamente contenido en inglés, o mantener versiones en español e inglés de un mismo producto, servicio, artículo o página.

Se evaluó almacenar directamente un campo `lang` o `locale` dentro de las tablas principales:

```text
products
id | lang | name
1  | es   | Curso de Laravel
2  | en   | Laravel Course
```

Este modelo permite representar diferentes idiomas, pero implica duplicar la entidad principal y puede generar ambigüedad respecto a información que no debería depender del idioma, como precio, stock, estado, relaciones, identificadores y otros datos estructurales.

También se consideró crear una organización independiente para cada idioma. Esta alternativa fue descartada debido a que diferentes idiomas representan versiones del mismo negocio y no organizaciones independientes.

## Decisión

La plataforma diferenciará entre **internacionalización de la interfaz administrativa** y **contenido multilingüe de las organizaciones**.

### 0. Fuente única de traducciones (revisión T-041)

Se consolidó el español como idioma principal con fuente única de traducciones:
todo texto de sistema (botones, etiquetas, placeholders, alertas, mensajes de
validación y notificaciones del panel, flujo público y páginas de auth) vive en
`lang/es/*.php`. El front NO mantiene un archivo de traducciones propio.

- `resources/js/i18n.js` fue eliminado (dejó de existir como fuente duplicada).
- El backend comparte en cada respuesta Inertia las props globales
  `translations` (todos los grupos de `lang/es/*.php`, key = basename del
  archivo) y `locale`, desde `HandleInertiaRequests`.
- El front consume el hook `useTranslations` (`resources/js/hooks/
  useTranslations.js`): `t('grupo.clave')` con lookup anidado por puntos,
  fallback = clave cruda si no existe, soporte `{ reemplazo: ':param' }` y
  devuelve también `locale`. Los componentes modernos lo usan vía
  `const { t } = useTranslations();`.
- Nomenclatura de claves: agrupadas por dominio funcional en `common`,
  `auth`, `menus`, `order`, `catalogs`, `profile`, `pages`, `tiptap`,
  `services`, `validation`. En React siempre se usa la clave anidada
  `grupo.clave`.
- `lang/es/auth.php` mantiene `password` para el mensaje de error del backend
  y expone `password_label` para el label del formulario.
- Regla de UI: los botones de guardar/enviar usan `SubmitButton`, que se
  bloquea (loading global) mientras haya una mutation Inertia en vuelo
  (`ProcessingProvider`), evitando dobles envíos. Aplica a login, registro,
  formulario público de pedidos, formularios de perfil, modal de catálogos y
  cambio de estado de pedido.
- Las traducciones aplican solo a la interfaz del sistema; la información
  registrada por las organizaciones (nombres de catálogos, estado de pedido,
  etc.) se muestra tal cual no se traduce.

### 1. Internacionalización del panel administrativo

El panel administrativo utilizará un sistema de traducciones centralizado basado en Laravel e integrado con Inertia para que React pueda consumir las traducciones.

La estructura deberá permitir inicialmente:

```text
lang/
├── es/
└── en/
```

El español será el idioma inicial del sistema, pero la arquitectura deberá permitir incorporar otros idiomas posteriormente.

Las traducciones de la interfaz deberán estar centralizadas y no deberán estar hardcodeadas directamente en los componentes React cuando representen textos propios de la plataforma.

Ejemplos:

```text
Nombre
Apellido
Estado
Guardar
Cancelar
Editar
Eliminar
Acciones
```

Se utilizará una estructura organizada por dominio funcional, por ejemplo:

```text
lang/
└── es/
    ├── common.php
    ├── auth.php
    ├── users.php
    ├── organizations.php
    ├── order.php
    ├── media.php
    ├── menus.php
    ├── settings.php
    └── validation.php
```
