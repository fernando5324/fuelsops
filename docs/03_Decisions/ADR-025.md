# ADR-025: Alta manual de pedidos en el panel y origen del registro

**Estado:** Accepted
**Fecha:** 2026-10-04
**Alcance:** Pedidos / Panel / Formulario público / Auditoría / Esquema
**Proyecto:** Plataforma multi-tenant de gestión de pedidos

---

## Problema

El único camino para crear un pedido era el formulario público. El panel no
tenía alta: un pedido recibido por teléfono, correo o Whatsapp y registrado por
un asesor tenía que anotarse fuera del sistema (hoja de cálculo, papel) y luego
volver a digitarse, o enviar al cliente al formulario web con el RUC de la
empresa equivocada.

Además, en la ficha del pedido no se podía distinguir **quién pidió el pedido**
de **quién lo registró**:

```
Pedido PED-000125
Cliente: Empresa ABC SAC
Asesor: Juan Pérez
```

El usuario que registró el pedido (`created_by`) no es necesariamente el
cliente que lo solicitó. Cuando el propio cliente entra al formulario con una
sesión abierta, `created_by` es ese cliente; cuando es anónimo, es el usuario
sistema `999999`. Ninguno de los dos valores responde "¿este pedido lo pidió el
cliente o lo registró un usuario del panel?".

## Decisión

### 1. El origen es una columna, no una inferencia

```
orders
└── source VARCHAR(20) NOT NULL DEFAULT 'panel'
```

Valores:

| Valor | Significado |
|---|---|
| `public` | Lo registró el cliente desde el formulario web |
| `panel` | Lo registró un usuario del panel (alta manual, ADR-025) |

El `DEFAULT 'panel'` existe para que un `INSERT` crudo (seeds, scripts) no
tenga que conocer la columna y no se rompa.

### 2. El origen lo fija el controlador que crea, nunca el formulario

```
Public\OrderController@store     → create($data, 'public')
Platform\OrderController@store   → create($data, 'panel')
```

No se deduce de la petición, ni de la sesión, ni de la IP, ni del User-Agent.
Un pedido que un usuario del panel rellena **por teléfono** usando el formulario
web sigue siendo `public`: lo pidió el cliente. Esa es justamente la
distinción que se quiere conservar.

`OrderService::create()` recibe el origen como **argumento explícito**:

```php
public function create(array $data, string $source = 'public'): Order
```

El default es `public` porque es el caso mayoritario y el histórico.

### 3. `source` es inmutable al editar

`UpdateOrderRequest` no acepta `source`. La edición de un pedido no puede
convertir un alta de panel en un alta pública ni al revés: el origen es un hecho
histórico del registro, igual que la fecha.

### 4. `created_by` conserva el actor, `source` el origen

Son datos distintos y se muestran distintos:

- `created_by` = quién hizo la acción (usuario autenticado, o `999999` si fue un
  envío público anónimo). Es lo que escribe el trait `Auditable`; no se toca.
- `source` = quién pidió el pedido.

En la cabecera de la ficha (`Components/Orders/OrderHeader.jsx`):

```
source = public  →  "Registrado por el cliente (formulario web)"
source = panel   →  "Creado por: {nombre}"
                     "Actualizado por: {nombre} · dd/mm/yyyy hh:mm:ss"   ← solo si updated_by ≠ NULL
```

`updated_by` es `NULL` mientras nadie haya modificado el pedido, así que esa
línea no aparece en un pedido recién creado (no se inventa una fecha de
actualización que no ocurrió).

### 5. El alta manual reutiliza el formulario de edición

```
GET  /pedidos/nuevo   →  Platform/Orders/Edit  con  order = null
POST /pedidos         →  OrderController@store
```

Un solo formulario para crear y editar, con las mismas secciones del diseño
(`docs/06_Design/order-detail.md`): información general, datos del chofer, datos
del vehículo, detalle del pedido, distribución por compartimentos (ADR-015),
observaciones y adjuntos. `Edit.jsx` deriva el modo de `order`
(`const isCreate = !order`).

Consecuencia: cualquier campo que se agregue a la edición aparece
automáticamente en el alta. La única excepción es `code`.

### 6. El código no se pide en el alta

El alta manual **no** muestra el campo de código: lo genera la secuencia por
organización (`OrderCodeService`, ADR-020). Es el mismo comportamiento del
formulario público y evita que un operador escriba un código repetido. Después
de crear, el pedido queda en modo consulta y su código se puede editar como
cualquier otro dato (ADR-020 §6).

### 7. Sin permiso adicional

Cualquier usuario autenticado del panel puede registrar un pedido. No se agrega
un gate: crear el pedido es la operación de menor riesgo del módulo y el panel
ya está detrás de la autenticación. Lo que sí sigue reservado al dueño
(`is_owner`) es la papelera y el borrado/restauración (ADR-011), sin cambios.

### 8. Rutas antes del binding

```
/pedidos               (index)
/pedidos/papelera      (trash)
/pedidos/papelera/{order}
/pedidos/nuevo         (create)   ← antes de /pedidos/{order}
/pedidos/{order}
```

`/pedidos/nuevo` y `POST /pedidos` deben declararse antes de `/pedidos/{order}`
o el binding se las comería.

### 9. El snapshot de papelera incluye el origen

`OrderService::buildSnapshot()` agrega `order.source` al snapshot de
`order_deletions`, para que un pedido dado de baja siga documentando de dónde
vino.

### 10. La fecha del alta manual admite pasado

`order_date` es `nullable|date` en `StoreOrderRequest` (igual que en la
edición, que opera sobre pedidos históricos). El formulario público sí exige
el día de hoy (ADR-023): quien registra en el panel está transcribiendo un
pedido que ya ocurrió.

## Migración

Aplicada directamente sobre la base viva (no hay migraciones en el proyecto,
ver `AGENTS.md`):

```sql
ALTER TABLE orders ADD COLUMN source VARCHAR(20) NOT NULL DEFAULT 'panel';
UPDATE orders SET source = 'public' WHERE id IN (...);   -- los que Vijeron por el formulario web
```

Se dejó `source = 'panel'` en los pedidos de semilla (`SEEDS.sql`), porque en
la historia de demo son altas de panel. Se reflejó el cambio en
`docs/02_Database/database.sql`, `docs/02_Database/database_design.md` y
`docs/02_Database/SEEDS.sql`.

## Impacto en código

- **Modelo**: `Order::$fillable` suma `source`; docblock que explica que es
  el origen y no el actor.
- **Service**: `OrderService::create(array $data, string $source = 'public')`
  (el `$source` viaja al `DB::transaction` y se persiste) y `buildSnapshot()`
  con `order.source`.
- **Requests**: nuevo `StoreOrderRequest` (espejo de `UpdateOrderRequest` sin
  `code` ni `remove_files`, con `order_date` admitted en pasado). `UpdateOrderRequest`
  no cambia: nunca admite `source`.
- **Controllers**: `OrderController::create()` (props de catálogos para el
  formulario), `OrderController::store()` (redirect a la ficha + flash
  `order.created_ok`) y `show()` que ya cargaba `createdBy`, ahora también
  `updatedBy:id,name`. `TrashController::show()` carga `updatedBy:id,name`.
  `Public\OrderController@store()` pasa `'public'` explícito.
- **Rutas**: `pedidos.create` y `pedidos.store` antes de `pedidos.show`.
- **Frontend**: botón "Nuevo pedido" en el `PageHeader` de `Orders/Index.jsx`
  (`Orders.routes.create` / `Orders.routes.store`); `Edit.jsx` en modo alta
  (`isCreate`): sin campo de código, botón "Registrar pedido", `forceFormData`
  con `router.post` al store, y en edición sigue `POST` + `_method=PUT`;
  `OrderHeader.jsx` acredita el origen y la última modificación.
- **i18n**: `order.new_order`, `order.create_order`, `order.created_ok`,
  `order.source_customer`.

  `/pedidos/nuevo` con el componente `Platform/Orders/Edit` y `order = null`;

## Notas

- **El alta manual no es una API JSON**: el panel consume Inertia para los
  formularios (ADR-009/ADR-066) y las APIs `/api/*` quedan para los catálogos y
  acciones puntuales. No se creó `POST /api/orders`.
- **`source` todavía no filtra ni exporta**: no entra en el `q` de los listados,
  ni en el export a Excel, ni en los reportes. Si se necesita, es un filtro
  aditivo sobre una columna indexable.
- **Multipart**: el alta y la edición van con `forceFormData`. En la edición se
  conserva el patrón ya documentado de `POST` + `_method=PUT` porque PHP no
  puebla `$_POST`/`$_FILES` en `PUT` multipart; el alta no necesita el truco
  porque su ruta es `POST`.
- **El E2E tiene que hablar multipart de verdad**: PHP cURL no procesa un
  `CURLFile` anidado dentro de `CURLOPT_POSTFIELDS` (el archivo llega como
  `files.0` sin ser archivo y el alta falla con un 422 que parece del producto).
  La forma que funciona es `curl.exe -F` invocado con `proc_open` y argumentos
  como array (`bypass_shell`), con cookies a mano y el `XSRF-TOKEN` URL
  decodificado en la cabecera.
- **Ojo con los redirects en un E2E**: un regex floja tipo
  `#/pedidos/(\d+)#` sobre el `Location` de un `back()` de validación
  (`/pedidos/1/editar`) hace que la prueba se quede con el ID de un pedido
  existente y termine borrándole los hijos. El `orderIdFromLocation` del script
  exige el path exacto (`/pedidos/{id}/confirmado`) y falla si el ID ya existía
  al inicio de la corrida.
- **`verify_order_compartments.php` estaba muerto** (no fallaba: no se
  ejecutaba). Tres defectos de un archivo minificado en una sola línea:
  `<?php/**` sin espacio (PHP exige un espacio tras `<?php`; con
  `short_open_tag=Off` el archivo se **imprime como texto** y sale con código 0,
  un verde falso), comentarios `//` que se comían el resto del archivo, y un
  nowdoc `<<<'PHPX'…PHPX;` que no puede cerrar sin salto de línea. Al
  repararlo apareció un error de sintaxis real oculto detrás de los `//`:
  `! empty($co['tractor_plate')` sin corchete. Se reparó el archivo y su
  aserción de placas del seed, que había quedado vieja con ADR-023 (ahora hay
  2 vehículos cisterna, cada uno con su `tractor_plate`, no 4 filas con 4
  placas). Además se le agregó restaurar `order_code_counters` al baseline: la
  corrida anterior lo dejó en 20 y desalineó la secuencia.
