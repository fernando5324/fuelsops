# ADR-024: Persistencia histórica de pedidos, referencias de catálogo y configuración de compartimentos

**Estado:** Accepted  
**Fecha:** 2026-10-03  
**Alcance:** Pedidos / Catálogos / Vehículos / Compartimentos / Snapshots históricos / JSON  
**Proyecto:** Plataforma multi-tenant de gestión de pedidos

---

## 1. Contexto

La plataforma trabaja con entidades reutilizables que funcionan como catálogos o maestros:

- Clientes.
- Asesores.
- Conductores.
- Vehículos.
- Plantas.
- Mayoristas.
- Productos.
- Otros catálogos relacionados con los pedidos.

Los pedidos utilizan estas entidades mediante relaciones.

Sin embargo, un pedido representa un hecho histórico.

Por lo tanto, la información mostrada en un pedido no debe depender exclusivamente del estado actual de los catálogos.

Por ejemplo:

```
Pedido PED-000125
Cliente: Empresa ABC SAC
Asesor: Juan Pérez
Cisterna: ABC-123
```
Si posteriormente:

- El cliente cambia de nombre.
- El asesor cambia de datos.
- El vehículo cambia su configuración.
- El vehículo queda inactivo.
- El registro de catálogo deja de estar disponible.

El pedido histórico debe continuar mostrando la información correspondiente al momento en que fue registrado.

## 2. Problema

Utilizar únicamente claves foráneas hacia los catálogos puede generar problemas históricos.

Ejemplo:
```
orders.customer_id = 20
```
Si el cliente 20 cambia su nombre, una consulta directa al catálogo podría mostrar el nombre actual en un pedido histórico.

También existe el problema de los vehículos y sus compartimentos.

Una cisterna puede tener una configuración:
```
Compartimento 1 → 5,000 galones
Compartimento 2 → 4,000 galones
Compartimento 3 → 3,000 galones
```
Esta configuración puede cambiar posteriormente.

El pedido debe conservar la configuración que correspondía al vehículo en el momento de realizarse.

## 3. Decisión

Se adopta un modelo híbrido:
```
Modelo relacional
        +
Referencias a catálogos
        +
Snapshots históricos
        +
JSON únicamente para información complementaria
```
El JSON no reemplazará las relaciones ni las tablas estructuradas del pedido.

Los datos importantes para consultas, cálculos, relaciones y reportes permanecerán en columnas y tablas relacionales.

Los snapshots conservarán la información histórica necesaria para representar correctamente el pedido en el momento en que fue creado.

## 4. Las relaciones con catálogos se mantienen

Los pedidos continuarán utilizando claves foráneas hacia las entidades maestras.

Ejemplo conceptual:

orders
├── tenant_id
├── advisor_id
├── customer_id
├── driver_id
├── tanker_id
└── tractor_id

Los detalles del pedido continuarán utilizando relaciones:

order_details
├── order_id
├── plant_id
├── wholesaler_id
└── product_id

Las relaciones son importantes para:

Integridad referencial.
Consultas.
Reportes.
Filtros.
Estadísticas.
Identificación de la entidad original.
Integración con otros procesos.

No se deben eliminar estas relaciones simplemente para utilizar JSON.

5. Los catálogos no deben eliminarse físicamente cuando tengan historial

Las entidades utilizadas por pedidos históricos deben conservarse.

Cuando una entidad deja de estar disponible para nuevos pedidos, debe utilizarse preferentemente:

is_active = 0

o el mecanismo equivalente existente.

Cuando corresponda al modelo del proyecto:

is_deleted = 1

Esto permite que:

Cliente ABC

pueda quedar inactivo para nuevos pedidos, pero continúe existiendo para los pedidos históricos.

No se debe utilizar eliminación física de registros maestros que tengan referencias históricas, salvo que exista una estrategia explícita para conservar el historial.

Las relaciones importantes deben utilizar ON DELETE RESTRICT cuando corresponda.

6. Snapshot histórico

Los pedidos deben conservar determinados datos históricos de las entidades relacionadas.

Un snapshot representa la información de una entidad en el momento en que fue utilizada por el pedido.

Ejemplo:
```
{
    "customer": {
        "id": 20,
        "name": "Empresa ABC SAC",
        "tax_id": "20123456789"
    },
    "advisor": {
        "id": 15,
        "name": "Juan Pérez"
    },
    "driver": {
        "id": 4,
        "name": "Carlos López",
        "license_number": "Q12345678"
    }
}
```
El snapshot no reemplaza:
```
orders.customer_id
orders.advisor_id
orders.driver_id
```
Ambos cumplen funciones diferentes.

## 7. Referencia vs Snapshot

Debe entenderse claramente la diferencia.

Referencia

Ejemplo:

orders.customer_id = 20

Significa:

Este pedido estuvo relacionado con el cliente cuyo ID era 20.

Permite relacionar el pedido con el catálogo actual.

Snapshot

Ejemplo:
```
{
    "name": "Empresa ABC SAC",
    "tax_id": "20123456789"
}
```
Significa:

Estos eran los datos relevantes del cliente en el momento en que se registró el pedido.

El sistema debe poder utilizar el snapshot para representar correctamente la información histórica.

## 8. No guardar todo el pedido como JSON

No se debe implementar el pedido como una única estructura JSON que contenga toda la información.

Evitar un diseño como:
```
orders
├── id
├── code
└── data JSON
```
donde toda la información del pedido esté almacenada dentro de data.

Esto dificultaría:

- Consultas.
- Reportes.
- Filtros.
- Agregaciones.
- Integridad referencial.
- Cálculos.
- Índices.
- Mantenimiento.

La información estructurada y consultable debe permanecer en el modelo relacional.

## 9. Uso permitido del JSON

El JSON puede utilizarse para almacenar información complementaria, flexible o snapshot histórico cuando resulte conveniente.

Por ejemplo:
```
orders
└── snapshot_data JSON
```

o una estructura equivalente definida durante la implementación.

El contenido debe representar datos históricos y no reemplazar columnas o relaciones necesarias para el funcionamiento normal del sistema.

El diseño final de la columna JSON puede adaptarse a la estructura existente siempre que respete esta decisión.

## 10. Datos del pedido que deben permanecer relacionales

Los siguientes tipos de información deben permanecer estructurados:

- Identificador del pedido.
- Tenant.
- Código del pedido.
- Fecha.
- Estado.
- Referencias principales.
- Detalles del pedido.
- Producto.
- Planta.
- Mayorista.
- Galones.
- Precios.
- Compartimento asignado.
- Valores utilizados para cálculos.
- Cualquier información necesaria para reportes o agregaciones.

No deben trasladarse a JSON simplemente para evitar crear o utilizar relaciones.

## 11. Configuración de compartimentos de vehículos

Se incorpora el concepto de configuración de compartimentos para vehículos tipo cisterna.

Una cisterna puede tener una configuración como:
```
Cisterna ABC-123

Compartimento 1 → 5,000 galones
Compartimento 2 → 4,000 galones
Compartimento 3 → 3,000 galones
Compartimento 4 → 2,000 galones
```
Esta configuración pertenece al vehículo y debe poder utilizarse para facilitar el formulario público.

La arquitectura debe permitir una estructura equivalente a:
```
vehicles
    ↓
vehicle_compartments
```

En el snapshot debe guardarse los compartimentos de un pedido asi:
```
{
"1": 1000,
"2": 0,
"3": 1000,
"4": 0
}
```

La tabla y nombres definitivos pueden adaptarse a las convenciones existentes.

## 12. Autocompletado de cisterna en el formulario público

El formulario público debe permitir ingresar o seleccionar una cisterna mediante autocompletado.

Flujo esperado:
```
Usuario ingresa código/placa de cisterna
              ↓
       Autocompletado
              ↓
      Vehículo encontrado
              ↓
    Obtener compartimentos
              ↓
Mostrar capacidades disponibles
```
Ejemplo:

```
Cisterna: ABC-123

Compartimentos disponibles:
1 → 5,000 gal
2 → 4,000 gal
3 → 3,000 gal
4 → 2,000 gal
```
Esto facilita al usuario la creación del pedido y reduce errores de digitación.

## 13. Los compartimentos pertenecen al vehículo como configuración

La configuración general del vehículo debe representar su capacidad conocida.

Ejemplo:
```
vehicle_id = 8

compartment 1
capacity = 5000

compartment 2
capacity = 4000

compartment 3
capacity = 3000
```

Esto permite que el formulario público consulte automáticamente las capacidades disponibles.

Sin embargo, la configuración actual del vehículo no debe utilizarse como única fuente para representar pedidos históricos.

## 14. Asignación de compartimentos en el pedido

Cuando un usuario crea un pedido, los compartimentos seleccionados forman parte de la información específica de ese pedido.

Ejemplo:
```
Pedido PED-000125

Producto: Diesel
Compartimento: 1
Capacidad histórica: 5,000
Galones solicitados: 4,800
```

Otro detalle podría ser:
```
Producto: Gasolina
Compartimento: 2
Capacidad histórica: 4,000
Galones solicitados: 3,800
```
La asignación al pedido debe quedar almacenada de manera estructurada.

## 15. Compartimentos y order_details

La asignación de compartimentos debe estar relacionada con los detalles del pedido cuando corresponda al modelo de negocio.

Conceptualmente:
```
order_details
├── order_id
├── product_id
├── compartment_number
├── compartment_capacity
├── gallons
└── sale_price
```
Los nombres y tipos exactos deben adaptarse al esquema final.

El objetivo es que cada detalle pueda indicar qué compartimento utilizó y qué capacidad tenía en ese momento.

## 16. Snapshot de la capacidad del compartimento

Cuando se crea un pedido, la capacidad obtenida desde la configuración del vehículo debe copiarse al pedido cuando sea relevante para el historial.

Ejemplo:

Configuración actual:
```
Compartimento 1 → 5,000 gal
```

Pedido:
```
compartment_number = 1
compartment_capacity = 5000
gallons = 4800
```

Si posteriormente el vehículo cambia:
```
Compartimento 1 → 6,000 gal
```

el pedido histórico debe continuar mostrando:
```
Capacidad en el momento del pedido: 5,000 gal
```

No debe recalcularse retroactivamente desde la configuración actual del vehículo.

## 17. Los compartimentos no deben depender únicamente de JSON

No se debe implementar únicamente:
```
{
    "compartments": [
        {
            "number": 1,
            "capacity": 5000
        }
    ]
}
```
si esa información es necesaria para cálculos, reportes o validaciones estructuradas.

Los valores relevantes del pedido deben permanecer en columnas relacionales.

Un snapshot JSON puede utilizarse adicionalmente si se necesita conservar información adicional de la configuración.

## 18. Validación de compartimentos

Al seleccionar una cisterna, el backend debe validar que los compartimentos utilizados correspondan a la configuración disponible para ese vehículo en el momento de crear el pedido.

El frontend no debe considerarse una fuente confiable para esta validación.

El servidor debe verificar:
```
Vehículo
    ↓
Compartimento solicitado
    ↓
Existe en la configuración
    ↓
Capacidad válida
```
El backend debe realizar la validación definitiva.

## 19. Cambios posteriores del vehículo

Si la configuración del vehículo cambia después de crear un pedido:
```
ANTES
Compartimento 1 → 5,000

PEDIDO
Compartimento 1 → 5,000

DESPUÉS
Compartimento 1 → 6,000
```

El pedido no debe modificarse automáticamente.

El pedido conserva su información histórica.

## 20. Cambios posteriores de catálogos

El mismo principio se aplica a:

- Clientes.
- Asesores.
- Conductores.
- Vehículos.
- Plantas.
- Mayoristas.
- Productos.

Un cambio posterior en el catálogo no debe alterar automáticamente los valores históricos almacenados en el pedido cuando esos valores formen parte del snapshot.

## 21. Qué información debe incluir el snapshot

El snapshot debe incluir únicamente la información histórica necesaria para representar correctamente el pedido.

No se debe copiar indiscriminadamente toda la fila de cada tabla.

Por ejemplo, para un cliente puede ser suficiente:
```
{
    "id": 20,
    "name": "Empresa ABC SAC",
    "tax_id": "20123456789"
}
```
No es necesario duplicar automáticamente todos los campos del catálogo.

El contenido debe definirse según las necesidades reales de presentación, auditoría y operación.

## 22. El ID original debe conservarse

Cuando sea útil, el snapshot debe conservar el ID original de la entidad.

Ejemplo:
```
{
    "id": 20,
    "name": "Empresa ABC SAC"
}
```
Esto permite conocer tanto:
```
Entidad original → ID 20
```
como:
```
Información histórica → Empresa ABC SAC
```
La existencia del ID dentro del snapshot no reemplaza la FK relacional.

## 23. Edición del pedido

Debe distinguirse entre:
```
información actual del catálogo
```
y:
```
información histórica del pedido
```
Cuando un pedido sea editado, la aplicación debe definir explícitamente qué información puede actualizarse y cuándo debe actualizarse su snapshot.

No se debe actualizar automáticamente todo el snapshot únicamente porque cambió el catálogo.

Si el usuario cambia una entidad relacionada dentro del pedido, el sistema debe actualizar de forma consistente:
```
FK
+
snapshot correspondiente
```
cuando dicha información forme parte del historial del pedido.

## 24. Pedidos públicos

El formulario público debe utilizar los catálogos para facilitar la selección.

Ejemplo:
```
Cliente
   ↓
selección

Asesor
   ↓
selección

Cisterna
   ↓
autocompletado

Compartimentos
   ↓
carga automática

Detalles
   ↓
productos / galones / precios
```
Sin embargo, al confirmar el pedido, el backend debe construir y almacenar la información histórica necesaria.

No se debe confiar en los datos enviados por el frontend como snapshot definitivo.

## 25. Seguridad y multi-tenancy

Todos los catálogos y configuraciones utilizados por un pedido deben pertenecer al mismo tenant del pedido.

Ejemplo:
```
Tenant A
   ├── Vehículo A
   ├── Cliente A
   └── Pedido A
```

No debe ser posible utilizar:
```
Tenant B → vehículo
```

dentro de:
```
Tenant A → pedido
```
El backend debe validar explícitamente la pertenencia al tenant.

Esto aplica también al autocompletado del formulario público.

## 26. Integridad histórica

La información histórica de un pedido debe considerarse parte del documento.

El objetivo es que un pedido creado hoy pueda consultarse correctamente en el futuro aunque:

- Cambien los datos del cliente.
- Cambie el asesor.
- Cambie el conductor.
- Cambie la configuración de la cisterna.
- El vehículo quede inactivo.
- Cambien los datos de otros catálogos.

## 27. Consecuencias positivas

Esta decisión permite:

- Mantener integridad referencial.
- Realizar consultas eficientes.
- Generar reportes.
- Mantener información histórica.
- Evitar pérdida de datos cuando los catálogos cambian.
- Mantener flexibilidad mediante JSON cuando sea necesario.
- Facilitar el autocompletado de vehículos.
- Cargar automáticamente los compartimentos.
- Conservar la capacidad histórica de los compartimentos.
- Preparar la plataforma para crecimiento multi-tenant.

## 28. Consecuencias negativas

El modelo será ligeramente más complejo que almacenar todo como JSON.

Será necesario mantener:

- Relaciones.
- Datos históricos.
- Snapshots.
- Configuración de vehículos.
- Asignaciones de compartimentos.
- Reglas para sincronizar FK y snapshot cuando corresponda.

Sin embargo, esta complejidad se considera justificada debido al carácter histórico y operativo de los pedidos.

## 29. Reglas para OpenCode

Antes de modificar el esquema o generar código, OpenCode debe:

1. Revisar el esquema actual de orders.
2. Revisar order_details.
3. Revisar customers.
4. Revisar advisors.
5. Revisar drivers.
6. Revisar vehicles.
7. Revisar plants.
8. Revisar wholesalers.
9. Revisar products.
10. Revisar el formulario público existente.
11. Revisar el autocompletado existente o componentes reutilizables.
12. Revisar las relaciones existentes.
13. Reutilizar las estructuras existentes cuando sean compatibles.

- No debe reemplazar el modelo relacional por un JSON global.
- No debe eliminar las FK existentes únicamente para solucionar el problema histórico.
- No debe implementar snapshots duplicando indiscriminadamente todos los campos de cada catálogo.
- No debe eliminar físicamente catálogos que tengan pedidos históricos.
- No debe recalcular pedidos históricos utilizando la configuración actual del vehículo.
- No debe asumir que los datos enviados por React son confiables.
- La validación definitiva debe realizarse en Laravel.

## 30. Implementación de compartimentos

OpenCode debe diseñar la estructura de compartimentos respetando estas reglas:
```
Vehículo
    ↓
Configuración de compartimentos
    ↓
Formulario público
    ↓
Selección/autocompletado de vehículo
    ↓
Carga automática de compartimentos
    ↓
Usuario asigna productos
    ↓
Pedido
    ↓
Guardar asignación y capacidad histórica
```
La estructura exacta de la tabla vehicle_compartments y los campos adicionales debe definirse revisando primero el esquema existente.

No crear una estructura duplicada si ya existe una equivalente.

## 31. Resultado esperado

El sistema debe permitir:

Catálogo
```
Cisterna ABC-123

Compartimento 1 → 5,000
Compartimento 2 → 4,000
Compartimento 3 → 3,000
```

Formulario público

```
Cisterna: ABC-123

Compartimentos cargados automáticamente:

[1] 5,000 gal
[2] 4,000 gal
[3] 3,000 gal
```

Pedido creado
```
PED-000125

Cisterna: ABC-123

Detalle:
Producto: Diesel
Compartimento: 1
Capacidad: 5,000
Galones: 4,800
```

Cambio posterior

La cisterna pasa a:
```
Compartimento 1 → 6,000
```
El pedido histórico continúa mostrando:
```
Compartimento: 1
Capacidad histórica: 5,000
Galones: 4,800
```
## 32. Decisión final

La plataforma utilizará un modelo híbrido:
```
RELACIONAL
    ↓
Para identidad, relaciones, consultas, cálculos y reportes.

SNAPSHOT
    ↓
Para conservar información histórica relevante.

JSON
    ↓
Para información complementaria o flexible,
sin reemplazar el modelo relacional.

CONFIGURACIÓN DE VEHÍCULO
    ↓
Para definir los compartimentos disponibles.

PEDIDO
    ↓
Para conservar la asignación histórica
de compartimentos y capacidades.
```
La prioridad es que un pedido represente fielmente lo ocurrido en el momento en que fue registrado, independientemente de los cambios posteriores realizados en los catálogos.
