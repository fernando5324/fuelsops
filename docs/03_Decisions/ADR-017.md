# ADR-017: Implementación de página "Avance de ventas"

## 1. Objetivo

Crear una nueva página administrativa llamada "Avance de ventas" para consultar el comportamiento de los pedidos dentro de un período determinado.

La página debe permitir visualizar de forma clara y ejecutiva:

* Total de galones.
* Compras totales.
* Ventas totales.
* Margen total.
* Evolución diaria de compras, ventas y margen.
* Distribución de galones por producto.
* Detalle diario de las operaciones.

La página estará orientada principalmente a gerentes y evaluadores, por lo que debe priorizar una presentación visual limpia, profesional, clara y fácil de interpretar.

La visualización de gráficos debe realizarse utilizando Apache ECharts.

---

# 2. Arquitectura existente

Mantener la arquitectura actual del proyecto:

* Backend: Laravel.
* Frontend: React.
* Comunicación: Inertia.
* Componentes de interfaz: Ant Design.
* Gráficos: Apache ECharts.
* Base de datos: MySQL.

No introducir otro framework de gráficos.

No cambiar la arquitectura existente del proyecto.

Laravel debe encargarse de realizar las consultas, agrupaciones y cálculos de negocio.

React debe encargarse principalmente de presentar la información y controlar la interacción de la interfaz.

ECharts debe encargarse exclusivamente de la visualización de los gráficos.

---

# 3. Nombre de la página

Nombre visible:

"Avance de ventas"

Descripción:

"Resumen de ventas y márgenes por período"

La página debe integrarse siguiendo las convenciones actuales del proyecto para rutas, controladores, servicios, componentes React y permisos.

Antes de crear nuevas estructuras, revisar cómo están implementadas las páginas existentes y seguir sus convenciones.

---

La página debe seguir esta estructura general:

```text
┌─────────────────────────────────────────────────────────────┐
│ Avance de ventas                                            │
│ Resumen de ventas y márgenes por período                   │
│                                                             │
│ [ Mes / período ] [Desde] [Hasta] [Filtrar]                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 🛢 Total galones       🛒 Compras        💰 Ventas         📈 Margen │
│    125,450              S/ 580,200       S/ 625,800        S/45,600 │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ Evolución de ventas y margen                                │
│                                                             │
│                Gráfico Apache ECharts                       │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ Galones por producto                                        │
│                                                             │

├─────────────────────────────────────────────────────────────┤

│       |               |         |        |        |         │
└─────────────────────────────────────────────────────────────┘
```

El diseño real no debe copiar literalmente el esquema ASCII. Utilizar Ant Design para conseguir una interfaz moderna, limpia y profesional.

---

# 5. Filtros

La página debe permitir consultar información por período.

Debe soportar:

1. Selección de mes.
2. Rango de fechas.

La interfaz puede utilizar componentes de Ant Design como DatePicker, RangePicker o Select, según las convenciones existentes del proyecto.

La lógica debe permitir seleccionar un mes completo o establecer explícitamente:

* Fecha desde.
* Fecha hasta.

Debe existir una acción clara para aplicar/consultar los filtros.

Al cambiar el período, todos los componentes dependientes deben actualizarse:

* Cards.
* Gráfico de evolución.
* Gráfico de galones por producto.
* Tabla de resumen diario.

No realizar múltiples consultas independientes innecesarias si la información puede obtenerse mediante una única respuesta estructurada del backend.

---

# 6. Cards de resumen

Mostrar cuatro cards principales:

## Total galones

Representa la suma total de galones de los pedidos del período seleccionado.

Mostrar icono relacionado con combustible/galones.

Ejemplo:

"125,450 gal"

---

## Compras totales

Representa el costo total de los pedidos dentro del período.

Ejemplo:

"S/ 580,200.00"

---

## Ventas totales

Representa el valor total de venta de los pedidos dentro del período.

Ejemplo:

"S/ 625,800.00"

---

## Margen total

Representa:

Ventas totales - Compras totales

Ejemplo:

"S/ 45,600.00"

Utilizar iconografía apropiada y discreta.

Los iconos deben mejorar la lectura, no saturar visualmente la página.

Mantener una apariencia profesional orientada a dashboard administrativo.

---

# 7. Gráfico "Evolución de ventas y margen"

Utilizar Apache ECharts.

El gráfico debe representar la evolución diaria dentro del período seleccionado.

Debe mostrar como mínimo:

* Compras.
* Ventas.
* Margen.

Se recomienda utilizar un gráfico combinado para facilitar la comparación.

Propuesta:

* Ventas: línea.
* Compras: línea.
* Margen: barras.

El eje X debe representar las fechas que realmente tengan pedidos.

No mostrar días sin pedidos.

Ejemplo:

```text
01/09
02/09
04/09
07/09
09/09
```

Si no existen pedidos el día 03/09, no debe aparecer como una fecha de datos en la serie.

El tooltip debe mostrar información clara al pasar sobre cada fecha:

* Fecha.
* Compras.
* Ventas.
* Margen.

Utilizar formato monetario apropiado para soles.

El gráfico debe ser responsive.

---

# 8. Gráfico "Galones por producto"

Agregar un segundo gráfico utilizando Apache ECharts.

Tipo:

Pie / Donut chart.

Título:

"Galones por producto"

El objetivo es mostrar qué proporción del total de galones corresponde a cada producto dentro del período seleccionado.

Ejemplo conceptual:

```text
             Galones por producto

                 ┌───────────┐
             ┌───┤           │
          ┌──┘   │    Pie    │
          │      │           │
          └──────┴───────────┘

       Producto A   45%
       Producto B   30%
       Producto C   15%
       Producto D   10%
```

El gráfico debe utilizar como valor:

Total de galones agrupado por producto.

No utilizar ventas ni margen para este gráfico.

---

# 9. Interacción del gráfico Pie

El gráfico debe permitir seleccionar/deseleccionar productos.

El usuario debe poder ocultar un producto del gráfico para comparar visualmente los demás.

Ejemplo:

```text
Producto A ✓
Producto B ✓
Producto C ✓
Producto D ✓
```

Si el usuario desactiva Producto B:

```text
Producto A ✓
Producto B ✕
Producto C ✓
Producto D ✓
```

Producto B debe dejar de mostrarse visualmente en el Pie.

La interacción debe utilizar las capacidades nativas de Apache ECharts siempre que sea posible, especialmente su legend selection.

No crear una implementación manual compleja si ECharts ya proporciona el comportamiento necesario.

El usuario debe poder volver a activar el producto.

La selección/deselección del gráfico es solamente visual.

No debe modificar los datos originales ni realizar una nueva consulta al backend.

---

# 10. Comportamiento del gráfico Pie

El gráfico debe mostrar:

* Nombre del producto.
* Cantidad de galones.
* Porcentaje correspondiente.

El tooltip debe mostrar información clara, por ejemplo:

```text
Producto: Diésel
Galones: 25,450
Participación: 35.4%
```

Los porcentajes deben calcularse sobre el total de galones correspondiente al conjunto actualmente visible/seleccionado, si esto es compatible con el comportamiento natural de ECharts.

No modificar los valores originales recibidos desde Laravel.

---

# 11. Tabla "Resumen por día"

Debajo de los gráficos debe existir una tabla con el título:

"Resumen por día"

Columnas:

1. Fecha.
2. Total Galones.
3. Compras S/.
4. Ventas S/.
5. Margen S/.
6. Margen S/ por galón.

Ejemplo:

```text
Fecha       Total Galones   Compras S/   Ventas S/   Margen S/   Margen S/ galón
01/09/26        12,500       58,000       62,000       4,000          0.32
02/09/26         9,800       45,200       48,300       3,100          0.32
04/09/26        15,200       70,100       75,000       4,900          0.32
```

No mostrar días que no tengan pedidos.

La tabla debe utilizar el componente Table de Ant Design si es consistente con el resto del proyecto.

Debe permitir scroll horizontal si el ancho de pantalla lo requiere.

---

# 12. Cálculo de margen

El margen de cada día se calcula como:

```text
Margen S/ = Ventas S/ - Compras S/
```

El margen por galón se calcula como:

```text
Margen S/ por galón = Margen S/ / Total Galones
```

Mostrar máximo 2 decimales para el margen por galón.

Ejemplo:

```text
Margen = S/ 4,000
Galones = 12,500

4,000 / 12,500 = 0.32
```

---

# 13. Cálculo de totales

Los cards superiores deben representar los totales del período seleccionado.

```text
Total galones = suma de galones de todos los días

Compras totales = suma de compras de todos los días

Ventas totales = suma de ventas de todos los días

Margen total = Ventas totales - Compras totales
```

Para el margen por galón total de la tabla, NO calcular un promedio simple de los márgenes por galón diarios.

Debe calcularse:

```text
Margen total / Total galones
```

Ejemplo:

```text
Margen total = S/ 12,000
Total galones = 37,500

12,000 / 37,500 = 0.32
```

Mostrar máximo 2 decimales.

---

# 14. Fuente de los datos

Utilizar los pedidos existentes del sistema.

No duplicar información de pedidos en nuevas tablas únicamente para generar este dashboard.

La información debe calcularse a partir de los datos existentes.

Revisar las relaciones actuales de:

* orders
* order_details
* products
* y cualquier otra tabla necesaria para determinar compras, ventas, galones y producto.

Antes de implementar, revisar la estructura real de la base de datos y utilizar los nombres existentes.

No asumir nombres de columnas que no existan.

---

# 15. Backend

Laravel debe realizar:

* Validación de filtros.
* Consulta de pedidos.
* Agrupación por fecha.
* Agrupación por producto.
* Cálculo de compras.
* Cálculo de ventas.
* Cálculo de margen.
* Cálculo de galones.
* Cálculo del margen por galón.

El backend debe devolver una estructura organizada para que React no tenga que reconstruir la lógica de negocio.

Estructura conceptual esperada:

```json
{
    "filters": {
        "from": "2026-09-01",
        "to": "2026-09-30"
    },
    "summary": {
        "total_gallons": 37500,
        "total_purchases": 173300,
        "total_sales": 185300,
        "total_margin": 12000,
        "margin_per_gallon": 0.32
    },
    "daily": [
        {
            "date": "2026-09-01",
            "total_gallons": 12500,
            "purchases": 58000,
            "sales": 62000,
            "margin": 4000,
            "margin_per_gallon": 0.32
        }
    ],
    "products": [
        {
            "id": 1,
            "name": "Producto A",
            "total_gallons": 15000
        },
        {
            "id": 2,
            "name": "Producto B",
            "total_gallons": 12000
        }
    ]
}
```

Esta estructura es conceptual.

Adaptarla a las convenciones y nombres reales del proyecto.

# 16. Responsabilidad de React

React debe:

* Mostrar los filtros.
* Mostrar los cards.
* Mostrar la tabla.
* Construir las opciones de ECharts.
* Controlar la selección visual del Pie.
* Mostrar estados de carga.
* Mostrar estado sin resultados.

Evitar duplicar cálculos de negocio en React.

Los cálculos financieros y de cantidades deben permanecer en Laravel.

---

# 17. Estado sin resultados

Si el período seleccionado no tiene pedidos:

No mostrar gráficos vacíos de forma confusa.

Mostrar un estado visual claro:

"Sin información para el período seleccionado"

Los cards deben mostrar valores en cero.

La tabla debe mostrar el estado vacío correspondiente.

El gráfico Pie tampoco debe intentar mostrar datos inexistentes.

---

# 18. Diseño visual

La página debe sentirse como un dashboard administrativo y no como una pantalla técnica.

Utilizar:

* Cards de Ant Design.
* Espaciado consistente.
* Tipografía clara.
* Iconos apropiados.
* Bordes y sombras sutiles.
* Gráficos con buena separación visual.
* Responsive design.

No saturar la interfaz con colores.

Los colores utilizados en ECharts deben mantener coherencia visual con el sistema actual.

No introducir una paleta completamente diferente al resto del proyecto.

Priorizar:

* legibilidad;
* contraste;
* jerarquía visual;
* facilidad de interpretación.

La información más importante debe poder entenderse rápidamente sin leer toda la tabla.

---

# 19. Responsive

La página debe funcionar correctamente en diferentes tamaños de pantalla.

En escritorio:

```text
[ Card ] [ Card ] [ Card ] [ Card ]

[        Evolución de ventas        ]

[       Galones por producto        ]

[          Resumen por día          ]
```

En pantallas más pequeñas:

```text
[ Card ]
[ Card ]
[ Card ]
[ Card ]

[ Evolución ]

[ Galones por producto ]

[ Tabla con scroll ]
```

No eliminar información importante solamente para adaptar el diseño.

---

# 20. Rendimiento

Evitar consultas innecesarias.

La información del dashboard debe obtenerse de manera eficiente.

No realizar una consulta al backend por cada gráfico.

Preferiblemente realizar una consulta/controlador que devuelva la información estructurada necesaria para:

* resumen;
* evolución diaria;
* productos.

Si el proyecto ya tiene una capa Service para este tipo de lógica, utilizarla siguiendo las convenciones existentes.

No crear múltiples Action classes si el proyecto no utiliza ese patrón.

---

# 21. Reglas importantes para la implementación

Antes de modificar archivos:

1. Revisar cómo están construidas las páginas administrativas actuales.
2. Revisar las rutas existentes.
3. Revisar la estructura de controladores/services.
4. Revisar cómo se manejan los filtros mediante Inertia.
5. Revisar cómo se importan y utilizan componentes React.
6. Revisar si Apache ECharts ya está instalado.
7. Si no está instalado, instalar únicamente la dependencia necesaria para React + ECharts siguiendo la versión y convenciones actuales del proyecto.
8. Revisar las tablas reales antes de construir las consultas.

No modificar módulos existentes que no sean necesarios para esta funcionalidad.

No cambiar la estructura de base de datos salvo que sea estrictamente necesario.

No crear tablas nuevas para almacenar estadísticas que pueden calcularse a partir de los pedidos existentes.

---

# 22. Resultado esperado

La página final debe permitir que un usuario:

1. Ingrese a "Avance de ventas".
2. Seleccione un mes o rango de fechas.
3. Consulte los totales generales.
4. Observe la evolución diaria de compras, ventas y margen.
5. Observe cómo se distribuyen los galones entre productos.
6. Active o desactive productos en el gráfico Pie para compararlos visualmente.
7. Revise el detalle diario en la tabla "Resumen por día".

La experiencia debe ser clara para un gerente o evaluador que no necesariamente conoce la estructura interna del sistema.

El resultado debe priorizar una presentación ejecutiva, profesional y fácil de interpretar.

---

# 23. Restricciones

No implementar:

* Nuevos módulos de estadísticas no solicitados.
* Gráficos adicionales no solicitados.
* Nuevas tablas de estadísticas.
* Exportaciones Excel/PDF en esta primera versión.
* Comparaciones entre períodos.
* Filtros por producto, proveedor o ubicación, salvo que sean necesarios para el funcionamiento solicitado.
* Lógica financiera duplicada en React.
* Datos ficticios en producción.

El objetivo de esta implementación es exclusivamente construir la página "Avance de ventas" con:

* Filtros por período.
* Cards de resumen.
* Gráfico de evolución.
* Gráfico Pie de galones por producto.
* Selección/deselección de productos en el Pie.
* Tabla "Resumen por día".

---

# 24. Criterio de aceptación

La funcionalidad se considera terminada cuando:

* La página "Avance de ventas" existe y es accesible desde el panel.
* Los filtros por mes/rango de fechas funcionan.
* Los datos corresponden realmente a los pedidos existentes.
* Los días sin pedidos no aparecen.
* Los cuatro cards muestran correctamente los totales.
* El gráfico de evolución representa compras, ventas y margen.
* El gráfico Pie representa galones por producto.
* Es posible activar/desactivar productos desde el Pie.
* La tabla "Resumen por día" muestra los datos diarios.
* El margen por galón se calcula correctamente.
* Los totales financieros coinciden entre cards, gráfico y tabla.
* La página funciona correctamente en escritorio y pantallas pequeñas.
* No se han introducido cambios innecesarios en módulos existentes.
* No existen datos ficticios.
* No quedan errores de consola ni errores de backend relacionados con esta funcionalidad.
