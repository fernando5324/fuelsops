# ADR-010: Modelo de precios, importación de Excel y cálculo de precios

- **Estado:** Propuesto
- **Fecha:** 2026-09-24
- **Proyecto:** Sertoco
- **Área:** Precios / Productos / Importación
- **Relacionado con:** ADR-001 - Modelo inicial de pedidos y archivos
- **Decisión:** Normalizar la información del Excel y separar datos fuente, configuración, importaciones y resultados históricos.

---

## 1. Contexto

Sertoco actualmente utiliza un formulario público donde se seleccionan, entre otros datos:

- Planta
- Mayorista
- Producto

Estos catálogos ya existen en la base de datos mediante las tablas:

- `plants`
- `wholesalers`
- `products`

Se ha identificado un archivo Excel utilizado para administrar precios de productos según una determinada planta y los precios ofrecidos por distintos mayoristas.

La estructura actual del Excel es:

### Columnas A-B

- Columna A: Planta / ubicación
- Columna B: Producto

### Columnas C-M

Cada columna representa un mayorista y contiene el precio correspondiente para el producto de una determinada planta.

Ejemplo conceptual:

| Planta | Producto | PRIMAX | Hidromundo | Petroperú |
|---|---|---:|---:|---:|
| Callao | Diesel DB S50 | 23.3347 | 22.7623 | — |

### Columnas N-V

Son valores derivados mediante fórmulas:

- N: mejor precio
- O: mejor mayorista
- P: precio redondeado
- Q: precio de compra
- R: margen Sertoco
- S: precio de venta
- T: precio de venta con IGV
- U: precio de venta con percepción
- V: precio final

Las fórmulas actuales son:

```
N = MIN(C:M)

O = SI.ERROR(
        INDICE(C1:M1,
        COINCIDIR(MIN(C3:M3),C3:M3,0)
    ),
    ""
)

P = REDONDEAR(N,4)

Q = P / 1.18

R = 0.13

S = Q + R

T = S * 1.18

U = T * 1.01

V = U
```

El Excel debe considerarse únicamente como una fuente de importación.

El sistema no debe depender de las fórmulas existentes en el Excel para obtener el precio final.

## 2. Problema

No es conveniente trasladar literalmente la estructura del Excel a la base de datos.

Por ejemplo, no se debe crear una tabla con columnas como:
```
pluspetrol_price
primax_price
petroperu_price
hidromundo_price
terpel_price
...
```
Esto generaría problemas cuando:

- aparezca un nuevo mayorista;
- se elimine un mayorista;
- un producto no esté disponible en una planta;
- cambien los precios;
- se agreguen nuevas plantas;
- cambien las reglas de cálculo;
- sea necesario consultar el historial;
- se necesite auditar una importación.

Además, las tablas plants, wholesalers y products ya son utilizadas por otras partes de Sertoco, especialmente por el formulario público.

No deben crearse catálogos paralelos para el módulo de precios.

## 3. Decisión

Se utilizarán los catálogos existentes:
```
plants
wholesalers
products
```
y se crearán tablas adicionales para representar:
```
Planta + Producto
        ↓
Precios por Mayorista
        ↓
Motor de cálculo
        ↓
Resultado
        ↓
Historial / Snapshot
```
Las nuevas tablas principales serán:
```
plant_products
wholesaler_prices
price_import_batches
price_import_items
pricing_configurations
price_calculations
```
El Excel será tratado como una fuente de entrada y no como el modelo de datos del sistema.

## 4. Objetivos

La implementación debe permitir:

1. Importar precios desde Excel.
2. Detectar nuevos productos.
3. Detectar nuevas plantas.
4. Detectar nuevos mayoristas.
5. Detectar nuevos precios.
6. Detectar precios modificados.
7. Detectar precios sin cambios.
8. Detectar registros con errores.
9. No depender de las columnas N-V del Excel para realizar cálculos.
10. Calcular automáticamente el precio usando el motor de cálculo del sistema.
11. Guardar el resultado del cálculo.
12. Mantener un historial de los valores utilizados para cada cálculo.
13. Permitir que posteriormente cambien parámetros como margen, IGV o percepción sin alterar los cálculos históricos.
14. Mantener compatibilidad con el formulario público existente.
15. Permitir agregar nuevos mayoristas sin modificar la estructura de la base de datos.
16. Permitir que diferentes tenants tengan sus propios catálogos y precios.


## 5. Conceptos del dominio

Para evitar confusiones entre el Excel y el sistema:

| Excel                              | Sistema                              |
| ---------------------------------- | ------------------------------------ |
| Agrupación / ubicación             | `plants`                             |
| Planta                             | `plants`                             |
| Mayorista                          | `wholesalers`                        |
| Proveedor                          | Se representa mediante `wholesalers` |
| Producto                           | `products`                           |
| Precio de mayorista                | `wholesaler_prices`                  |
| Relación Planta + Producto         | `plant_products`                     |
| Importación Excel                  | `price_import_batches`               |
| Registro individual de importación | `price_import_items`                 |
| Parámetros del cálculo             | `pricing_configurations`             |
| Resultado histórico                | `price_calculations`                 |


Para la interfaz futura se puede utilizar una terminología más general como "Ubicación" en lugar de "Planta" si se desea reutilizar Sertoco para entidades similares.

Internamente se mantienen los nombres actuales de las tablas.

## 6. Tablas existentes

Ya existen las siguientes tablas:
```
plants
wholesalers
products
```
Estas tablas NO deben duplicarse.

El nuevo módulo debe reutilizar directamente estos catálogos.

Todas ellas ya utilizan:
```
tenant_id
created_by
updated_by
created_at
updated_at
is_active
```
Las nuevas tablas deberán mantener las convenciones existentes de Sertoco y utilizar tenant_id para aislar los datos entre tenants.

## 7. Nueva tabla: plant_products
Propósito

Representar qué productos están disponibles en cada planta.

No se debe asumir que todos los productos existen en todas las plantas.

Ejemplo:
```
Callao
    Diesel DB S50
    Diesel DB S50 UV
    Gasohol Regular
    Gasohol Premium

Monte Azul
    Diesel DB S50
    Diesel DB S50 UV
```

Estructura propuesta
```
CREATE TABLE IF NOT EXISTS plant_products (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    tenant_id BIGINT UNSIGNED NOT NULL,

    plant_id BIGINT UNSIGNED NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,

    is_active BOOLEAN NOT NULL DEFAULT TRUE,

    created_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NULL DEFAULT NULL,

    created_by BIGINT UNSIGNED NOT NULL,
    updated_by BIGINT UNSIGNED NULL,

    UNIQUE KEY uq_plant_products_tenant_plant_product (
        tenant_id,
        plant_id,
        product_id
    ),

    INDEX idx_plant_products_tenant (tenant_id),
    INDEX idx_plant_products_plant (plant_id),
    INDEX idx_plant_products_product (product_id),
    INDEX idx_plant_products_active (is_active),

    CONSTRAINT fk_plant_products_tenant
        FOREIGN KEY (tenant_id)
        REFERENCES tenants (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_plant_products_plant
        FOREIGN KEY (plant_id)
        REFERENCES plants (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_plant_products_product
        FOREIGN KEY (product_id)
        REFERENCES products (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_plant_products_created_by
        FOREIGN KEY (created_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_plant_products_updated_by
        FOREIGN KEY (updated_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
) ENGINE=InnoDB;
```
OpenCode debe adaptar la implementación final a las convenciones reales de las tablas existentes antes de ejecutar el DDL.

## 8. Nueva tabla: wholesaler_prices
Propósito

Almacenar el precio que un determinado mayorista ofrece para un determinado producto en una determinada planta.

No se deben crear columnas por mayorista.

Ejemplo:
```
Callao
Diesel DB S50

PRIMAX       23.3347
Hidromundo   22.7623
Petroperú    23.0000
```
Debe representarse como registros independientes.

Estructura propuesta
```
CREATE TABLE IF NOT EXISTS wholesaler_prices (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    tenant_id BIGINT UNSIGNED NOT NULL,

    plant_product_id BIGINT UNSIGNED NOT NULL,
    wholesaler_id BIGINT UNSIGNED NOT NULL,

    price DECIMAL(12,4) NULL,

    import_batch_id BIGINT UNSIGNED NULL,

    created_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NULL DEFAULT NULL,

    created_by BIGINT UNSIGNED NOT NULL,
    updated_by BIGINT UNSIGNED NULL,

    UNIQUE KEY uq_wholesaler_prices_relation (
        tenant_id,
        plant_product_id,
        wholesaler_id
    ),

    INDEX idx_wholesaler_prices_tenant (tenant_id),
    INDEX idx_wholesaler_prices_plant_product (plant_product_id),
    INDEX idx_wholesaler_prices_wholesaler (wholesaler_id),
    INDEX idx_wholesaler_prices_import_batch (import_batch_id),

    CONSTRAINT fk_wholesaler_prices_tenant
        FOREIGN KEY (tenant_id)
        REFERENCES tenants (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_wholesaler_prices_plant_product
        FOREIGN KEY (plant_product_id)
        REFERENCES plant_products (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_wholesaler_prices_wholesaler
        FOREIGN KEY (wholesaler_id)
        REFERENCES wholesalers (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_wholesaler_prices_created_by
        FOREIGN KEY (created_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,

    CONSTRAINT fk_wholesaler_prices_updated_by
        FOREIGN KEY (updated_by)
        REFERENCES users (id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
) ENGINE=InnoDB;

```
Consideraciones

Un precio ausente en Excel NO debe convertirse automáticamente en 0.

Debe diferenciarse entre:

- sin precio registrado

y:
```
precio = 0
```

Para el cálculo del mínimo solamente deben considerarse precios válidos.

Propósito

Registrar el resultado de cada registro procesado durante una importación.

Esta tabla es importante porque price_import_batches por sí sola no permite saber qué ocurrió con cada fila.

Debe permitir identificar:
```
nuevo
actualizado
sin cambios
error
```
También debe conservar información suficiente para mostrar al usuario un resumen de la importación antes de confirmarla o para consultar posteriormente el resultado.

Estructura conceptual

```
price_import_items

tenant_id
import_batch_id

row_number

plant_name
product_name
wholesaler_name

previous_price
new_price

status

error_message

created_at
updated_at
```
Estados sugeridos:
```
new
updated
unchanged
error
```
Si posteriormente se necesita procesar una importación en modo "preview", esta tabla debe permitir almacenar el resultado de la validación sin modificar todavía las tablas definitivas.

## 11. Nueva tabla: pricing_configurations
Propósito

Guardar los parámetros utilizados por el motor de cálculo.

Actualmente:
```
Margen = 0.13
IGV = 18%
Percepción = 1%
```
El margen actualmente no necesita ser editable desde la interfaz, pero debe almacenarse en base de datos y no quedar como un valor mágico dentro del código.

Estructura propuesta
```
pricing_configurations

id
tenant_id

name

margin
igv_rate
perception_rate

is_active

effective_from
effective_until

created_at
updated_at

created_by
updated_by
```
Ejemplo:
```
name = "Configuración estándar"

margin = 0.1300
igv_rate = 0.1800
perception_rate = 0.0100
```
Los porcentajes deben almacenarse como valores decimales:
```
0.13
0.18
0.01
```
No como:
```
13
18
1
```
La configuración deberá poder versionarse posteriormente mediante fechas de vigencia.

No es necesario desarrollar todavía una interfaz administrativa para modificar estos valores, salvo que el alcance actual lo requiera.

Nota de implementación (26-09-2026): el **margen dejó de ser un parámetro
global del motor** y pasó a ser un dato de cada relación
`plant_products.margin` (§35). `pricing_configurations.margin` se conserva
únicamente como **valor por defecto** para las relaciones nuevas (la UI lo
propone en el modal "Nueva relación" y la importación puede aplicarlo), mientras
que `igv_rate` y `perception_rate` **siguen siendo globales** para todos los
cálculos. El default físico de la columna es `0.1300` (`SEEDS.sql` siembra la
configuración con el mismo valor).

## 12. Nueva tabla: price_calculations
Propósito

Registrar el resultado de un cálculo de precios.

Esta tabla NO debe ser utilizada solamente como una tabla de resultados actuales.

Su función principal es mantener un historial de cómo se obtuvo un determinado precio.

Esto es importante porque posteriormente pueden cambiar:

- precio del mayorista;
- margen;
- IGV;
- percepción;
- reglas de cálculo;
- proveedor ganador.

El registro histórico debe seguir mostrando los valores utilizados en el momento del cálculo.

## 13. Uso del JSON en price_calculations

El JSON se utilizará como un snapshot histórico del cálculo.

No será la fuente principal para consultar los datos actuales.

La información actual continuará estando normalizada en:
```
plants
products
wholesalers
plant_products
wholesaler_prices
pricing_configurations
```
Mientras que price_calculations conservará una fotografía de los valores utilizados en un determinado cálculo.

Ejemplo conceptual:
```
{
    "version": "1.0",

    "source": {
        "plant_id": 1,
        "product_id": 1,
        "wholesaler_id": 4,
        "wholesaler_price_id": 25
    },

    "inputs": {
        "best_supplier_price": 22.7623,
        "margin": 0.13,
        "igv_rate": 0.18,
        "perception_rate": 0.01
    },

    "results": {
        "best_price": 22.7623,
        "rounded_price": 22.7623,
        "purchase_price": 19.2901,
        "margin": 0.13,
        "sale_price": 19.4201,
        "sale_price_with_igv": 22.9157,
        "sale_price_with_perception": 23.1449,
        "final_price": 23.1449
    }
}
```
Este JSON debe representar los valores reales utilizados en ese momento.

No debe construirse dinámicamente al consultar el historial.

## 14. Propósito del snapshot histórico

Ejemplo:

El 24/09/2026:
```
Precio Hidromundo = 22.7623
Margen = 0.13
IGV = 0.18
Percepción = 0.01
Precio final = 23.1449
```
Posteriormente el precio cambia:
```
Precio Hidromundo = 23.1000
```
El cálculo anterior debe seguir mostrando:
```
Precio Hidromundo = 22.7623
Precio final = 23.1449
```
Aunque la tabla wholesaler_prices ahora contenga:
```
23.1000
```
De igual forma, si posteriormente cambia:
```
margin = 0.15
```
el cálculo histórico anterior debe seguir conservando:
```
margin = 0.13
```
Por esta razón, el JSON funciona como snapshot y no como fuente dinámica.

## 15. Estructura propuesta de price_calculations

Conceptualmente:
```
price_calculations

id
tenant_id

plant_product_id

wholesaler_price_id
pricing_configuration_id

calculation_version

calculation_data JSON

calculated_at

created_at
created_by
```
No es necesario duplicar dentro de las columnas relacionales todos los resultados del JSON.

El objetivo de las columnas relacionales es permitir identificar el contexto del cálculo.

El JSON conserva los valores históricos utilizados y los resultados.

## 16. Motor de cálculo

El sistema debe implementar un motor de cálculo propio.

El Excel NO será la fuente de verdad para las columnas N-V.

El motor deberá:

Paso 1: obtener precios válidos

Para un:

- plant_product

buscar sus:

- wholesaler_prices

ignorando registros sin precio válido.

Paso 2: obtener el menor precio

Equivalente a:
```
N = MIN(C:M)
```
Resultado:
```
best_price
```
Paso 3: obtener el mayorista ganador

Equivalente a:
```
O = proveedor correspondiente al menor precio
```

Debe conservarse también el wholesaler_id.

Si existen varios mayoristas con exactamente el mismo precio mínimo, se debe definir una regla determinística.

Inicialmente puede utilizarse el primer registro según un orden estable, por ejemplo:
```
wholesaler_id ASC
```
No se debe dejar el resultado a un orden no determinístico de la base de datos.

Paso 4: redondear

Equivalente a:
```
P = ROUND(N, 4)
```
Paso 5: precio de compra

Equivalente a:
```
Q = P / 1.18
```
Pero el factor debe derivarse de la configuración de IGV:
```
Q = P / (1 + igv_rate)
```
Con:
```
igv_rate = 0.18
```
Paso 6: margen

Actualmente:
```
R = 0.13
```
Debe obtenerse desde:
```
pricing_configurations.margin
```

Paso 7: precio de venta
```
S = Q + margin
```
Paso 8: precio de venta con IGV
```
T = S * (1 + igv_rate)
```
Paso 9: percepción

Actualmente:
```
U = T * 1.01
```
Debe derivarse de:
```
U = T * (1 + perception_rate)
```
Paso 10: precio final

Actualmente:
```
V = U
```
Por el momento:
```
final_price = sale_price_with_perception
```
Debe mantenerse como una etapa independiente del cálculo porque posteriormente podría cambiar la definición de "precio final".

## 17. Columnas N-V del Excel

Las columnas N-V pueden seguir leyéndose durante la importación como valores de referencia.

Sin embargo:
```
N-V NO serán la fuente de verdad.
```
Durante la importación inicial se recomienda comparar:
```
valor Excel
vs.
valor calculado por Sertoco
```
Ejemplo:
```
Excel:
N = 22.7623

Sistema:
best_price = 22.7623

Resultado:
MATCH
```
Esto permitirá validar que el motor de cálculo reproduce correctamente la lógica existente.

Si existe una diferencia:
```
Excel = 23.1449
Sistema = 23.2000
```
la importación debe poder identificarla.

No se debe sobrescribir silenciosamente el resultado calculado por el sistema utilizando el valor del Excel.

Nota de implementación (26-09-2026): la columna **R (`MARGEN SERTOCO`) sí es
fuente de verdad** y es la excepción a la regla de este §17. El margen pertenece
a la **relación planta+producto** (no a la fila del mayorista), así que la
importación lo escribe en `plant_products.margin` y el motor lo usa en el paso
`S = Q + margin` (§35). El resto de columnas derivadas (N-V) siguen siendo solo
referencia para comparar.

## 18. Flujo de importación

La importación deberá plantearse en etapas.
```
Seleccionar Excel
       ↓
Leer archivo
       ↓
Validar estructura
       ↓
Detectar encabezados
       ↓
Procesar filas
       ↓
Identificar Planta
       ↓
Identificar Producto
       ↓
Identificar Mayoristas
       ↓
Comparar precios existentes
       ↓
Generar Preview
       ↓
Mostrar cambios
       ↓
Confirmar importación
       ↓
Actualizar base de datos
       ↓
Ejecutar cálculos
       ↓
Guardar snapshots
```
No debe modificarse inmediatamente la información definitiva al seleccionar/subir el archivo.

## 19. Detección de nuevos registros

Si aparece una planta que no existe:
```
Nueva planta:
Pisco
```
el sistema debe poder identificarla.

Lo mismo para:
```
Nuevo producto
```
o:
```
Nuevo mayorista
```

La primera versión puede requerir que el usuario confirme la creación de estos catálogos durante el proceso de importación.

No se debe crear automáticamente un registro definitivo sin que exista una política clara para evitar errores tipográficos.

Ejemplo:
```
PRIMAX
PRIMAX S.A.
PRIMAXSA
```
podrían ser el mismo mayorista, por lo que la importación debe evitar asumir que cualquier nombre nuevo representa automáticamente una entidad distinta.

## 20. Detección de precios modificados

Ejemplo:

Precio actual:
```
Hidromundo = 22.7623
```
Excel:
```
Hidromundo = 23.1000
```
Debe detectarse:
```
previous_price = 22.7623
new_price = 23.1000
status = updated
```
El usuario debe poder visualizar esta diferencia antes de confirmar.

## 21. Registros sin cambios

Si:
```
precio actual = 22.7623
precio Excel = 22.7623
```
el registro debe marcarse:
```
unchanged
```
No debe generarse innecesariamente una modificación.

Dependiendo de la implementación, tampoco es necesario generar un nuevo cálculo histórico si los datos y parámetros utilizados son exactamente iguales y no existe una razón funcional para registrar otro cálculo.

## 22. Registro de la importación

Ejemplo:
```

precios_24_09_2026.xlsx

128

Nuevos:
8

Actualizados:
27

84
```

- price_import_items

## 23. Manejo de errores

Errores posibles:

- Planta inexistente.
- Producto inexistente.
- Mayorista inexistente.
- Precio inválido.
- Precio negativo.
- Fila vacía.
- Encabezados inválidos.
- Producto sin planta.
- Excel con estructura incompatible.
- Columnas de mayoristas no reconocidas.
- Datos duplicados.
- Fórmula o valor inesperado.

Los errores deben almacenarse en:
```
price_import_items.error_message
```
y no deben detener silenciosamente toda la importación.

## 24. No utilizar 0 como ausencia de precio

Este punto es obligatorio.

Si una celda del Excel está vacía:
```
Hidromundo = ""
```
no debe interpretarse como:
```
Hidromundo = 0
```
porque eso provocaría:
```
MIN(...) = 0
```
y generaría cálculos incorrectos.

Una celda vacía representa:
```
sin precio disponible
```
El motor solamente debe considerar precios válidos.

## 25. Multi-tenancy

Todas las nuevas tablas deben utilizar:

tenant_id

Los registros nunca deben cruzarse entre tenants.

Todas las búsquedas deben filtrar por tenant_id.

Esto incluye:

- plants
- products
- wholesalers
- plant_products
- wholesaler_prices
- price_import_batches
- price_import_items
- pricing_configurations
- price_calculations

No asumir que un id de una tabla pertenece al tenant actual solamente porque el FK exista.

Las consultas del módulo deben validar el tenant explícitamente cuando corresponda.

## 26. Integración con el formulario público

El formulario público actualmente utiliza:
```
plants
wholesalers
products
```
El nuevo módulo no debe romper esta relación.

La información de precios debe complementar estos catálogos.

La relación:
```
plant_products
```
puede servir posteriormente para determinar qué productos están disponibles para cada planta.

Los precios no deben duplicar los catálogos existentes.

## 27. Reglas para eliminación

No eliminar físicamente:

- plants
- products
- wholesalers

si existen relaciones históricas que dependan de ellos.

Las relaciones deberán utilizar:
```
is_active
```
cuando corresponda.

Las FK deben utilizar:
```
ON DELETE RESTRICT
```
siguiendo la estrategia actual del proyecto.

No utilizar CASCADE para eliminar información histórica de precios o cálculos.

Nota de implementación (26-09-2026): la relación `plant_products` admite
también **baja lógica** (`is_deleted`), para poder quitar de la matriz una
planta+producto que ya no se cotiza sin perder su información:

- Es una baja **lógica**, nunca física: `wholesaler_prices.plant_product_id` y
  `price_calculations.plant_product_id` referencian la relación con
  `ON DELETE RESTRICT` y ambos son históricos (§28).
- `wholesaler_prices` y `price_calculations` **no se tocan**: la relación dada
  de baja conserva sus precios y sus snapshots. Esto respeta "no eliminar
  información histórica" y "no CASCADE" de este §27.
- El índice único `uq_plant_products_tenant_plant_product` no incluye
  `is_deleted`: no puede haber dos filas de la misma relación, así que volver a
  crearla la **revivifica** en vez de insertar (tanto desde la matriz como
  desde la importación de Excel, que de otro modo fallaría con duplicate key).
- La baja la puede ejecutar solo el dueño (`is_owner`), igual que enviar un
  pedido a la papelera (ADR-011).
- Como `is_active` (§27, para desactivar) y `is_deleted` (para eliminar) son
  cosas distintas, desactivar NO elimina: la fila desactivada sigue en la
  matriz y se ve con el filtro de inactivos.
- Los consumidores que deben seguir viendo las relaciones dadas de baja usan
  `withDeleted()`: el precio de compra de los pedidos
  (`OrderService::purchasePricesFor()`, la relación es un dato de referencia)
  y la re-importación de precios (`PriceImportService`).

## 28. Historial y modificaciones

La información actual puede cambiar:
```

```
pero el historial de:
```

```
no debe modificarse.

Los snapshots históricos deben considerarse inmutables.

No utilizar:

## 35. Nota de implementación — margen por relación (columna R del Excel)

Implementado y verificado E2E (26-09-2026). **Cambio de alcance del §11 y del
§16**: el margen deja de ser un parámetro global del motor y pasa a ser un dato
de la **relación** `plant_products.margin`; la columna R del Excel real
(`MARGEN SERTOCO`) es su **fuente de verdad**. UI en
`docs/06_Design/pricing-admin.md`.

### 35.1 Decisión

- El margen es un **MONTO absoluto en S/ por combinación planta+producto**, no
  una tasa: `S = Q + margin` (no `Q * (1 + margin)`). Se guarda en
  `plant_products.margin DECIMAL(12,4) NOT NULL DEFAULT 0.1300`.
- `pricing_configurations.margin` se mantiene, pero **solo como default para
  relaciones nuevas**. `igv_rate` y `perception_rate` **siguen siendo globales**
  (se toman siempre de la configuración activa).
- `plant_products.is_deleted` (baja lógica, §27) y `margin` conviven: la fila
  dada de baja conserva su margen y lo revive intacto.

### 35.2 Precedencia del valor (de mayor a menor)

1. **Columna R del Excel** (importación): manda siempre, incluso si el margen
   fue editado a mano en la matriz o si la relación estaba dada de baja
   (revivificada). Un cambio de margen sin cambio de precio **también** dispara
   recálculo + snapshot.
2. **Edición manual** en `/precios` (modal "Editar precios" o "Nueva relación").
3. **Default de la relación**: `plant_products.margin` tal como quedó guardado.
4. **Default global** `pricing_configurations.margin` (solo si la relación no
   tiene valor; en la práctica no ocurre porque la columna es NOT NULL).

En el **preview de la importación** el margen de cada fila se muestra como
"cambia" cuando el valor de R difiere del margen vigente de la relación o del
default.

### 35.3 Validación del margen

- Número, `>= 0`, hasta **4 decimales**; acepta coma como separador decimal
  (`0,13` → `0.1300`) porque el archivo puede venir de Excel es-ES.
- **`0` es válido** y significa "sin margen" (`S = Q`). No confundir con el §24
  (celda vacía = sin precio, 0 explícito = error de precio): aquí el 0 sí es un
  dato.
- Negativo o no numérico → la fila se marca con error `invalid_margin` y no
  escribe nada.
- Se normaliza con `PricingAdminService::normalizeMargin()` /
  `number_format(..., 4)`, de modo que la BD siempre guarda 4 decimales.

### 35.4 Modelo de datos

- `plant_products.margin DECIMAL(12,4) NOT NULL DEFAULT 0.1300` (aplicado a la
  BD viva y reflejado en `docs/02_Database/database.sql`; no hay migraciones).
- `price_import_items.margin DECIMAL(12,4) NULL DEFAULT NULL`: auditoría por
  item del margen leído de R. Los 36 items históricos quedan en `NULL` (no se
  rellenan retroactivamente: no hay de dónde sacarlos).
- `PlantProduct` y `PriceImportItem` incluyen `margin` en `$fillable` con cast
  `decimal:4`.
- El **snapshot** `price_calculations.calculation_data` ya guardaba los factores
  del cálculo en `inputs`; el margen va ahí (`inputs.margin`) y **no** en
  `results` (los `results` son los 6 montos P/Q/S/T/U/V). El historial usa los
  factores de su día, no los vigentes.

### 35.5 Motor

- `PriceCalculator` resuelve el margen así: override explícito (`resolve()` /
  `calculate()` con margen) → `plant_products.margin` → default de la
  configuración activa. `forPlantProduct()` ya no necesita que exista
  configuración para el margen (solo para IGV y percepción).
- `PriceCalculator::resolve()` acepta el margen para que el **preview en vivo**
  del modal muestre el resultado con el valor que el usuario está tecleando y no
  con el guardado.
- Cadena intacta: P (REDONDEO del mínimo, 4dp) → Q = P/(1+igv) → **S = Q +
  margin** → T = S\*(1+igv) → U = T\*(1+percepción) → V = U. Se sigue operando
  a 12 decimales y redondeando half-away-from-zero solo al devolver.

### 35.6 Importación (PriceImportService)

- `const EXCEL_MARGIN_COLUMN = 17;` (columna R, 0-based).
- `excelMargin($row)`: cadena vacía → `NULL`; numérico >= 0 →
  `Decimal::round(..., 4)`; si no → `['margin' => null, 'error' =>
  'invalid_margin']`.
- `parse()`: el margen se parsea **después** del bucle de precios y solo se
  adjunta al grupo (`excel_margin`) si la fila tiene al menos un precio válido
  (ver la trampa del 0 de relleno en §33 punto 4). Si hay precios y el margen es
  inválido, el item queda `error` con `invalid_margin` y no se escribe nada.
- `calcPreview()`: el margen de cada fila es el de R (si la hay) y se muestra en
  la comparación contra la columna V (`calc.rows[].margin`).
- `confirm()`: `findOrRestoreRelation($plant, $product, $fileMargin)` aplica el
  margen del Excel; una relación **dada de baja** revive (`is_deleted = 0`,
  `is_active = 1`) con el margen de R; si solo cambia el margen (precios
  `unchanged`) también recalcula y registra snapshot.

### 35.7 API y UI

- `POST /api/pricing/prices/preview` acepta `margin` (opcional).
- `POST /api/pricing/prices` acepta `margin` (opcional): lo escribe en la
  relación y recalcula.
- `POST /api/pricing/relations` acepta `margin` (opcional, default = el de la
  configuración activa que propone el modal).
- Validación en `PriceApiController`: `nullable`, string, `max:20`, regex
  `^\d{1,10}(\.\d{1,4})?$`.
- `PriceController::index` expone `row.margin` y `config.default_margin` (alias
  de `config.margin`, que se conserva por compatibilidad).
- `Pages/Platform/Pricing/Index.jsx`: columna "Margen" en la matriz, campo en el
  modal de edición (con preview en vivo debounced 400 ms) y en el de nueva
  relación (prellenado con el default); columna en el drawer "Ver cálculos".
- `Pages/Platform/Pricing/Import.jsx`: columna de margen en el detalle de items
  y en la comparación con el motor.
- `PricesExport`: columna de margen por fila.
- i18n (`lang/es/pricing.php`): `margin_col`, `margin_field`, `margin_hint`,
  `margin_default_hint`, `margin_col_import`, `calc_active`,
  `errors.invalid_margin`.
