# ADR-022: Procesamiento asíncrono mediante Laravel Queues

**Estado:** Accepted  
**Fecha:** 2026-10-03  
**Alcance:** Backend / Procesamiento asíncrono / Formulario público / Pedidos / Tareas pesadas  
**Proyecto:** Plataforma multi-tenant de gestión de pedidos

---

## 1. Contexto

La plataforma debe ejecutar diferentes tipos de operaciones:

- Creación de pedidos desde el formulario público.
- Validación anti-bot mediante reCAPTCHA.
- Procesamiento de documentos y archivos.
- Generación de PDFs.
- Generación de reportes.
- Procesamiento de archivos Excel.
- Importación de precios.
- Cálculos o procesos que puedan involucrar muchos registros.
- Envío de correos electrónicos.
- Notificaciones.
- Procesamiento de imágenes.
- Exportaciones.
- Integraciones con servicios externos.
- Otros procesos que puedan aumentar el tiempo de respuesta HTTP.

A medida que la plataforma crezca y sea utilizada por diferentes tenants, algunas de estas operaciones pueden consumir recursos durante varios segundos o incluso minutos.

No se desea que una petición HTTP permanezca esperando innecesariamente mientras Laravel ejecuta tareas pesadas.

---

## 2. Problema

Ejecutar todas las operaciones directamente durante una petición HTTP puede producir:

- Respuestas lentas.
- Timeouts.
- Mayor consumo de memoria.
- Mayor consumo de CPU.
- Mala experiencia para el usuario.
- Problemas cuando se generan PDFs o reportes grandes.
- Problemas al procesar archivos.
- Bloqueos durante importaciones.
- Mayor riesgo de fallos cuando intervienen servicios externos.
- Dificultad para reintentar operaciones fallidas.

La plataforma necesita una estrategia clara para determinar qué procesos deben ejecutarse de forma síncrona y cuáles mediante colas.

---

## 3. Decisión

La plataforma utilizará **Laravel Queues** para ejecutar de manera asíncrona las operaciones que sean:

1. Potencialmente pesadas.
2. Lentas.
3. Costosas en CPU o memoria.
4. Dependientes de servicios externos.
5. Basadas en archivos grandes.
6. Repetitivas o procesadas en segundo plano.
7. No necesarias para completar inmediatamente la respuesta HTTP.
8. Susceptibles de necesitar reintentos.

No se utilizarán colas indiscriminadamente para todas las operaciones.

Las operaciones CRUD simples y las acciones que necesitan devolver inmediatamente un resultado al usuario permanecerán síncronas.

---

## 4. Regla principal

Antes de implementar una nueva funcionalidad, se debe determinar si el proceso:

```
¿Necesita terminar para poder responder correctamente al usuario?
        │
        ├── Sí → proceso síncrono
        │
        └── No
             │
             └── ¿Puede ser pesado, lento, externo o costoso?
                    │
                    ├── Sí → Laravel Queue
                    │
                    └── No → proceso síncrono
```
No se debe enviar a Queue una operación únicamente por el hecho de que exista la posibilidad de utilizarla.

## 5. Formulario público de pedidos

El formulario público es especialmente importante porque debe responder rápidamente y no debe quedar bloqueado por procesos secundarios.

La creación del pedido debe dividirse conceptualmente en:
```
Formulario público
       │
       ├── Validación de datos
       │
       ├── Validación reCAPTCHA
       │
       ├── Validación de tenant
       │
       ├── Creación del pedido
       │
       └── Generación del código
              │
              ▼
        Respuesta HTTP
              │
              ▼
        Procesos secundarios
              │
              ├── Notificaciones
              ├── Correos
              ├── Procesamiento de archivos
              ├── Auditoría adicional
              └── Otros procesos pesados
```
### 5.1 Creación del pedido

La creación básica del pedido debe permanecer síncrona.

Debe completarse antes de responder al usuario porque el sistema necesita garantizar:

- Que el pedido fue creado correctamente.
- Que pertenece al tenant correcto.
- Que tiene un order_id válido.
- Que tiene un code válido.
- Que sus detalles principales fueron guardados correctamente.
- Que la transacción de base de datos terminó correctamente.

El usuario debe recibir inmediatamente una confirmación similar a:

Pedido registrado correctamente.
```
Código: PED-000125
```

No se debe crear el pedido únicamente dentro de una Queue si el usuario necesita inmediatamente su código y confirmación.

## 6. Procesos posteriores al pedido

Una vez confirmado y guardado correctamente el pedido, los procesos que no sean necesarios para completar la respuesta pueden enviarse a Queue.

Ejemplos:

Pedido creado
    │
    ├── Enviar correo de confirmación → Queue
    │
    ├── Enviar notificación → Queue
    │
    ├── Procesar archivos → Queue si corresponde
    │
    ├── Procesar imágenes → Queue
    │
    ├── Registrar procesos secundarios → Queue
    │
    └── Integraciones externas → Queue

La respuesta HTTP no debe esperar a que estos procesos terminen.

7. reCAPTCHA

La validación de reCAPTCHA que determina si el usuario puede crear el pedido debe realizarse de manera síncrona.

Motivo:

El resultado de reCAPTCHA es necesario antes de aceptar la creación del pedido.

Flujo:
```
Formulario
   ↓
reCAPTCHA
   ↓
Validación Laravel
   ↓
Validación reCAPTCHA
   ↓
Crear pedido
   ↓
Despachar tareas secundarias
   ↓
Responder
```

No se debe enviar la validación principal de reCAPTCHA a una Queue si eso significa aceptar el pedido antes de saber si la solicitud es legítima.

## 8. Operaciones que deberían utilizar Queue

Como regla general, las siguientes operaciones deben evaluarse para ejecutarse mediante Queue:

### 8.1 Correos

Ejemplos:

- Confirmación de pedido.
- Notificación de cambio de estado.
- Notificación al administrador.
- Correos automáticos.
- Correos masivos.

Ejemplo conceptual:
```
SendOrderConfirmation::dispatch($order->id);
```

### 8.2 Notificaciones

Las notificaciones que no sean necesarias para completar inmediatamente la operación deben procesarse mediante Queue.

### 8.3 Generación de PDF

La generación de PDFs debe utilizar Queue cuando:

- El documento sea complejo.
- Incluya gráficos.
- Incluya muchas páginas.
- Utilice Browsershot/Chromium.
- Requiera procesamiento considerable.

Ejemplo conceptual:
```
GenerateOrderPdf::dispatch($order->id);
```

La aplicación no debe bloquear innecesariamente una petición HTTP esperando la generación completa de un PDF pesado.

## 9. Reportes

Los reportes grandes deben utilizar Queue.

Ejemplos:

- Reportes mensuales.
- Reportes de ventas.
- Reportes con ECharts.
- Reportes PDF.
- Exportaciones grandes.
- Reportes que combinan múltiples consultas.

Para reportes pequeños que puedan generarse rápidamente, se permite procesamiento síncrono.

La decisión debe basarse en el costo real o esperado del proceso.

## 10. Importaciones de Excel

Las importaciones de Excel deben utilizar Queue cuando impliquen:

- Muchas filas.
- Cálculos por fila.
- Actualización de múltiples registros.
- Procesamiento de precios.
- Validaciones complejas.
- Generación de resultados o historial.

El proceso recomendado será:
```
Usuario
   ↓
Sube Excel
   ↓
Validación inicial
   ↓
Guardar archivo
   ↓
Crear registro de importación
   ↓
Dispatch Job
   ↓
Respuesta inmediata
   ↓
Procesamiento en segundo plano
   ↓
Actualizar estado
```

Estados sugeridos:

- PENDING
- PROCESSING
- COMPLETED
- FAILED

No es necesario implementar todos estos estados para cualquier Job, pero deben utilizarse cuando el usuario necesite conocer el progreso o resultado de un proceso largo.

## 11. Procesamiento de archivos

Los archivos grandes o procesos relacionados con archivos deben evaluarse para Queue.

Ejemplos:

- Compresión.
- Conversión.
- Optimización.
- Procesamiento de imágenes.
- Generación de miniaturas.
- Lectura masiva de documentos.
- Procesamiento posterior a una subida.

La subida básica del archivo puede permanecer síncrona si es necesaria para confirmar que el archivo fue recibido.

El procesamiento posterior puede ejecutarse en Queue.

## 12. Integraciones externas

Las operaciones que dependan de APIs o servicios externos deben utilizar Queue cuando no sea necesario esperar la respuesta para completar la operación principal.

Ejemplos:

- Servicios de correo.
- Servicios de notificaciones.
- APIs externas.
- Webhooks salientes.
- Integraciones con proveedores.
- Sincronizaciones.

Esto permite utilizar:

- Reintentos.
- Backoff.
- Manejo de errores.
- Registro de fallos.

No se debe hacer que una API externa lenta bloquee innecesariamente la petición principal.

## 13. Jobs

Cada proceso pesado debe implementarse como un Job independiente y con una responsabilidad clara.

Ejemplos:
```
app/Jobs/

SendOrderConfirmation.php
GenerateOrderPdf.php
GenerateSalesReport.php
ProcessPriceImport.php
ProcessUploadedFile.php
SendOrderNotification.php
```

Los nombres deben representar la acción que ejecuta el Job.

Evitar Jobs genéricos que realicen demasiadas responsabilidades diferentes.

## 14. Identificadores en los Jobs

Siempre que sea posible, los Jobs relacionados con entidades de negocio deben trabajar con identificadores y no transportar grandes cantidades de información innecesaria.

Preferentemente:
```
GenerateOrderPdf::dispatch($order->id);
```
en lugar de transportar estructuras completas del pedido.

El Job puede recuperar la información necesaria desde la base de datos.

Esto reduce el tamaño de la información serializada y evita transportar estados obsoletos innecesariamente.

## 15. Transacciones y Queue

No se debe despachar una Queue que dependa de datos que todavía no fueron confirmados en la base de datos.

Incorrecto:
```
BEGIN TRANSACTION

Crear pedido

Dispatch Job

ROLLBACK
```
El Job podría ejecutarse antes de que los datos existan realmente.

La implementación debe garantizar que los Jobs dependientes de una transacción se ejecuten después de que la transacción haya sido confirmada.

Cuando corresponda, utilizar el mecanismo de Laravel para despachar Jobs después del commit de la transacción.

Conceptualmente:
```
BEGIN
   ↓
Guardar datos
   ↓
COMMIT
   ↓
Dispatch Job
```
o utilizar explícitamente la capacidad de Laravel para ejecutar el Job después del commit.

## 16. Reintentos

Los Jobs que dependan de servicios externos o procesos que puedan fallar temporalmente deben permitir reintentos.

Cada Job debe definir, según corresponda:
```
tries
backoff
timeout
```
Los valores deben ajustarse al proceso.

No establecer valores arbitrariamente iguales para todos los Jobs.

## 17. Jobs fallidos

Los Jobs que fallen definitivamente deben poder registrarse mediante el mecanismo de Laravel para Jobs fallidos.

La aplicación debe permitir posteriormente identificar:

- Qué Job falló.
- Cuándo falló.
- Cuántos intentos realizó.
- Qué excepción ocurrió.

No se debe ocultar silenciosamente un fallo de Queue.

## 18. Idempotencia

Los Jobs que puedan ejecutarse más de una vez deben diseñarse considerando idempotencia.

Ejemplo:

Si un Job envía una notificación, un reintento no debería provocar consecuencias duplicadas no deseadas cuando sea posible evitarlo.

Si un Job actualiza un reporte, debe poder ejecutarse nuevamente sin corromper la información.

La implementación debe evitar depender de que un Job se ejecute exactamente una sola vez.

## 19. Driver de Queue

La arquitectura debe utilizar la abstracción oficial de Laravel Queue.

No se debe acoplar la lógica de negocio directamente a un proveedor específico.

El driver inicial puede definirse mediante configuración:
```
QUEUE_CONNECTION=
```
Para desarrollo puede utilizarse un driver sencillo.

Para producción se debe utilizar un mecanismo persistente y adecuado al entorno de despliegue.

La elección del driver de producción debe quedar separada de la lógica de los Jobs.

## 20. Worker

La aplicación debe contemplar la ejecución de workers de Laravel para procesar las colas.

Conceptualmente:
```
Laravel Application
       │
       ├── HTTP Requests
       │
       └── Queue
             │
             └── Worker
                   ├── Job 1
                   ├── Job 2
                   ├── Job 3
                   └── ...
```
El worker no debe ser ejecutado dentro de una petición HTTP.

En producción debe existir un proceso independiente encargado de consumir la Queue.

## 21. No convertir todo en Queue

No deben utilizarse Jobs para operaciones simples que:

- Son rápidas.
- Necesitan respuesta inmediata.
- Son CRUD normales.
- Requieren inmediatamente el resultado.
- No presentan un costo significativo.

Ejemplos normalmente síncronos:

- Crear cliente
- Editar cliente
- Eliminar/desactivar cliente
- Crear producto
- Editar producto
- Consultar pedido
- Cambiar estado simple
- Buscar catálogo
- Actualizar configuración

Siempre se debe evaluar el costo real de la operación antes de enviarla a Queue.

## 22. Separación entre HTTP y procesos pesados

Los Controllers no deben contener grandes bloques de procesamiento pesado.

Preferentemente:
```
Controller
   ↓
Validación
   ↓
Service / acción de negocio
   ↓
Guardar información necesaria
   ↓
Dispatch Job
   ↓
Respuesta HTTP
```
Los Jobs contienen el procesamiento asíncrono.

Esto permite mantener los Controllers pequeños y facilita las pruebas.

## 23. Services y Jobs

La arquitectura existente de Services debe mantenerse.

Las responsabilidades deben separarse:
```
Service
    → lógica de negocio reutilizable

Job
    → ejecución asíncrona de un proceso

Controller
    → HTTP / entrada y respuesta

Model
    → persistencia y relaciones
```
No colocar toda la lógica del sistema directamente dentro de un Job.

Cuando un proceso necesite lógica de negocio compleja, el Job puede utilizar un Service especializado.

## 24. Multi-tenancy

Todos los Jobs relacionados con datos de negocio deben conservar el contexto del tenant.

Un Job nunca debe procesar información de otro tenant.

Ejemplo conceptual:
```
Job
 ├── tenant_id
 └── entity_id
```
Cuando corresponda, el Job debe recuperar la entidad verificando explícitamente su pertenencia al tenant.

Nunca asumir que un order_id por sí solo es suficiente para determinar el contexto de seguridad.

La lógica debe mantener el aislamiento:
```
Tenant A
   └── Job → Order A

Tenant B
   └── Job → Order B
```
Nunca:
```
Job → Order ID
        ↓
buscar sin tenant
```
cuando el contexto pueda provocar acceso cruzado.

## 25. Logs

Los procesos importantes ejecutados mediante Queue deben producir logs suficientes para diagnosticar problemas.

No se deben registrar datos sensibles innecesarios.

Los logs deben permitir identificar como mínimo:

- Tipo de proceso.
- Entidad relacionada.
- Tenant.
- Resultado.
- Error cuando corresponda.

## 26. Procesos futuros

Esta arquitectura debe permitir incorporar posteriormente:

- Procesamiento masivo de pedidos.
- Importaciones.
- Exportaciones.
- Reportes programados.
- Correos programados.
- Sincronizaciones.
- Integraciones externas.
- Procesamiento de imágenes.
- Generación masiva de PDFs.
- Tareas programadas.

No implementar funcionalidades futuras únicamente para demostrar el uso de Queue.

La arquitectura debe quedar preparada para ellas.

## 27. Reglas para OpenCode

Antes de implementar Queue, OpenCode debe:

- Revisar la arquitectura actual.
- Identificar Controllers, Services y procesos existentes.
- Identificar operaciones potencialmente pesadas.
- No crear Jobs duplicados para procesos que ya tengan una implementación reutilizable.
- No mover automáticamente todos los CRUD a Queue.
- Mantener las operaciones que necesitan respuesta inmediata de forma síncrona.
- Mantener la creación principal del pedido síncrona.
- Mantener la validación de reCAPTCHA síncrona.
- Ejecutar mediante Queue los procesos secundarios que no sean necesarios para responder.
- Mantener el aislamiento por tenant.
- Utilizar Jobs independientes y con responsabilidades claras.
- Implementar reintentos y backoff cuando corresponda.
- Configurar timeout apropiado para Jobs pesados.
- Considerar idempotencia.
- Evitar despachar Jobs antes de confirmar una transacción de base de datos.
- Utilizar after commit cuando el Job dependa de datos recién creados dentro de una transacción.
- No almacenar información innecesaria dentro del payload del Job.
- Mantener la lógica de negocio reutilizable en Services cuando corresponda.
- No modificar funcionalidades existentes que no estén relacionadas con esta decisión.
- No introducir un proveedor externo de Queue sin necesidad.
- Utilizar la abstracción oficial de Laravel Queue.
- Documentar cualquier nueva Queue, Job o configuración agregada.


## 28. Criterios de aceptación

La implementación será considerada correcta cuando:

- Laravel Queue esté correctamente configurado.
- Exista una estrategia clara de ejecución asíncrona.
- La creación del pedido público no quede bloqueada por procesos secundarios.
- reCAPTCHA continúe siendo validado antes de aceptar el pedido.
- Los procesos pesados identificados utilicen Jobs.
- Los CRUD simples continúen funcionando de forma síncrona.
- Los Jobs mantengan el contexto del tenant.
- Los Jobs importantes tengan manejo de errores.
- Los Jobs que lo requieran tengan reintentos.
- Se considere la ejecución después del commit.
- Exista soporte para identificar Jobs fallidos.
- Los Workers puedan ejecutarse independientemente del proceso HTTP.
- La implementación sea extensible para futuros procesos.

## 29. Resultado esperado

La arquitectura final debe permitir que una petición HTTP realice únicamente el trabajo necesario para responder rápidamente.

Ejemplo para el formulario público:
```
Usuario
   ↓
Formulario
   ↓
Validación
   ↓
reCAPTCHA
   ↓
Crear pedido
   ↓
Generar código
   ↓
COMMIT
   ↓
Dispatch Jobs
   ↓
Respuesta inmediata
```
Mientras los procesos secundarios continúan:
```
Queue Worker
   │
   ├── Enviar confirmación
   ├── Procesar archivos
   ├── Generar documentos
   ├── Ejecutar notificaciones
   └── Otros procesos pesados
```
El usuario no debe esperar innecesariamente a que terminen dichos procesos.

## 30. Decisión final

Se adopta Laravel Queues como mecanismo estándar de procesamiento asíncrono de la plataforma.

La Queue se utilizará de forma selectiva para operaciones pesadas, lentas, externas o que no sean necesarias para completar inmediatamente una respuesta.

La creación principal de entidades y operaciones CRUD simples permanecerán síncronas cuando el resultado sea necesario inmediatamente.

En el formulario público, la validación de seguridad y la creación del pedido serán síncronas; los procesos posteriores y potencialmente pesados serán delegados a Jobs.

Esta decisión busca mejorar:

- Rendimiento.
- Tiempo de respuesta.
- Escalabilidad.
- Tolerancia a fallos.
- Capacidad de reintento.
- Experiencia del usuario.
- Preparación para crecimiento multi-tenant.
