# ADR-001: Initial Database Structure

- **Status:** Accepted
- **Date:** 2026-09-18
- **Scope:** Sertoco prototype

## Context

The existing Sertoco workflow uses a simple form to register fuel
delivery orders.

The form contains general order information, customer information,
driver and vehicle information, and a dynamic table containing the
products and quantities associated with the order.

Several fields are selected from information already registered by
Sertoco.

The prototype needs to reproduce this workflow while keeping the
database extensible for future validations and integrations.

## Decision

We will use a relational MySQL database centered on the `orders` entity.

The initial business tables are:

```
advisors
customers
wholesalers
plants
products
drivers
vehicles
orders
order_details
media_files
```
## Catalogs


Advisors, plants, wholesalers and products are independent catalogs.

They are stored in separate tables and referenced by foreign keys.

These catalogs use is_active to allow records to be deactivated
without removing historical references.

## Customers, drivers and vehicles

Customers, drivers and vehicles are modeled as independent entities
instead of storing all their information directly in orders.

This allows the same entity to be reused across multiple orders and
provides a foundation for future enrichment through external legal or
regulatory information.

A customer may optionally have a preferred wholesaler. This preference
is only a reference for convenience and does not determine the
wholesaler actually used in an order.

## Vehicles

Vehicles are stored in a single vehicles table.

The initial vehicle types are:
```
TANKER
TRACTOR
```
An order references one tanker and one tractor.

The current prototype does not model individual tanker compartments.

## Order details

An order has one-to-many order_details.

Each detail stores:

- SCOP
- Plant
- Wholesaler
- Product
- Gallons
- Sale price
- Compartments

SCOP is considered part of the order detail because it belongs to the
specific product/operation represented by that row.

compartments represents the quantity or portion of tanker
compartments assigned to the product. Individual compartment
identification is not modeled in this first stage.

## Order totals

For the prototype, totals are calculated from the order details:
```
detail_total = gallons × sale_price

total_gallons = SUM(gallons)

total_sale = SUM(gallons × sale_price)
```
Totals will not be stored as independent fields during this stage.

The definitive business calculation will replace this provisional rule
when the actual business rules are provided.

### Update ADR-013 (2026-09-27): ganancia por margen

Two totals were added when the pricing module (ADR-010) reached the order
detail, and their semantics were fixed by ADR-013:

```
total_purchase = SUM(gallons × precio de compra de la celda ganadora)
                 (wholesaler_prices, ADR-010; null si NINGUNA línea tiene precio)

margin(detalle)        = plant_products.margin de (plant_id, product_id)
                         (monto absoluto en S/ por galón, columna R del Excel;
                          null si la relación no existe)
margin_amount(detalle) = gallons × margin(detalle)
gain(pedido)           = SUM(margin_amount de sus detalles)
                         (null si NINGÚN detalle tiene margen)
```

`gain` **dejó de ser** `total_sale - total_purchase` (ADR-013 §3): el margen es
un dato que el negocio conoce aunque falte el precio de compra de alguna línea,
mientras que la resta dependía de que todas las líneas tuvieran precio. El
porcentaje de margen (`totals.margin`) se **eliminó**: la información vive ahora
línea a línea en la tabla de detalle. Todos los montos se suman con **bcmath**
(nunca float) y se redondean a 2 decimales.

Los depósitos del cliente (`order_deposits`, ADR-013 §4) **no** son un total del
pedido: se listan aparte con su propio "Total depositado" calculado en pantalla
(`SUM(amount)` de las filas activas), y no se almacenan como campo del pedido.

## File storage

Files are generalized through a centralized media_files table instead
of creating a table specifically for orders.

media_files uses a polymorphic relationship through:
```
model_type
model_id
```
This allows the same file repository to be used by different entities,
such as orders, customers, drivers or vehicles, without creating a
separate file table for each entity.

The table stores file metadata and storage information, including:

- Related entity
- Storage disk
- Directory
- Physical file name
- Extension
- MIME type
- General file type
- File size
- Image dimensions when applicable
- SHA-256 hash when available
- Visibility
- Original file name
- Creation/update information
- Logical deletion status

The file binary itself is not stored in the database.

Invoices, vouchers and other supporting documents associated with an
order will therefore be represented as records in media_files.

Files related to sensitive business documents should use private
visibility and be served through an appropriate application-level
access mechanism.

Because model_type and model_id form a polymorphic relationship,
referential integrity for the related entity is handled at the
application level rather than through a conventional foreign key.

Active catalog records

Catalog entities use is_active instead of physical deletion for
normal deactivation.

This allows historical orders to continue referencing existing catalog
records.

Transactional records are not removed merely to deactivate related
master data.

## Consequences
Positive
- Clear separation between master data and transactions.
- Order details can grow dynamically.
- Historical orders retain foreign-key references to the original
entities.
- Customers, drivers and vehicles can be reused across multiple orders.
- Future external integrations can enrich customers, drivers and
vehicles.
- Catalog records can be deactivated without deleting them.
- A single media_files repository can handle files from different
entities.
- The file storage structure can be extended without creating new
file tables for each module.
- The provisional calculation can be changed without redesigning the
entire database.
- The structure provides a foundation for future modules without
overcomplicating the first prototype.
## Limitations
- Historical snapshots of master data are not implemented yet.
- Compartment-level identification is not modeled individually.
- External legal/regulatory integrations are not implemented.
- The final order total formula is not yet known.
- Polymorphic file relationships do not have database-level foreign-key
enforcement and therefore depend on application-level integrity.
- File access and authorization rules are not fully defined yet.
- Multi-tenancy is not implemented in this prototype.
- The initial media_files structure is intentionally smaller than the
one used in the Sertoco SaaS project and can be extended if future
requirements justify additional metadata.
