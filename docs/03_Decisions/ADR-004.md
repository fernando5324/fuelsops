# ADR-004: Flujo público → interno y modelo de estados de pedido

**Estado:** Aceptado
**Fecha:** 2026-09-18
**Ámbito:** Prototipo Sertoco

## Contexto

El sistema debe permitir el registro de pedidos de entrega de
combustible a través de un formulario público, sin que el usuario final
necesite iniciar sesión.

Una vez registrado, el pedido debe ser visible y administrable por
usuarios internos autenticados en el panel administrativo.

Internamente, cada pedido pasa por distintos estados controlados por el
administrador. Los estados iniciales son: `pendiente`, `atendido` y
`anulado`. Por defecto, todo pedido registrado desde el formulario
público se guarda con estado `pendiente`.

En el futuro se deben poder agregar nuevos estados sin modificar el
esquema de la base de datos.

Se descartó modelar el estado como un campo `ENUM` dentro de `orders`
porque agregar un nuevo estado requeriría una operación `ALTER TABLE`
durante cada evolución del flujo.

## Decisión

### Formulario público

El registro de pedidos se realiza a través de un formulario accesible
sin autenticación:

```text
GET  /pedidos/registro   -> formulario público
POST /pedidos/registro   -> guarda el pedido
```

Al guardar, la orden se crea con estado `pendiente` (por defecto) y con
`created_by` igual al usuario `sistema`, ya que no existe un usuario
autenticado.

### Catálogo de estados

Se introduce una tabla catálogo `order_statuses`:

```text
id
code         (único, p. ej. pending, attended, cancelled)
name
description
color        (uso en la interfaz)
is_default
is_active

created_at, updated_at, created_by, updated_by   (véase ADR-005)
```

Los estados iniciales sembrados son:

| code      | name      | default |
|-----------|-----------|---------|
| `pending` | Pendiente | sí      |
| `attended`| Atendido  | no      |
| `cancelled`| Anulado  | no      |

Nuevos estados pueden agregarse al catálogo desde el panel interno sin
cambiar el esquema.

### Estado en el pedido

`orders` gana la columna `status_id` (`BIGINT UNSIGNED NOT NULL`) con
referencia a `order_statuses`. El valor por defecto lo asigna la
aplicación al crear la orden (`pendiente`).

### Historial de cambios de estado

Se introduce `order_status_history` para registrar cada cambio:

```text
id
order_id            -> orders
status_id           -> order_statuses (nuevo estado)
previous_status_id  -> order_statuses (estado anterior, nullable)
notes
created_at, updated_at, created_by, updated_by
```

El campo `created_by` registra el usuario interno que realizó el cambio
de estado. No se utiliza una columna adicional `changed_by` para evitar
duplicar la información de auditoría (véase ADR-005).

## Consecuencias

### Positivas

- El registro público no requiere autenticación.
- Los pedidos entran al sistema con un estado claro y controlado.
- El administrador puede cambiar el estado desde el panel y queda
  trazabilidad de cada cambio.
- Nuevos estados se agregan mediante el catálogo, sin cambios de
  esquema ni de código de migración.
- El historial permite auditar la evolución de cada pedido.

### Limitaciones

- `created_by` NOT NULL obliga a definir el usuario `sistema` para los
  envíos del formulario público (véase ADR-005).
- El catálogo de estados inicial (pendiente/atendido/anulado) es
  provisional hasta que Sertoco confirme su flujo real de estados.
- Las reglas de transición entre estados (p. ej. prohibir modificar un
  pedido anulado) aún no están definidas por completo — ver Roadmap
  Fase 4.

## Nota de implementación (flujo público)

El envío del formulario público ya no recibe `driver_id`/`tanker_id`/
`tractor_id`: el cliente escribe la licencia y las placas como texto y el
backend resuelve dichas entidades con find-or-create (mismo patrón que el
RUC del cliente), reutilizando los registros existentes de la
organización o creándolos con el usuario sistema. Un vehículo se identifica
por placa + tipo: la misma placa puede estar registrada como cisterna
(`TANKER`) y como tracto (`TRACTOR`) sin conflicto, pues la unicidad en BD es
`UNIQUE (tenant_id, license_plate, type)`.
Los lookups de autocompletado (`consulta-chofer`, `consulta-vehiculo`)
son consultas aditivas con throttle, igual que `consulta-cliente`.
