# ADR-012: Visualización de calculos en la tabla de precios.

- **Estado:** Implementado
- **Fecha:** 2026-09-26
- **Proyecto:** Sertoco
- **Relacionado con:** ADR-010 - Modelo de precios, importación de Excel y cálculo de precios


## 1. Contexto

Mejora visual de los calculos para los precios implementado opciones para que el usuario eliga cuando verlos y cuando no, esto para aligerar el consumo de recursos y darle la opcion al usuario de revisar los calculos cuando realmente lo necesite. 

---

Lo plantearía en tres niveles de interacción:

## 2. Tabla principal: mostrar solamente el resultado

Por cada fila mostraría los datos que realmente necesita revisar el usuario:

Ubicación	Producto	Mejor proveedor	Precio base	Precio final
Lima	Diesel	Proveedor A	S/ 10.50	S/ 12.45

Así el usuario puede editar los precios de proveedores y ver inmediatamente que el resultado cambia.

Por ejemplo:
```
Proveedor A     10.50
Proveedor B     10.80
Proveedor C     11.20
                 ↓
Mejor precio     10.50
Proveedor        A
Precio final     12.45
```

## 3. Una acción "Ver cálculo"

Agregaría una acción por fila:

Ver cálculo

Al hacer clic, abriría un pequeño panel/modal con el detalle:
```
Cálculo de precio
────────────────────────────

Menor precio
S/ 10.5000

Proveedor seleccionado
Proveedor A

Precio redondeado
S/ 10.5000

Precio sin IGV
S/ 8.8983

Margen
S/ 0.1300

Subtotal
S/ 9.0283

Precio con IGV
S/ 10.6534

Ajuste 1%
S/ 10.7600

Precio final
S/ 10.7600
```
Esto ya esta implementado pero mostraría también la fórmula utilizada, no solamente el resultado. 

Por ejemplo:
```
Precio sin IGV
10.5000 ÷ 1.18 = 8.8983
```
Eso hace que el usuario pueda entender por qué obtuvo ese precio.

## 3. Una opción para ver el cálculo completo de varias filas

También pondría una acción general, por ejemplo:
```
Ver cálculos
```
Esto podría abrir un panel donde se puedan revisar los cálculos de todos los productos de la ubicación seleccionada.

No haría que el usuario tenga que abrir 30 modales uno por uno si quiere revisar una actualización completa.

¿Y calculation_data?

Aquí creo que la decisión que tomaron está bien.

El JSON debería guardar el resultado y los valores utilizados para producirlo, por ejemplo:
```
{
    "source_price": 10.5,
    "source_wholesaler_id": 4,
    "minimum_price": 10.5,
    "rounded_price": 10.5,
    "price_without_tax": 8.8983,
    "margin": 0.13,
    "subtotal": 9.0283,
    "price_with_tax": 10.6534,
    "adjustment": 1.01,
    "final_price": 10.76
}
```
Así, cuando posteriormente cambien las reglas del cálculo, el historial conserva exactamente qué valores produjo el precio anterior.

Mi propuesta para la pantalla

Yo lo dejaría conceptualmente así:
```
┌───────────────────────────────────────────────────────────────┐
│ Precios                                                       │
│                                                               │
│ Ubicación: [ Lima ▼ ]      [ Ver cálculos ]                  │
├───────────────────────────────────────────────────────────────┤
│ Producto │ Prov. A │ Prov. B │ Prov. C │ Mejor │ Precio final│
├───────────────────────────────────────────────────────────────┤
│ Diesel   │ 10.50   │ 10.80   │ 11.20   │ A     │ 10.76  ⋮   │
│ Gasolina │ 12.20   │ 11.90   │ 12.10   │ B     │ 12.18  ⋮   │
│ ...                                                             │
└───────────────────────────────────────────────────────────────┘

⋮
 ├── Editar precios
 └── Ver cálculo
```
Y al seleccionar Ver cálculo, mostrar el desglose.

En resumen

Yo utilizaría:

Tabla: precios de proveedores + resultado principal.
Por fila: Ver cálculo.
General: Ver cálculos para revisar varios.
JSON: conservar todo el cálculo realizado al guardar.
No: convertir N–V en columnas permanentes de la tabla.

Esto mantiene la interfaz limpia, pero no oculta la información: simplemente la presenta cuando realmente se necesita. Además, para el usuario que viene acostumbrado al Excel, el "Ver cálculo" por fila le permite comprobar exactamente cómo se llegó al precio final sin volver a tener una tabla inmanejable.

## 4. Nota de implementación (26-09-2026)

Implementado según lo propuesto, con dos ajustes respecto del texto original:

1. **Sin conmutador de vista.** La idea de §1 ("opciones para que el usuario
   elija cuándo verlos y cuándo no") se resolvió con acciones secundarias en
   lugar de un modo de tabla alternativo: la matriz principal **no cambia** y
   el detalle se abre bajo demanda. Se descartó una opción adicional tipo
   conmutador "compacto / detallado" en la tabla.
2. **Los factores salen del resultado, no del front.** La fórmula se arma con
   los propios factores del cálculo (`igv_rate`, `margin`, `perception_rate`),
   de modo que si cambia la configuración del tenant la fórmula mostrada
   cambia con ella y sigue cuadrando con el valor.

Lo sí se respetó al pie de la letra:

- `PriceController::calculationFor()` ahora entrega, en cada fila de
  `rows.data`, el **mismo desglose completo** que ya devolvía
  `POST /api/pricing/prices/preview` (11 claves, todas como string decimal de
  4: `best_price`, `rounded_price`, `winner_wholesaler_id`,
  `purchase_price`, `margin`, `igv_rate`, `perception_rate`, `sale_price`,
  `sale_price_with_igv`, `sale_price_with_perception`, `final_price`).
  Es **aditivo**: el export a Excel y las columnas que ya existían siguen
  usando las tres claves que usaban.
- El JSON del historial **no se cambió**: ya guardaba `source`, `inputs`
  (incl. `best_price`, `margin`, `igv_rate`, `perception_rate`) y `results`,
  que es la estructura propuesta en este ADR. El drawer de historial ahora
  muestra la fórmula a partir del snapshot, así que la fórmula refleja el
  cálculo histórico real y no el de la configuración vigente.
- Componente compartido `CalculationBreakdown` (presentación pura) en las 4
  superficies: modal por fila, drawer general, preview del modal de edición y
  expandable del historial.
- Nomenclatura visible P / Q / S / T / U / V tal como aparece en el ejemplo de
  §3: Precio redondeado, Precio sin IGV, Subtotal, Precio con IGV, Ajuste
  percepción y Precio final.

**Detalle importante sobre el margen:** el ejemplo de §3 lo lista como
"S/ 0.1300" y el motor lo trata como **monto absoluto** que se suma a Q
(`S = Q + margen`), no como una tasa. Por eso en la interfaz se muestra como
monto al pie ("Margen S/ 0.1300") y dentro de la fórmula del paso S
(`8.8983 + 0.1300 = 9.0283`), mientras que IGV y percepción sí se muestran
como porcentajes (18.00% / 1.00%).
