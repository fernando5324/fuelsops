# ADR-013: Margen por detalle y depósitos del cliente en el pedido

- **Estado:** Aceptado
- **Fecha:** 2026-09-27
- **Proyecto:** Sertoco
- **Área:** Pedidos / Precios / Tesorería
- **Relacionado con:** ADR-001 (modelo de pedidos y totales), ADR-010 §35 (margen
  por relación planta+producto), ADR-011 (papelera de pedidos), ADR-012
  (visualización de cálculos)

---

## 1. Contexto

El detalle del pedido (`/pedidos/{order}`) ya muestra el **precio de compra** de
cada línea: el backend resuelve la celda ganadora de `wholesaler_prices` para la
relación planta+producto y la mayorista de la línea (ADR-010). El usuario pidió
extender esa misma idea al margen:

- cada línea debe mostrar el **margen que le corresponde** a su planta y
  producto, igual que hoy muestra el precio de compra;
- el resumen financiero debe mostrar la **ganancia** como la suma de los
  márgenes de las líneas (no como venta − compra);
- el cuadro de **Margen (%)** que estaba al lado de Ganancia debe desaparecer,
  porque era un porcentaje derivado de la propia ganancia y duplicaba
  información que ahora vive línea a línea;
- el cuadro de **Depósitos**, hoy un placeholder vacío, debe permitir registrar
  los depósitos que el cliente paga y que llegan como vouchers adjuntos al
  pedido.

Preguntas resueltas con el usuario antes de implementar:

| Decisión | Valor elegido |
| --- | --- |
| Campos del depósito | banco, número de operación, monto y **fecha** |
| Operaciones sobre un depósito | **agregar** y **eliminar** (sin edición) |
| Ubicación de la multiplicación | **por fila** (`margen × galones`) y total en el pie de la tabla |

## 2. Decisión

1. El detalle del pedido muestra, por línea, `margin` y `margin_amount`, y el
   pie de la tabla totaliza `margin_amount`. La **Ganancia** del resumen es
   exactamente esa suma.
2. `totals` ya **no** expone la clave `margin` (el porcentaje); expone
   `total_gallons`, `total_sale`, `total_purchase` y `gain`.
3. Los depósitos del cliente se registran **manualmente** leyendo el voucher
   adjunto: el sistema guarda lo que el usuario capturó, sin interpretar el
   archivo.
4. El bloque de **depósitos de proveedor** sigue siendo un placeholder: no hay
   módulo de pagos ni de cuentas por cobrar hacia proveedores.

## 3. Márgenes: de dónde sale el número

El margen es un **monto absoluto en soles por galón** y pertenece a la
**relación planta + producto** (`plant_products.margin`, columna R del Excel,
ADR-010 §35). No depende del mayorista:

```
margin(detalle)         = plant_products.margin   de (plant_id, product_id)
margin_amount(detalle)  = gallons × margin(detalle)
gain(pedido)            = SUM(margin_amount de sus detalles)
```

Reglas de resolución (idénticas a las del precio de compra, para que ambas
columnas se lean igual):

- la relación se busca con `withDeleted()`: una relación **dada de baja**
  (`is_deleted = 1`) sigue dando su margen y sus precios al pedido, porque son
  datos históricos y el pedido no debe "perder" su referencia de precio;
- `is_active = 0` también se muestra (es un dato de referencia, no un estado de
  la operación);
- si **no existe** la relación planta+producto, `margin` y `margin_amount` son
  `null` y la UI muestra `—`. Nunca 0 (un 0 real significaría "sin margen");
- `margin` es **independiente** del precio: una línea sin precio de compra
  (celda vacía o precio 0) igual muestra su margen y suma a la ganancia.

La precisión es decimal con **bcmath** (`bcmul(..., 4)` por línea, `bcadd(...,
2)` al acumular), nunca float: los importes se registran en soles con 2
decimales y el margen vive con 4.

El total de la tabla y el cuadro Ganancia muestran el **mismo** valor: el pie usa
`totals.gain` (calculado en el backend con bcmath) en vez de recalcular la suma
en JavaScript, para que nunca haya diferencias de redondeo entre ambos.

## 4. Nueva tabla: `order_deposits` (sección 20 del esquema)

```sql
CREATE TABLE IF NOT EXISTS order_deposits (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id BIGINT UNSIGNED NOT NULL,
    order_id BIGINT UNSIGNED NOT NULL,
    deposit_date DATE NOT NULL COMMENT 'Fecha del depósito segun el voucher adjunto',
    bank VARCHAR(100) NOT NULL,
    operation_number VARCHAR(50) NOT NULL,
    amount DECIMAL(12,4) NOT NULL,
    created_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NULL DEFAULT NULL COMMENT 'Fecha y hora del registro en America/Lima',
    created_by BIGINT UNSIGNED NOT NULL,
    updated_by BIGINT UNSIGNED NULL,
    is_deleted TINYINT(1) NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    INDEX idx_order_deposits_tenant (tenant_id),
    INDEX idx_order_deposits_order (order_id),
    INDEX idx_order_deposits_date (deposit_date),
    INDEX idx_order_deposits_created_by (created_by),
    INDEX idx_order_deposits_updated_by (updated_by),
    CONSTRAINT fk_order_deposits_tenant FOREIGN KEY (tenant_id) REFERENCES tenants(id),
    CONSTRAINT fk_order_deposits_order  FOREIGN KEY (order_id)  REFERENCES orders(id),
    CONSTRAINT fk_order_deposits_created_by FOREIGN KEY (created_by) REFERENCES users(id),
    CONSTRAINT fk_order_deposits_updated_by FOREIGN KEY (updated_by) REFERENCES users(id),
    CONSTRAINT chk_order_deposits_amount CHECK (amount > 0)
);
```

Notas de diseño:

- **Una fila por depósito**, no un acumulado: el voucher es el documento y
  puede haber varios. El **total depositado se calcula en pantalla**
  (`SUM(amount)` de las filas activas) y no se persiste, para que dar de baja un
  depósito nunca deje un total mentiroso guardado.
- `amount` es `DECIMAL(12,4)` (misma precisión que los precios) con
  `CHECK (amount > 0)`: un depósito de 0 no es un depósito.
- **No hay unicidad** en `(order_id, operation_number)`: dos vouchers del mismo
  banco pueden compartir número de operación y, si el negocio lo necesita,
  obligaría a una excepción en el flujo de captura.
- `deposit_date` es `DATE` (no `DATETIME`): es una fecha de calendario del
  voucher, sin hora. Se castea a `date:Y-m-d` para que se serialice como
  `2026-09-22` y la UI la pinte como `22/09/2026` sin desfase de zona horaria.
- FK a `orders` con `ON DELETE RESTRICT` (convención del proyecto) y baja
  lógica con `is_deleted` vía el trait `LogicalDelete`.
- `tenant_id` + trait `BelongsToTenant`: un depósito de otra organización no es
  visible ni accesible (404), igual que el resto del pedido.

## 5. Captura manual de depósitos

No hay OCR ni lectura automática del voucher: el usuario **transcribe** los
datos y el sistema los registra. El formulario pide:

| Campo | Reglas |
| --- | --- |
| Fecha del depósito | obligatoria, no puede ser futura (`before_or_equal:today`) |
| Banco | obligatorio, máx. 100 |
| Número de operación | obligatorio, máx. 50 |
| Monto | obligatorio, `> 0`, hasta 4 decimales, acepta coma como separador en la UI |

El **deposit_date** no puede ser futuro porque un voucher siempre es un hecho
pasado; la UI reinforces con `disabledDate` en el `DatePicker`.

El banco es un `AutoComplete` con la lista de bancos del sistema (BCP, BBVA,
Interbank, Scotiabank, Bancoficial, Bancesud, Citibank, Credibank, Mibanco, Banco
de la Nación, Cajas Arequipa/Piura/Mars, "Otro") que **acepta texto libre**, para
que un banco que no esté en la lista se pueda escribir sin bloquear el flujo.

## 6. Operaciones: agregar y eliminar (sin editar)

- **Agregar**: cualquiera con sesión en el panel (igual que el cambio de estado);
  no es una acción reservada al dueño porque registrar un pago recibido es una
  operación de caja, no una eliminación de negocio.
- **Eliminar**: **baja lógica** (`is_deleted = 1`). La fila sigue existiendo y
  sale del cuadro de depósitos; el voucher adjunto **no** se toca.
- **No hay edición**: corregir un voucher se hace dando de baja el registro
  erróneo y registrando el correcto; así el histórico nunca se reescribe y cada
  baja queda auditada. Es la misma philosophy de `order_status_history`.
- No hay restauración de un depósito dado de baja desde la UI: el borrado es
  una corrección operativa, no una eliminación de negocio con papelera.

## 7. Permisos y aislamiento

- El alta y la baja no requieren `is_owner` (a diferencia de eliminar la
  relación de precios o enviar un pedido a la papelera).
- Un pedido en la papelera **no expone** sus depósitos por API: el
  route-model binding no resuelve pedidos con `is_deleted = 1` (el scope global
  de `LogicalDelete`), por lo que `POST`/`DELETE` sobre `/api/orders/{id}/deposits`
  responden **404**, igual que el resto de la API de pedidos. El
  `abort_if(... 409)` del controlador queda como red de seguridad por si algún
  día el binding se abriera a `withTrashed`.
- El depósito se resuelve **dentro del pedido** y con el scope del tenant:
  un id de otro pedido, de otra organización o ya dado de baja → **404**.
- En la UI el detalle en papelera es **solo lectura**: sin botón de agregar, sin
  columna de acciones y con un aviso de que los depósitos se conservan.

## 8. Interacción con la papelera (ADR-011)

ADR-011 §9/§12/§16/§21 marcaban los **pagos** como N/A porque no existía el
módulo. Con esta tabla:

- los depósitos **sobreviven** a la papelera (`is_deleted` del pedido no toca
  `order_deposits`): son información financiera del pedido;
- el snapshot de `order_deletions` cambia su bloque `payments: []` (placeholder)
  por **`deposits`**, con `id`, `deposit_date`, `bank`, `operation_number` y
  `amount` (como string decimal) de cada depósito **activo** en el momento de la
  eliminación;
- como el snapshot es informativo y la restauración usa los registros reales, la
  restauración no necesita tocar los depósitos.

## 9. Backend

- `Order::deposits()`: `hasMany` **ordenado del más reciente al más antiguo**

- `OrderService::storeDeposit(Order $order, array $data): OrderDeposit`: crea el

- `OrderService::buildSnapshot()`: el bloque `payments` se reemplaza por

- `StoreOrderDepositRequest`: validación de la tabla de la §5, con mensajes en

- `OrderApiController::storeDeposit()` / `destroyDeposit()` y rutas

## 11. Criterios de aceptación

1. `/pedidos/17` (relación planta 32 + producto 49 con margen 0.1300, 3000 gal)
   muestra Margen `0.1300`, Monto `390.0000` y Ganancia `S/ 390.00`.
2. Un detalle sin relación planta+producto muestra `—` en Margen y Monto, y si
   ningún detalle tiene margen la Ganancia es `—` (no `S/ 0.00`).
3. Una relación `is_active = 0` o `is_deleted = 1` sigue mostrando su margen y
   su precio de compra.
4. Una línea con precio de compra 0 muestra `—` en Precio de compra pero **sí**
   muestra su margen y suma a la Ganancia.
5. `totals` no contiene la clave `margin`.
6. Registrar un depósito lo guarda con `tenant_id` y `created_by` del usuario de
   sesión, y el detalle lo lista con su total.
7. Montos 0, negativos, con letras, con más de 4 decimales y fechas futuras se
   rechazan con 422 (y con 302 + errores en sesión en el flujo de Inertia).
8. `DELETE` da de baja el depósito (sale de la lista, la fila queda) y repetirlo
   responde 404; un depósito de otro pedido u otra organización también 404.
9. La ficha en papelera del pedido conserva los depósitos y no permite escribir.
10. El snapshot de `order_deletions` trae `deposits` y ya no trae `payments`.

## 12. Alternativas descartadas

- **Ganancia = venta − compra**: se descartó porque depende de que TODAS las
  líneas tengan precio de compra (si una no lo tiene, la ganancia vanishía) y
  porque el margen es un dato que el negocio conoce aunque falte el precio. El
  precio de compra sigue mostrándose aparte, como dato de referencia.
- **Margen como porcentaje en el resumen**: duplicaba la ganancia y confundía
  markup sobre el precio sin IGV (ADR-010 §35) con margen sobre el precio de
  venta. Se reemplaza por el monto por galón, línea a línea.
- **Editar depósitos**: se descartó para no reescribir el histórico de caja.
- **Depósito único acumulado por pedido**: se descartó porque hay varios
  vouchers y el total debe reflejar exactamente los documentos registrados.
- **OCR o lectura automática del voucher**: fuera de alcance; la captura es
  manual.
- **Depósitos de proveedor como registro de caja**: se descartó; el bloque es la
  **cuenta por pagar derivada** por mayorista (§14), sin vouchers ni saldos.

Tres defectos reales encontrados y corregidos por esta verificación:

1. `trash.deletion` puede ser **`null`** (el pedido 5 está en la papelera sin fila
   en `order_deletions`) y el banner leía `trash.deletion.deleted_at` sin
   guardia: la página entera reventaba con `Cannot read properties of null`.
   Ahora hay fallback con la clave `order.in_trash_banner_no_history`.
2. El monto se capturaba y guardaba con 4 decimales pero se pintaba con 2

   mostrado. Ahora la columna y el total usan `formatMoney(v, { digits: 4 })` y el

3. La clave `order.deposit_delete_warning` estaba definida pero **no se usaba**:
   la confirmación de borrado no aclaraba que el voucher adjunto no se modifica.

## 14. Depósito por proveedor: cuenta por pagar **derivada**

Decisión posterior a la primera versión de este ADR (27-09-2026), que dejó el
bloque como placeholder.

### 14.1 Qué es

El bloque **Depósitos por proveedor** del detalle del pedido pasa a mostrar, para
cada mayorista, **cuánto se le debe a ese mayorista por este pedido**:

``` text
por cada mayorista = SUM( galones × precio de compra de la celda de ESE mayorista )
                     (las líneas del detalle cuyo wholesaler_id es ese)
```

El total del cuadro es **exactamente** el cuadro **Compra** (`totals.total_purchase`),
que es lo que pidió el negocio. Ejemplo con datos reales (`/pedidos/17`): una sola
línea de **PRIMAX**, 3000 gal × 22.4672 = **S/ 67,401.60**, igual que su Compra.

El mayorista es **el de cada línea** (`order_details.wholesaler_id`, `NOT NULL`),
no el ganador global del motor: lo que Sertoco debe a un mayorista es lo que le
compró a ese mayorista. `/pedidos/1` tiene dos (Mayorista Lima y Mayorista Callao)
y por eso muestra dos filas.

### 14.2 Es dato DERIVADO, no un depósito

| | Depósitos del cliente (§4) | Depósito por proveedor (§14) |
|---|---|---|
| Origen | voucher transcrito a mano | cálculo desde las líneas |
| Se guarda | sí (`order_deposits`) | **no**, nada |
| Total | suma de los vouchers | `total_purchase` (el cuadro Compra) |
| Operaciones | alta y baja lógica | ninguna (solo lectura) |

No hay tabla, ruta, permiso ni escritura nueva. Se recalcula en cada lectura del
detalle, como `total_purchase` y `gain`. Por eso el bloque **no tiene columna de
acciones ni modal**: ni en el pedido activo ni en la papelera, y no se confunde
con el registro de caja del cliente (el diseño pide explícitamente no mezclarlos).

### 14.3 Backend

`OrderService::supplierPayables(Order $order): array`, en una sola pasada sobre
`$order->details`:

- el precio de la línea se resuelve **igual que en `totals()`**
  (`$detail->purchase_price ?? $pricing['purchases'][$purchaseKey]`), con las
  mismas 2 consultas constantes de `pricingFor()` y el mismo criterio `> 0`;
- acumula en paralelo el total y los subtotales por mayorista, con
  `bcmul(gallons, precio, 4)` + `bcadd(..., 2)`. El `total` se acumula con la
  **misma operación y sobre las mismas líneas en el mismo orden** que
  `total_purchase`, así que cuadra por construcción, no por coincidencia;
- devuelve `items` (`wholesaler_id`, `wholesaler_name`, `gallons`, `amount`,
  `lines`) ordenadas por monto descendente con desempate `wholesaler_id ASC`
  (criterio determinista, el mismo que usa el motor cuando dos mayoristas
  empatan), `total` y `lines_without_price`.

`lines_without_price` cuenta las líneas sin precio (celda vacía o 0 explícito):
no aportan al total —igual que en `total_purchase`— y la UI lo dice con
`:count línea(s) sin precio de compra: no se incluyen en el total`, en lugar de
mostrar un total aparentemente completo. Si ninguna línea tiene precio, `total`
es `null` y el bloque muestra su estado vacío.

`totals()` **no se modificó** (misma forma de array), así que los E2E que la
afirman siguen valiendo.

### 14.4 Frontend

- `Components/Orders/OrderDeposits.jsx`: el bloque derecho pasa de placeholder a
  tabla de 2 columnas (`order.wholesaler`, `order.amount`) + fila
  `order.supplier_total`, Tooltip con `order.supplier_payable_hint` (la fórmula y
  que el total coincide con Compra) y el aviso de líneas sin precio. El total
  mostrado es el que devuelve el backend, **no** la suma de las filas visibles.
- `Pages/Platform/Orders/Show.jsx`: prop `supplier_payables` (la reciben
  `OrderController::show` y `TrashController::show`).
- i18n: `order.supplier_total`, `order.supplier_payable_hint`,
  `order.supplier_no_price_lines`, `order.supplier_none` (se reutilizan
  `order.supplier_deposits`, `order.wholesaler` y `order.amount`).
- Sin CSS nuevo: reutiliza `.ui-order-deposit-block` y `.ui-empty-note`.

### 14.5 Alternativas descartadas

- **Registro de pagos reales al proveedor** (vouchers con banco, operación, fecha
  y monto, como los depósitos del cliente): exigiría una tabla nueva y CRUD, y
  su total sería el **saldo pendiente**, que ya no coincidiría con el cuadro
  Compra. El negocio pidió el monto a pagar, no el registro de caja.
- **Una fila por mayorista + producto**: con varias plantas el bloque se
  encoge; el detalle por línea ya está en la tabla de productos de arriba, así
  que el desglose se lee ahí. Se dejó una fila por mayorista.
- **Mostrarlo también en el drawer del listado y en la página pública de
  confirmación**: fuera de alcance de este ADR (el bloque vive en el detalle).

## Nota de implementación

- `attachPurchasePrices()` → `attachPricing()`: el nombre viejo se eliminó de
  todo el código (`OrderController`, `TrashController`, `OrderService`); no
  quedaron referencias colgadas.
- `pricingFor()` hace **una sola consulta** de `plant_products` y otra de
  `wholesaler_prices` para todo el pedido: el costo por pedido es constante
  (2 consultas) sin importar cuántas líneas tenga, en vez de una consulta por
  línea.
- Un `FormRequest` que falla responde **302 back** con los errores en sesión
  cuando la petición no es JSON; el E2E debe enviar `Accept: application/json`
  para afirmar el **422**. Ojo: el header `Accept` debe ir **con el prefijo
  `Accept: `** en `CURLOPT_HTTPHEADER` (si se manda el valor suelto, la cabecera
  se descarta y Laravel responde 302).
- El modelo castea `deposit_date` a `date:Y-m-d`: con el cast `date` a secas,
  Laravel serializaba `2026-09-22T05:00:00.000000Z` y el navegador podía pintar
  23/09 según la zona horaria del cliente.
- `amount` se valida con `gt:0` además del regex: sin esa regla, un monto `0`
  pasaba la validación y reventaba el `CHECK (amount > 0)` de MySQL con un 500.
- Los `DatePicker` de antd entrega un objeto `dayjs`; el submit lo convierte a
  `YYYY-MM-DD` antes de mandarlo al backend (`values.deposit_date.format(...)`).
- Gotcha heredado: en papelera `GET /pedidos/papelera/5` sí resuelve el pedido
  (usa `Order::onlyDeleted()` con resolución manual), mientras que
  `/api/orders/5/...` responde 404 por el binding normal.
- `trash.deletion` **no siempre existe**: un pedido puede estar en la papelera sin
  fila en `order_deletions` (se dio de baja con `LogicalDelete` directo antes de
  existir la papelera; en la base viva es el pedido 5). Cualquier lectura de
  `trash.deletion.*` en `Show.jsx` tiene que ir con guardia, o la página entera
  queda en blanco por una excepción en el render.
- Los montos de depósito se muestran con **4 decimales** (`formatMoney(v, {
  digits: 4 })`) porque esa es la precisión con la que se capturan y se guardan
  (`DECIMAL(12,4)`); con 2 decimales el detalle visible no suma el total visible.
- El test headless necesita **Node ≥ 22** para el `WebSocket` global (los
  `.mjs` de CDP); el `build` de Vite sigue con Node 20 (`v20.20.2`).
